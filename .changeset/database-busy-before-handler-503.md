When the database is too busy for a read that comes before the handler runs, a request answers `503 database-busy` with `Retry-After: 5` on any method, not `500 internal-server-error`: nothing ran, so sending it again is safe. That covers the read an authorization check makes (the tenant's store id, read before the store is asked), the `authorize` middleware's resource getter, the run a cancel, a resume or a provenance export reads to find its project, and the projects an agent, flow, guardrail, test set or tool is served in, read before its own checks and before a pin write's. Those checks of an item also answer `503 authz-backend-unavailable` on any method when the authorization store can't be reached, as the middleware's do. A busy database inside a handler still answers the 503 on a `GET` or `HEAD` and the 500 on any other method. A handler that goes on past a check's busy answer, as an Improve schedule's project admin who pauses it does, answers with its own status. The OpenAPI document's 503 on every operation that declares a 401 names `database-busy`.
