**`gmailReply` and `outlookReply` answer a mail in its thread,** with plain text: `{ inReplyTo, to, body }`, where `inReplyTo` is the message's id as the list tools give it. Each has `as: 'company'` for the company's mailbox, as the other mail tools do, and asks before an unattended reply, as a send does: in a mail's run, a reply waits for a yes unless the trigger lists it in `toolsAllowedUnattended`.
- **Where a reply goes:** the tool reads the mail and works out the one address it asks for, its Reply-To, else its From, as a mail client does. The call's `to` must name that address, in any letter case. A reply to a mail whose Reply-To (else From) names two addresses or none, or the mailbox's own, is refused, and so is a `to` that names another address: the refusal names the address the mail asks for, and nothing is sent. The sender of a mail chooses both headers, so an agent that replies mustn't give out an order's details on the From address alone.
- **`gmailReply`** sends in the message's thread with `In-Reply-To` and `References`, and the subject with `Re: ` before it. A value of the mail's goes into the reply's headers only once it's safe: a line break left in it once unfolded and decoded, or a message id that isn't `<…>` or runs past 900 characters, refuses the call. `References` keeps 20 ids, the first and the newest. In a run, the reply carries an `X-Reply-Ref` header with the run's mark, so a runtime reading the thread again knows the agent's own reply. It needs `gmail.send` and `gmail.readonly`, and answers the reply's id and its thread's.
- **`outlookReply`** posts to the message's `/reply` in Graph's JSON form, with the body as its comment and the one address as its recipient; Graph keeps it in Sent Items. Graph's reply takes no header of ours, so it carries no mark. It needs `Mail.Send` and `Mail.Read`, and answers `{ accepted: true }`.
