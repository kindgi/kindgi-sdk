A deploy can run under a project-only key scope, a server's own setting for the caller's key: its middleware, ahead of the deployments routes, sets `deployKeyScope` to `project`, and nothing in a request sets it. Under it, `POST /v1/deployments` records each of the pack's tools' secrets at the body's `projectId` only, a secret that project doesn't hold included, never at its org or the workspace. The deployment record says so (`keyScope: 'project'`), and the pack env check and the env served to the pack read that deployment's env at that project only. It refuses with `403 permission-denied`, and deploys nothing, a body that names no `projectId`, or a pack's tool version the runtime already holds that was made in another project or reads its secrets wider than that project (`details.primitive` is `tool`, `details.id` is `<id>@<version>`; give the tool a new version, or have an admin deploy). A version recorded inside the project still deploys. A promotion under the scope (`POST /v1/deployments/{deploymentId}/promotions`) is refused with `403 permission-denied` before the deployment is read, and nothing is written: it would record the build's secrets and pack env as wide as the caller reads them. Have a key without the scope promote it; the promotion check still answers. A deployment registry that doesn't say it keeps the scope (`keepsKeyScope`) gets `500 internal-server-error` before anything is written. Without the scope, nothing changes. The Python (`kindgi`) and JVM (`kindgi-models`, `kindgi-client`) clients show `keyScope` on `DeploymentRecord`.
