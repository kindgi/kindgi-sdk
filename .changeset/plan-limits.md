**A runtime can count the flows and agents in production against its license key's plan: at the plan, a write's answer warns, and past the most the key runs, a write that adds new ones is refused, with nothing written.** The app takes a plan limits binding (`planLimits`, a `PlanLimitsBinding`) and asks it on each write that can add a flow or an agent to production: publishing an agent or a flow (`POST /v1/agents`, `POST /v1/flows`) and reinstating a retired version of one, deploying (`POST /v1/deployments`), promoting a build (`POST /v1/deployments/{deploymentId}/promotions`), putting a project in production (`PUT /v1/projects/{projectId}/production`), and the agent version a suggested change's check makes. Past the most, the write is refused with `403 plan-limit-reached`, whose `details` name each count over and the ids the write adds; when its turn to count takes too long, with `503 plan-count-busy` and `Retry-After`, and a retry is safe. Once a count reaches its plan, these answers carry `planWarning` (`PlanWarning`: `flows` and `agents`, each a `PlanCount` with `plan`, `most` and `inUse`), and so do the deploy check's and a promotion check's, which answer as the write would. `POST /v1/deployments/check` takes the pack's `flows` too. Without a binding, nothing is counted, as before. `kindgi deploy` sends the pack's flows to the check and stops there on `plan-limit-reached`, with nothing deployed; it and `kindgi promote` print a line for each count the answer warns of, flows first. The client's types gain `planWarning` on those answers.
