Released November 5, 2026. For the docs of this version, see
[docs.kindgi.com/v0.5.0](https://docs.kindgi.com/v0.5.0/).

## New

- **Connections have names.** A connection takes its name when it's
  made: the one given at the connect, else its account's, such as an email
  address. The console's Connect dialog has Name (optional), and after the
  connect it asks for a name or keeps the account's. Rename one with Rename
  on the Connections page or on the connection's own page, with
  `kindgi connections update <connection> --label=<name>`, or with
  `PATCH /v1/connections/{connectionId}` and its `label`
  (`client.connections.update` in the clients). Its owner or a tenant
  admin may rename it.
  `kindgi connections connect <app> --label=<name>` names a new one. A
  name is 1 to 100 characters, with no control, format or invisible
  characters, and one owner's live connections of an app in an environment
  each have their own (`409 connection-label-taken`).
  `kindgi connections update`, `kindgi connection-choices set`,
  `--reconnect` and `--connection` take a connection's name or its id. A
  connection made before
  0.5.0 has no name until someone gives it one: the console shows its
  account, marked not named. A tool reads the name too, in every
  language: each connection in `ctx.connections` has its `name`, the
  connection's name, else its account's (pack protocol 2.11.0).

- **The company keeps a connection per account,** so it can connect two
  mailboxes of one app, such as support@acme.example and
  sales@acme.example. Connecting an account again reconnects its
  connection, which keeps its name, when the grant keeps every permission
  the connection holds. A connect can name the connection it reconnects:
  `reconnects` on `POST /v1/connections`, or `--reconnect=<connection>` on
  `kindgi connections connect`.

- **Choose which company connection an agent or a flow uses.** When a
  project has several company connections of an app, a project admin
  chooses one for each agent and flow: on the agent's and the flow's
  **Connections** page (Choose and Clear); with
  `kindgi connection-choices set <connection> --agent=<id>` (or
  `--flow=<id>`), `list` and `unset`; or over HTTP, with
  `GET` and `PUT /v1/connection-choices`,
  `DELETE /v1/connection-choices/{choiceId}` and
  `GET /v1/connection-choices/candidates` (`client.connectionChoices` in
  TypeScript, `client.connection_choices` in Python,
  `client.connectionChoices()` in Java). An unknown or removed choice is
  `404 connection-choice-not-found`. In the console, a connection's
  **Used by**, on its page and in Disconnect's confirm, lists the choices
  that name it and the mail triggers that store it. A flow's choice is
  for the tool steps the flow runs itself: an agent the flow runs uses its
  own. Within a run and the runs it starts, an agent or a flow keeps the
  connection its first call got through its choice, so replacing or
  removing that choice applies to every run that hasn't used it yet. The
  project's members see the connections' names; project admins also see
  each one's account and state. A rename, a choice and a removed
  choice are audit events (`connection-renamed`, `connection-choice-set`,
  `connection-choice-removed`), kept on legal hold, and
  `kindgi exports create` writes each project's choices
  (`connection-choices.jsonl`)
  ([Choose a connection](../../guides/connections/choose-a-connection/)).

- **A call uses the company connection it's meant to, or none.** A call
  that needs the company's connection of an app uses the mailbox the run's
  mail came to, else the agent's or the flow's choice, else the project's
  only company connection of the app. It never falls back to another: a
  mailbox's or a choice's connection that can't serve the call fails it
  with `connection-missing`, naming the connection and why. With several
  and no choice, the run fails with `connection-not-chosen`, and its
  failure names the ones to choose from: "This project has 2 company
  Google connections (sales, support), and agent acme.mail-helper has no
  choice of one."

- **A mail trigger for each of the company's mailboxes.** A trigger on the
  company's mailbox names the connection it reads with:
  `config.mailbox.connectionId`, `--connection=<connection>` on
  `kindgi mail-triggers create` and `update` (with `--as=company`), the
  Connection picker when you make a trigger in the console, and Point at
  another on its Mailbox card. Make one trigger for each mailbox: a run's
  reply leaves from the mailbox its mail came to. With several company
  connections of the app, a trigger made without one is refused
  (`409 connection-not-chosen`, listing them), and nothing is made.
  Pointing a trigger at another connection is a change of mailbox: it
  takes a project admin, it reads the inbox unless a folder is named, and
  its tools allowed unattended, if it has any, are named again.

- **An approval names the connection its call runs on,** the company's
  included: an approval of a call on the company's connection carries it
  as its `connection`, with its `name`, and the console shows the name
  with the account under it. A call's connection is decided before it
  waits for its yes, and asked for again right before the tool runs. When
  the two differ, the call doesn't run, and the model reads why as its
  result (`connection-changed`). So an approved call runs only on the
  connection it was approved against, a person's connection too
  ([An approval's fields](../../guides/approvals/approvals-reference/#an-approvals-fields)).

- **A run's journal says how each call's connection was picked.** Each
  call an agent makes on a connection already has a record in the run's
  journal of the connection it used, and each attempt of a flow's tool
  step now has one too. The record now also says how that
  connection was picked (`pick.by`: by the run's mailbox, the account the
  call named from its tool's set, a choice, the company's only one, or the
  person's main or only one), whose it was (`as`), how many a set held
  (`setSize`), and through which registration. These new fields name
  registrations only, never a person's connection names or addresses. The
  console words the record below each tool call that ran, in an agent's
  turn or a flow's tool step, on the run's page
  ([What a run records](../../guides/connections/reference/#what-a-run-records)).

- **A person can connect several accounts of an app, and one is their
  main.** A person keeps a connection per account too, such as a work
  account and a home account at Google, each with its own name.
  Connecting an account they already have reconnects that connection
  when the grant keeps every permission it holds, as the company's does.
  Their first connection is the one their agents use. When they connect
  a second account (for a second Google account, the console's connect
  dialog reads **Connect another Google account**), the first becomes
  their **main**, and their agents go on using it.
  `kindgi connections update <connection> --main`, **Make main** in the
  console, or `PATCH /v1/connections/{connectionId}` with
  `{ "main": true }` makes another one main, and only the person whose
  connection it is can. `main` is on the connection and on the person's
  candidates, `kindgi connections list` marks it `(main)`, a connect's
  finish says what became of it (`main`: `set`, `kept` or `missing`), and
  the CLI's connect says which one their agents use. Making one main is
  an audit event, `connection-main-set`. With several and none main, such
  as after they disconnect their main, a call that needs their connection
  fails the run with `connection-not-chosen`, which counts them and names
  none, and the run's page links them to **Make one your main**
  ([A person's accounts](../../guides/connections/choose-a-connection/#a-persons-accounts)).

- **Choose a connection for one tool, or for your own runs.** A choice can
  be one tool's own, ahead of its agent's or flow's: `--tool=<tool-id>`
  on `kindgi connection-choices set`, with `--need=<name>` for a tool that
  uses the app twice (`toolId` and `need` over HTTP). A person makes their
  own choices, of their own connections, for their own runs: `--mine`
  (`person`). `GET /v1/connection-choices/needs` lists what a choice can be
  for, and `GET /v1/connections/{connectionId}/choices` the live choices
  that name a connection (`connectionChoices.needs` and
  `connections.choices` in the clients). `GET /v1/connection-choices`
  takes `toolId` and `owner=me`, and its candidates take `owner=me`.
  `kindgi connection-choices list` takes `--tool` and `--mine`, with
  TOOL, NEED and CONNECTIONS columns. A choice its agent or flow would
  never read is refused (`400 bad-input`): the company's where the version
  it resolves to now uses the app, or the tool's need, only as each
  person's own connection, and a person's own where it's only the
  company's. One that doesn't use the app yet still takes a choice, and a
  refused one can be made again once the version moves to one that reads
  it
  ([Choose one for a tool](../../guides/connections/choose-a-connection/#choose-one-for-a-tool),
  [Your own choices](../../guides/connections/choose-a-connection/#your-own-choices)).

- **Read several accounts with one tool.** A tool that only reads can be
  given a set of 2 to 10 named connections, one of them its default:
  `kindgi connection-choices set <connection>... --tool=<tool-id> --default=<connection>`,
  `connectionIds` over HTTP, or **Choose several** on the agent's or the
  flow's **Connections** page. The model then sees an `accounts` input on
  the tool, with the set's names, and each call names the account it
  reads, or reads the default. The tool itself never sees `accounts`. A
  tool that changes things, declares `sensitive-data-egress`, or has an
  `accounts` input of its own keeps one connection. A name outside the
  set, or any name once the tool's version no longer takes a set, fails
  the call with `connection-missing`, without repeating the name
  ([Read several accounts with one tool](../../guides/connections/choose-a-connection/#read-several-accounts-with-one-tool)).

- **A trigger on a person's mailbox stores the connection it reads
  with.** `--connection` with `--as=person` names one of the owner's own
  connections of the app (`config.mailbox.connectionId`). Without it, the
  trigger stores their main, else their only one, and with several and
  none main it's refused (`409 connection-not-chosen`), counting them.
  Making another connection main never moves it, and a take-over drops it
  ([Which mailbox a trigger reads](../../guides/runs/start-runs-from-new-mail/#which-mailbox-a-trigger-reads)).

- **List an account's calendars, and read several in one call.** The new
  tools `googleCalendarCalendarsList` and `outlookCalendarCalendarsList`
  (`@kindgi/connections/google/tools` and
  `@kindgi/connections/microsoft/tools`), each for a person or the
  company, list the calendars of the connected account. Each has its
  `id`, `name`, `main`,
  `access` (`owner`, `write`, `read` or `free-busy`) and, when someone
  else owns it, its `owner`, with the main calendar first, then by name.
  From version 1.1.0, the events list and the free/busy tools take an
  optional `calendarIds`, 1 to 10 ids from that list, and read those
  calendars in one call: the events come back in start order, the
  earliest `top` of them across the calendars, each with its
  `calendarId`, and the busy times are joined. Without `calendarIds` they
  read the main calendar, and answer exactly as before. Creating and
  changing events stays on the main calendar. On
  Google, the list tool needs a new permission,
  `calendar.calendarlist.readonly` ("See the list of your calendars"), and
  the events list still reads only calendars the account owns. Outlook
  needs no new consent, and its free/busy reads at most 1000 events
  across the calendars, failing past that
  ([Several calendars](../../guides/connections/calendar/#several-calendars)).

## Fixed

- **Java SDK: an app's own Jackson (2.15 and later, or 3) now keeps a
  newer runtime's variant of a union of objects, and an open record's
  other properties.** Before, Jackson 2.15 and 2.17 dropped them without a
  sign and 2.18 failed the read, and on every Jackson, the client's too, a
  property named `properties` or `additionalProperties` was lost or broke
  the read.

- **A HEAD request is checked as its GET.** Some routes let a HEAD
  through without the check its GET makes, so a caller without the right
  read the GET's status and headers; others asked a HEAD for more than
  its GET. Now every route asks a HEAD for the same right as its GET:
  without it both are `403`, and with it the HEAD answers as the GET.

- **Every program the CLI starts is the one on `PATH`, never a copy in
  the folder it runs in.** 0.4.0 did so for git and `kindgi dev`'s
  sandbox helpers. Now docker, the package manager, a cloud's CLI for a
  token, the pack's Python, JDK, Maven and sbt, and the other programs it
  starts are found in `PATH`'s absolute entries and run by that path. A
  command set as a path (`dev.python`, `JAVA_HOME`, `EDITOR`) runs as
  given.

- **A deploy of an image that's deployed already says so, and says its
  pack service's state.** Its banner reads
  `200 OK (this image was deployed before)`, no longer an idempotent
  replay. When the deployment's pack service was asked for, as when you
  deploy a pack again after the upgrade from the one pack service, the
  deploy says whether it's asked for, ready or taken down, as
  `kindgi deployments get` does.

- **At start, the line that lists the deployments with no routes says
  how to deploy them again:** the same image, each with a new idempotency
  key (`kindgi deploy --idempotency-key <new value>`), so it isn't
  answered as its earlier deploy was.

- **When the app allows less than a connect asked for and the connection
  is stored anyway, the console says it was connected.** The page you
  come back to from the app said **Not connected** and that nothing was
  connected. It now says **Connected, with less than asked**
  (**Reconnected, with less than asked** when the connect names the
  connection it reconnects), what the app allowed and what it didn't, and
  that a run that needs what's missing asks again.

- **A connection app that refuses its client id or secret now says so.**
  When an app refused its client id or secret, Kindgi said the app's
  token endpoint answered with `invalid_client`. On a sign-in at Google,
  LinkedIn or any app whose `account.issuers` lists more than one issuer,
  it said instead that the token endpoint couldn't be reached or answered
  badly, so a wrong client secret looked like a network failure, and so
  did a sign-in code that was used or had expired. Now a sign-in or a
  renewal says the app didn't accept the client id or secret registered
  for it, and at those apps a used or expired code says so too. The page
  you come back to from the app, **The app didn't give a token**, says
  nothing was connected, then what the app refused and what to do next:
  for a refused client id or secret, check both in the registration,
  then start again. Before, it said the sign-in's code was refused,
  whatever the app refused. A sign-in's token request or a renewal that
  the app fails is logged with the app's error code and what failed, by
  class name and code only, never a message, a body or a token.

- **The links at the foot of each console page are underlined.** Your
  own links there (`KINDGI_CONSOLE_LINKS`) showed their underline only
  on hover, and so did a project's name on the **Environments** page.
  Both are underlined now, like the console's other links, and each link
  at the foot ends with the arrow of a link that opens a new tab. The
  sign-in page's links were underlined already.

- **Erasing a person's run clears why it failed from its webhook
  deliveries.** A `run.finished` delivery says why the run failed in
  `failureMessage`, and again in `failure`, with any cause. Erasing the
  run removed `failureMessage`, which the event requires, and left
  `failure`: the delivery kept the person's words, and one not yet sent
  had a body a receiver could fail to read. Now `failureMessage` is
  `null`, as the erased run reads back, and `failure` is gone. A run
  erased before you upgrade can still have the person's words in its
  webhook deliveries, in why the run failed. The server deletes each
  delivery it has finished sending 30 days after it was created.

## Changed

- **Connecting another account of an app makes a second connection,**
  the company's or a person's. Each kept one connection per registration
  and environment, so connecting another account was refused with
  `connection-account-mismatch`, and changing accounts meant disconnecting
  first. A person's second connection makes their first their main.

- **To add permissions to a connection, reconnect that one.** A connect
  that names no connection asks only for the permissions it lists, and no
  longer reconnects the one you have by itself. Connecting an account you
  already have reconnects its connection only when the grant keeps every
  permission the connection holds. Otherwise the connection stays as it
  was: the connect answers connected if the connection is working and
  already holds what it asked for, and is declined with what's `missing`
  if not. Name the connection to reconnect it, and the connect asks for
  what it holds as well as what it lists: `--reconnect=<connection>` on
  `kindgi connections connect`, or `reconnects` on `POST /v1/connections`.
  The console's **Reconnect** shows on a connection that needs
  reconnecting, and asks again for what it holds.

- **With a second company connection of an app, agents, flows and mail
  triggers need to know which one.** While the company has one, nothing
  changes. Once it has two, a call of an agent or a flow with no choice
  fails its run with `connection-not-chosen`, and a company mail trigger
  that stores no connection doesn't read, and shows
  `connection-not-chosen` with the names, until a project admin points it
  at one. A trigger that stores no connection, such as one made before
  0.5.0, is pointed at the project's only company connection of the app
  when it next reads. A person's trigger that stores no connection is
  pointed at their main connection of the app, else their only one; with
  several and none their main, it doesn't read, and shows
  `connection-not-chosen` with how many there are, until they make one
  their main.

- **Names refuse more hidden characters.** A connection's name, a site's
  display name and a console link's label (`KINDGI_CONSOLE_LINKS`) follow
  one rule, which now also refuses a lone surrogate, the characters that
  render as nothing (such as the Hangul fillers and the combining
  grapheme joiner), and a variation selector anywhere but in an emoji. An
  emoji with its variation selector still passes.

- **An approval's `connection` names no account when it's a person's
  own, and `as` says whose,** `company` or `person`. It was always the
  person's, with their `account`, so code that reads `account` now finds
  it optional in the clients' types. The approval shows "this person's
  Google account" for a Google connection. An approval made before the
  upgrade keeps its `account`, and has no `as`
  ([An approval's fields](../../guides/approvals/approvals-reference/#an-approvals-fields)).

- **`kindgi connections list` shows each connection's name first,** in a
  LABEL column. Its JSON is the server's, which now has each connection's
  `label` when it has one.

- **A trigger on a person's mailbox shows the address it reads to its
  owner and tenant admins only.** Anyone else reads the trigger without
  its `account`, and `kindgi mail-triggers list --table` shows "this
  person's Google account" in its place.

- **A project or a team moved into or out of an org, or one whose org was
  deleted, no longer stays open to the old org's admins.** A move or an
  org's delete changed only the row, so the old org's admins kept their
  way in, and the new org's admins had none. Its authorization parents
  now change with it. What earlier moves and deletes left behind, the
  upgrade sets right (Upgrade steps).

- **Moving a project or a team into or out of an org takes a tenant
  admin.** A `PATCH` of a project or a team whose body names `orgId`, even
  its current org or `null`, needs a tenant admin, as making one in an
  org does. Anyone else gets `403 permission-denied`, and nothing in the
  body changes. Before, the project's or the team's own admins, a
  project's owner among them, could move it. A body without `orgId` works
  as before.

- **The console, the CLI, the server's messages and the docs call the
  place a workspace.** What you type or match on keeps `tenant`:
  `--tenant`, `kindgi tenant`, `tenantId`, `KINDGI_TENANT_*`, the scope
  value `tenant`, the error codes and the paths, and so do the tenant
  admin role and the system routes' messages, for the operator of a
  runtime that serves several workspaces. Match on a message's code, not
  its text. A new runtime names its first workspace Default workspace;
  one made before keeps its name.

- **`kindgi build` refuses a block file or template named in another
  case than the disk has.** On macOS and Windows such a pack ran under
  `kindgi dev`, then a build on Linux, as in CI, didn't find the file.
  The build names each one as the pack names it and as the disk spells
  it. `kindgi dev` says the same once, and still loads the block.

- **`--clear-label` takes a schedule's, a webhook trigger's or a mail
  trigger's label off.** On `update`, an empty or blank `--label=` is now
  a usage error that names `--clear-label`, and a label is saved trimmed.

## Known issues

- **The run's page can be wrong about which calls ran on a connection.**
  In an agent's turn that's still running, or that failed, a call that
  the check right before its tool stopped, such as with
  `connection-changed`, still shows the connection it would have run on.
  And in a turn that completed, a call that ran, was refused by the app
  and then couldn't get its connection again shows none.

- **A command that names a renamed project's old slug can act on another
  project.** The CLI looks a slug up each time it runs, wherever you name
  a project by its slug: `kindgi deploy --project`, say, or an
  environment's `project` in your pack config
  (`environments.<name>.project`), which `kindgi deploy`,
  `kindgi promote`, `kindgi environments set`, and `kindgi secrets` and
  `kindgi env` with `--env` read. After a rename, the old slug names no
  project, so such a command is refused, unless another project has that
  slug: one in another org may have it already, and any project can take
  it later. Then the command acts on that project with no error: a deploy
  goes into it, and a secret or value is set on it, and
  `kindgi environments set` puts it in the order. After you rename a
  project, change the old slug to the new one in every script, pack
  config and `--project` flag before you run one of those commands again,
  or name the project by its id, which a rename doesn't change.
  [Organize work by org and project](../../guides/projects/organize-by-org-and-project/)
  has the details.

- **Your app's own Jackson can't read some of the Java SDK's answers
  yet.** With your app's own `ObjectMapper` (Jackson 2 or 3), an agent
  doesn't read, and neither does a list of agents, a test run that has a
  comparison (alone or in a list), or a secret rotation's answer. The
  client's own calls are unaffected. Read them with
  `KindgiJson.read(json, Type.class)` from `kindgi-client`, such as
  `KindgiJson.read(json, Agent.class)`.

## Upgrade steps

- **From 0.3.x, follow 0.4.0's Upgrade steps first**
  ([Kindgi 0.4.0](../0.4.0/#upgrade-steps)).

- **Before you upgrade, check your console links' labels.** A runtime
  whose `KINDGI_CONSOLE_LINKS` holds a label with one of the newly refused
  characters doesn't start, and says which link. Type the label again
  without it
  ([Your own links in the console](../../deploy/self-hosted/sign-in/#your-own-links-in-the-console)).

- **The upgrade's two migrations let the company and each person keep a
  connection per account.** They add three tables (`connection_choices`,
  `connection_choice_uses` and `connection_choice_members`) and new
  columns that are empty, and fill nothing in: your connections keep
  working, with no name, and no agent or flow has a choice. Name them
  when you like. The first start runs the migrations, as it runs any
  other migration. They lock `connections` and `connection_requests`,
  and each keeps `connections` locked while it reads every row, to build
  its new indexes or check a new rule: meanwhile anything that reads or
  saves a connection waits, such as a call that runs on one, on a server
  of the earlier version still running too. With many connections
  (`SELECT count(*) FROM connections`), upgrade at a quiet time. A long
  transaction holding one of those tables makes the start stop after
  about a minute, naming the session that holds it. End that session or
  let it finish, then start again. On Cloud Run or Azure Container Apps,
  the old revision serves meanwhile; on a single server, such as the
  Docker setup, the runtime is down until the new start succeeds.

- **Before you connect a second company account of an app, choose for
  the agents and flows that use it.** For each agent and flow whose tools
  use the company's connection of that app, choose the connection it uses
  now, and check that each company mail trigger of the app shows its
  Connection, which it stores when it first reads after the upgrade.
  Otherwise their runs stop with `connection-not-chosen` once the second
  account is connected. A call that isn't an agent's or a flow's can't
  have a choice, so it needs a project with one company connection of
  the app.

- **A person's account label is no longer recorded.** When a call runs on
  a person's own connection, the run's journal keeps the account's id
  without its label, and an approval shows "this person's Google account"
  for a Google connection. A pick from several of their accounts says how
  many there were, without their names. A company connection's record
  keeps its label. Runs and
  approvals recorded before 0.5.0 keep the label they were recorded with,
  such as an email address. What a call took and returned, and what the
  model wrote, stay as the model and the tool made them, so an account the
  call named can still show there.

- **To list Google calendars,** add the
  `https://www.googleapis.com/auth/calendar.calendarlist.readonly` scope
  to your Google Cloud project's consent screen. A connection made before
  grants it once, when it's reconnected (`--reconnect=<connection>`, or
  **Reconnect** in the console once it needs reconnecting); the
  permissions it had stay.

- **In Java and Scala, code that builds a `ToolConnection` adds its
  `name`.** The record's constructor is now
  `new ToolConnection(connectionId, app, appName, accessToken, account, name, expiresAt)`,
  and none without `name` is kept, so a unit test that builds one adds
  the argument; `null` is fine. In Python, `name` is the last field and
  defaults to `None`, so nothing changes there.

- **On Azure Container Apps, the way back's plan shows the server's
  secrets removed and added again.** The plan in the way back that
  `upgrade.sh` prints changes the images and the server's `database-url`
  reference only, but Terraform plans the server's secrets as one set, so
  it shows them all removed and added again, their contents hidden. The
  printed steps and the module's README now say so.

- **On a runtime serving many tenants, run
  `kindgi-runtime tenants repair --all` after the upgrade.** It sets right
  the authorization parents that earlier moves of projects and teams, and
  deletes of orgs, left behind, and each tenant's line counts the changes
  it queued, such as `1 parent change queued for the server to apply`
  ([After each upgrade: tenants repair](../../deploy/self-hosted/serve-many-tenants/#after-each-upgrade-tenants-repair)).
  A runtime serving one tenant does it when it starts.
