Released November 11, 2026. For the docs of this version, see
[docs.kindgi.com/v0.6.0](https://docs.kindgi.com/v0.6.0/).

## New

- **Use Kindgi from Claude.** People in your workspace can add Kindgi to
  claude.ai as a custom connector, sign in as themselves, and ask Claude to
  run the agents and flows your builders offer in chat. Kindgi's consent page
  asks for two permissions: "Follow runs you can see in Kindgi, and see their
  results" and "Run the agents and flows you're allowed to run, and follow
  their runs". A run that isn't done within about 25 seconds comes back with
  its link and Kindgi's own view of the run, right in the chat. The view
  follows the run to its end, and Claude waits for it too. When a run waits
  for someone, Claude says what for and gives its link: approving or
  declining stays in the console. To end it, open **My access**, then
  **Chat apps**, and choose **Disconnect**.
  [Use Kindgi from Claude](../../guides/chat/) has the steps.

- **Turn chat apps on for your runtime.** Set `KINDGI_MCP_SERVER=on`, and
  the runtime serves Kindgi to people's chat apps at `/mcp`, the address
  they add. It needs sign-in and `KINDGI_PUBLIC_URL` with no path, or the
  runtime doesn't start, and says why. It's off by default. Behind a proxy or a load balancer, set
  `KINDGI_TRUSTED_PROXIES` first: unset, every request counts as coming from
  your proxy, so people's browsers and Claude's servers all share one count
  for each limit the runtime keeps per address. Behind a firewall, open
  `/mcp` and the sign-in paths the page lists.
  [Let people use Kindgi from Claude](../../deploy/self-hosted/chat-apps/).

- **Offer an agent or a flow in chat.** Only the agents and flows their
  builder offers show up in a chat, with the new optional `mcp` field:
  `mcp: { expose: true }`, or `Agent(mcp={"expose": True})` and
  `Flow(mcp={"expose": True})` in Python. Each one offered is a tool for the
  people who can see it, an agent's named by its id and a flow's by `flow.`
  and its id. So with `expose: true`, the id must be a tool's name (letters,
  digits, `_`, `-` and `.`, at most 128 characters, or 123 for a flow), and
  an agent's can't start with `kindgi.` or `flow.`. `readOnly` and
  `destructive` become the tool's hints. `defineAgent` and `loadFlow` refuse
  one that breaks these rules (`invalid-mcp-exposure`), and so do the Python
  classes when the module loads. Without `mcp`, nothing changes. The schemas
  that take it: `agent.schema.json` 1.8.0, `flow.schema.json` 1.10.0 and
  `pack-index.schema.json` 1.9.0.

- **What a chat app can do.** It acts as the person, through their own
  grants, narrowed to three scopes: `kindgi:read`, `kindgi:run` and
  `kindgi:schedule`. None of them allows writing, publishing, admin or
  deleting, so from a chat even an editor acts only on their own runs and
  schedules. A run it starts can't act as a tenant admin either, even when
  the person is one: an agent there that tries to remember a fact for
  everyone in the organization is refused, and the model is told that a
  tenant admin can, in a run they start from the console. A chat app never
  gets a run's access token, an agent's instructions, an approval's
  context or a connect link, and a run's answer reaches it marked as agent
  output, to treat as data. Each run it starts carries an idempotency key,
  so a chat app's retry doesn't start a second run. It names no project:
  an agent's run lands in the conversation's project when the call
  continues one, else in the agent's own, and a flow's in the flow's own.
  Starting it there takes only the right to run it, so someone who may
  only run a project starts runs from a chat too. On hosted Kindgi, a chat
  app's reads of a run it waits for count toward your API requests
  ([Limits](../../hosted/limits/#api-requests)).

- **A runner role.** A project role between editor and viewer: a `runner`
  starts runs of the project's agents and flows, uses their tools inside
  those runs, stops their own runs and keeps their own schedules, and
  changes nothing else in the project. Give it to a person, a service
  account or a team wherever you give a project role: it's **Runner** in
  the console's role lists. In the CLI, a service account gets it with
  `kindgi service-accounts create --project=<id>:runner` or
  `kindgi service-accounts grant <id> --project=<id> --role=runner`. A
  runner cancels only the runs that act for them, and closes only the
  conversations they opened.
  [Run with authorization](../../deploy/authorization/) has what each role
  may do.

- **Everyone in a workspace can run a project.** A project's new setting,
  `everyoneCanRun` in the API, lets every person in its workspace run its
  agents and flows without a role of their own. Service accounts aren't
  included. They see only what running takes: the project, its agents and
  flows with their versions, and their own runs, conversations and personal
  schedules. Anyone else's stay hidden. A project admin turns it on or off
  on the project's **Members** page, where it reads "Everyone in
  <workspace> · Can run", or with `PATCH /v1/projects/{projectId}`. A
  new project has it on: the console's New project dialog has "Everyone
  in <workspace> can run it" ticked, and the API sets it unless you send
  `"everyoneCanRun": false`, to choose people one by one. A new
  workspace's default project has it on too. Existing projects keep it
  off. A person
  sees the projects they can run this way on **My access**, and
  `GET /v1/identity/me/permissions` lists them in
  `everyoneCanRunProjects`.

- **A runner's own runs and files.** Someone who may only run a project, a
  runner or anyone where everyone in the workspace can run it, sees the
  runs that act for them in `GET /v1/runs`, with the runs of the projects
  they may read, a full page at a time, even where many newer runs of
  others lie between theirs. `GET /v1/runs?actsFor=me` lists only the
  runs that act for you (`runs.list` takes `actsFor: 'me'`,
  `acts_for="me"` in Python). In such a project they also reach their
  own files: they upload a file as an input for a run they start and
  download it again, download the files their own runs stored, and list
  a run of their own's files.
  Anyone else's files stay hidden, and deleting a file takes `write`, even
  one of their own. Across projects, the projects someone may only run
  come from the authorization store's list, which answers at most 1000 by
  default: someone who reads or runs more may miss the runs of some.

- **Calendar tools that read calendars others share.**
  `googleCalendarSharedEventsList` and `outlookCalendarSharedEventsList`
  list a window's events as the events lists do, also on a calendar someone
  else owns that the account has, such as a colleague's or a family
  calendar. They act as the person, or as the company with
  `as: 'company'`. They ask for a wider permission than the events lists, so
  only a pack that includes one asks for it: Google's
  `calendar.events.readonly` and Microsoft's `Calendars.Read.Shared`. Add
  it to your Google OAuth client's Data access, or to your Microsoft app's
  API permissions. A connection made before lacks it until its person
  allows it.
  [Calendars](../../guides/connections/calendar/).

- **An approval says which connection its call acts with.** An approval,
  and a run's `waitingFor`, carry the connection's id: `connectionId`
  (`connection_id` in Python). Whoever may read the connection, its person
  or a tenant admin, looks its account up with
  `GET /v1/connections/{connectionId}`. So with several accounts of one
  app, a person can tell which of theirs a call uses. For anyone else, the
  approval reads as before. Approvals from before 0.6.0 have no
  `connectionId`. In the console, whoever may read that connection sees
  its account on the approval and on the run's page, such as
  `alex@acme.com (Google)`, or `alex@acme.com (Google, disconnected)`
  once it's disconnected, and to its person the approval says "your
  Google account". Anyone else still sees "this person's Google account".

- **Ask a connection's app for more.** In the console, a connection's page
  has **Ask Google for more** (or its own app's name) for whoever may
  reconnect it: the person whose account it is, or a tenant admin for the
  company's. Its permissions page lists what the app offers, with what the
  connection may do now ticked and locked, and asks the app only for the
  ones you tick: asking for more never takes one away. On an agent's and a
  flow's Connections pages, a tool's row says what its connection can't
  do yet, such as "Sales desk can't yet: Send email as you", to whoever
  may read that connection, with the same link
  for whoever may reconnect it. A sign-in that allows only part of what was
  asked keeps what it allowed, and one that allows less than the connection
  already holds leaves it as it was. `GET /v1/connection-choices/needs`
  answers each need's `permissions`. A `kindgi connections connect`
  without `--reconnect` that's declined at the app now says
  `Declined at <app> (not <permissions>): nothing from this sign-in was kept.`,
  since a connection the owner already has of that account stays as it was.
  [Choose a connection](../../guides/connections/choose-a-connection/).

- **A run's record says whether a call's tool ran, and whose connection a
  stopped call needed.** The run's journal gets a `ran` record for a call
  whose tool was handed its connections, right before its first run on
  them, and the gate's `ready` record says it records those
  (`recordsRan`). So a call with no `ran` record didn't run, even in a turn
  that's still running or that failed. A refused connection record gains
  `as`: `company`, or `person`, the run's person. Records from before have
  neither. The run's page reads `as`: a call stopped with
  `connection-not-chosen` says whether it needed the company's connection
  or the person's, and links to where to choose one.

- **Short links to a run, an agent, a flow and a schedule.** On your
  runtime's address, `/console/runs/<run-id>`, `/console/agents/<agent-id>`,
  `/console/flows/<flow-id>` and `/console/schedules/<schedule-id>` open
  the item's own page, after sign-in if it's needed. A person who may not
  open it reads "You can't open this run" (or agent, flow or schedule)
  and "Ask an admin of its project for access."

- **The Cloud Run module can put the server behind your own load
  balancer.** Set `server_ingress = "INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER"`,
  and the server sits behind your own external Application Load Balancer,
  with your domain and your Cloud Armor policy. Its run.app URL then takes
  only the load balancer's calls and internal ones. It needs
  `network_mode = "direct"` and `public_url`, the load balancer's address.
  The default, `INGRESS_TRAFFIC_ALL`, keeps things as they are.
  [Deploy on Google Cloud Run](../../deploy/self-hosted/cloud-run/).

- **For your own server code.** `createApp` takes an optional `mcpServer`,
  which mounts `/mcp` outside `/v1` with its own token check
  (`mcpServer.resolveToken`). `MCP_SCOPES` and `McpScope` are exported.
  `bearerAuthMiddleware`, `BearerAuthMiddlewareOptions` and
  `tokenSignInKey` are exported too, so a route of your own can admit a
  caller exactly as `/v1` does.

## Fixed

- **A command that names a renamed project's old slug no longer acts on
  another project.** A project renamed from 0.6.0 on keeps its old slugs: no other
  project in the workspace can take them, in any org, and a project that
  tries gets `409 slug-conflict` with `details.heldAs: 'old-slug'`. A
  command that names a project by an old slug is refused, and the refusal
  names the new slug and where to change it: `kindgi deploy --project`,
  `kindgi deployments list --project`,
  `kindgi suggested-changes pull --project`, `kindgi promote`,
  `kindgi environments set`, and `kindgi secrets` and `kindgi env` with
  `--env`. A slug one project has and another had before a rename names two
  projects, so it's refused too: pass the id. A project can take its own old
  slug back, and deleting a project frees its slugs. A project's old slugs
  are in its `formerSlugs` (`former_slugs` in Python).
  [Organize work by org and project](../../guides/projects/organize-by-org-and-project/).

- **Claude's thinking goes back with the tool results.** When Claude
  thought before it called a tool, the next step lost that thinking: the
  adapter didn't send it back with the tool's result, as the Messages API
  wants. It now does, unchanged and where it was, on the next call to the
  same model. The thinking is kept with the conversation and the turn's run,
  encoded but not encrypted, so whoever can read them can read it. And when
  the output cap is reached before any answer text, the answer now carries a
  `thinking-used-max-tokens` warning that names the cap and says to raise
  `maxOutputTokens`.

- **A flow with a fan-out in a loop body is refused when it's loaded.** A
  loop body never ran a fan-out: the run failed there, with no branch run.
  `loadFlow` now refuses such a flow with `LoopBodyFanoutError`
  (`loop-body-fanout`), naming the fan-out and its loop, at any depth. A
  subgraph node in a loop body can still run a flow that has a fan-out. A
  run of such a flow stored before fails at the loop, with a message that
  names the fan-out.

- **A site can't enroll a key it retired.** `POST /v1/auth/sites/enroll`
  answers `409 site-enrollment-key-retired` for a key the site retired,
  whether an admin's `kindgi sites revoke-key` retired it or a newer key's
  enroll did. It refuses one too that another of the workspace's sites at
  the same address retired and no longer uses. The refusal comes only once the code checks out, and doesn't use
  the code up: the same code works with a new key until it expires. The
  WordPress plugin says where to set a new key when Kindgi refuses one.
  [Let a store's staff ask and approve in WordPress](../../sites/wordpress/).

- **Reading your own access no longer fills the access audit.** The
  console reads whoami's `tenantAdmin`, `GET /v1/identity/me/permissions`
  and an expert queue item's `can` again and again, and each read left a
  row in the workspace's access audit. They're decided as before, and
  recorded nowhere. Every decision on what a request may do or read is
  recorded as before.

- **`kindgi dev` takes a database URL with a list of hosts.** A URL such
  as `postgres://<user>:<password>@h1:5432,h2:5432/<database>` stopped
  `kindgi dev` with `Invalid URL`, and in a list without ports a local host
  was missed. It now reaches each local host in the list from the runtime's
  container, on macOS, on Windows and under Docker Desktop. And a changed
  password no longer makes the providers `kindgi dev` registered read as
  registered by someone else.

- **A run waits when it can't read what its version needs, instead of
  failing.** When a run is resumed, such as after an approval, it reads its
  tools, data blocks, model providers and guardrails, and its project, as
  they were in its version. If such a read failed, the resume failed, and
  so did a flow's step. Now the run keeps waiting, and the runtime resumes
  it again later: a flow's step is left for the run's next resume.

- **A file Kindgi converts is no longer refused as too large because its
  worker started slowly.** The time a conversion may take, such as an
  Office document's or an image's, counted from its worker's start, so on
  a busy server a slow start could get a file refused as too large. It
  now counts from when the worker is ready. A worker that isn't ready
  within 30 seconds answers that it's unavailable for now, so the file
  can be tried again.

- **The run's page is no longer wrong about which calls ran on a
  connection.** In an agent's turn that's still running, or that failed, a
  call that the check right before its tool stopped, such as with
  `connection-changed`, no longer shows the connection it would have run
  on. And in a turn that completed, a call that ran, was refused by the app
  and then couldn't get its connection again now shows the one it ran on.
  The page reads these two cases in a turn recorded before the upgrade as
  before, so it can still be wrong there. A call whose input failed its
  tool's check shows none, as its tool didn't start, unless the turn
  failed on it and more than one call of that tool in the model's last
  reply got its connections. A flow's tool step shows the connections its
  tool was handed on the step's current attempt.

- **A chat app's `subscriptions/listen` on `/mcp` ends at once.** `/mcp`
  said its tool and resource lists could change, though Kindgi builds them
  afresh for each request and never sends a notice that they did. So a
  client on the 2026-07-28 protocol that listened for changes was held
  open, with keep-alives, for notices that never came. `/mcp` now says its
  lists never change (`listChanged: false`), and a listen is answered and
  ended straight away. Listing tools, calling them and reading the run
  view are unchanged.

- **Without an authorization store, a key limited to a project can't write
  above it.** On a runtime without an authorization store, a key or a
  session limited to a project could write to the workspace (its settings
  and config; its workspace- or org-wide secrets, env values, MCP
  endpoints, corrector groups and memory facts; its workspace-wide agents,
  tools, flows, guardrails and deployments; memory erasures, retention
  sweeps, release gates and the reviewer roster), to an org or a team, or
  make a new project, move one into an org, or put one in or out of
  production. Each is now refused with
  `403 key-project-mismatch` (`details.keyProjectId`), as a runtime with a
  store already refused it. So is a body that names another project as
  `scopeKind: 'project'` with `scopeId` (registering an MCP endpoint) or as
  `improve.projectId` (an Improve schedule's target), and setting or
  clearing the workspace's or an org's environment order. Reads are
  unchanged, and so is a write to an existing item by its id, except a
  memory fact's: superseding, deleting or verifying one is held by the
  fact's scope, as writing one is. A workspace- or org-wide pin or unpin is
  refused by its scope alone, so for an item only the key's own project
  serves it's stricter than a store. With a store, the environment order's
  refusal for such a key now answers `key-project-mismatch`, not
  `permission-denied`. Keys and sessions not limited to a project are
  unchanged.

- **A key with limits manages only the keys within them.** A key or a
  session limited to a project, or with the `member` role, could list,
  read and revoke every key of its owner, wider ones too. Now it sees only
  the keys no wider than itself: those limited to the same project and,
  for the `member` role, the `member` keys. Every key it can make is among
  them. `GET /v1/tokens` leaves the others out. Reading or revoking one of
  them answers `403`, naming only the caller's own limit:
  `key-project-mismatch` for a key not limited to the caller's project,
  `permission-denied` for an `admin` key and a `member` caller. Nothing
  about that key is in the answer, and someone else's key still reads as
  missing (`404`). A tenant admin, and a key or session without limits,
  see what they did before.
  [People, API keys and service accounts](../../deploy/people-and-keys/#api-keys).

- **The email about a removed second factor names a tenant admin.** When
  someone else removes a person's second factor and the deployment sends
  mail, the email names who removed it. If whoever removed it has no email
  address, it says "A tenant admin", where it said "A workspace admin",
  and when a service account's key removed it, "A tenant admin's API key",
  where it said "A workspace admin's API key". Tenant admin is the role's
  name in the console.

## Changed

- **A correction's text of only spaces counts as not given.** In
  `POST /v1/corrections` and a test case you add by hand
  (`POST /v1/agents/{agentId}/test-set/cases`), a `shouldSay` or `why` of
  only spaces was stored, and could hide the other text from the answer
  checker. It isn't stored now, as an empty one isn't. So
  `{ "answer": "wrong", "shouldSay": "  " }` is refused with a `400`
  (`answer: "wrong" needs shouldSay or why.`), and a `shouldSay` of only
  spaces without `"answer": "wrong"` is no longer refused, and isn't
  stored. The console's corrections and test set show the other text where
  one was only spaces.

- **A page for a feature your runtime doesn't offer says so, and why.**
  Connections, mail triggers, deployments and project roles each need
  something a runtime can run without, such as its own secrets store or
  an authorization store. Their pages now say "Not available in this
  runtime" and why, and under `kindgi dev`, why it runs without them.

- **`kindgi dev` warns when `--database-url` has a password,** which `ps`
  shows to other users on the machine, and goes on. Keep the URL in
  `.kindgi/secrets.env` as `KINDGI_DATABASE_URL` instead: that's on no
  command line. And `kindgi dev` no longer takes over a providers record
  written by 0.1.3: a provider it registered reads "registered already, not
  from kindgi.config.ts". `kindgi providers unregister <id>`, then a
  restart, makes it the pack's own again.

- **A new tenant's default project gets another slug when
  `first-project` is taken.** When a project without an org has that slug,
  or another project of the tenant had it before it was renamed, the
  default project gets the first free one of `first-project-2`,
  `first-project-3` and so on, and the tenant's line says so. A deploy that
  names no project still goes into the default project.
  [Serve many tenants](../../deploy/self-hosted/serve-many-tenants/).

- **The licensing page names the production plans.** Free, Starter,
  Business and Enterprise, with the flows and agents each covers, its
  support, and the prices on
  [kindgi.com/pricing](https://kindgi.com/pricing). Cancelling a plan ends
  its license, even if the key hasn't expired yet. Your plan's limits are
  terms of your license: the runtime doesn't count them yet.
  [Licensing](../../concepts/licensing/).

- **The docs, the skills and the CLI's README install the CLI of the
  release they describe.** They installed the CLI's 0.2 line, so a reader
  of later docs ran an older CLI than the one the docs describe. Now they
  name the release's own line, or a release candidate's exact build.

- **A rotation's grace period is a whole number of milliseconds from 0 to
  365 days.** `POST /v1/secrets/{name}/rotate` checked only that
  `revokeOldAfterMs` was a number: a negative one was taken and did
  nothing, and one of hundreds of thousands of years made the store fail.
  It now answers `400 bad-input` for a value outside that range: a
  negative number, a fraction, or more than 31536000000 (365 days). So a
  value over 365 days that was taken before is refused now. The message
  names the range. `kindgi secrets rotate --revoke-old-after` refuses
  such a value before it sends anything, in the same words, and exits 2.
  The schema now says what a version's `revokedAt` and a rotation's
  `oldVersionRevokedAt` mean: a time still to come is the old version's
  grace period, and the old version still resolves until then.
  `MAX_REVOKE_OLD_AFTER_MS` is exported from `@kindgi/api`.

- **The packages ask for releases with security fixes.** `@kindgi/api`
  needs hono 4.13.11 or later, `@kindgi/bounds` re2js 2.8.7,
  `@kindgi/cli` esbuild 0.25.12, and `@kindgi/client` zod 4.6.6.
  `kindgi init` adds zod at 4.6.7, the version Kindgi is now tested with:
  exactly `4.6.7` when your app pins exact versions or its package manager
  saves them, otherwise `^4.6.7`.

## Known issues

- **Your app's own Jackson can't read some of the Java SDK's answers
  yet.** With your app's own `ObjectMapper` (Jackson 2 or 3), an agent
  doesn't read, and neither does a list of agents, a test run that has a
  comparison (alone or in a list), or a secret rotation's answer. The
  client's own calls are unaffected. Read them with
  `KindgiJson.read(json, Type.class)` from `kindgi-client`, such as
  `KindgiJson.read(json, Agent.class)`.

## Upgrade steps

- **From 0.4.x, follow 0.5.0's Upgrade steps first**
  ([Kindgi 0.5.0](../0.5.0/#upgrade-steps)).

- **The upgrade's migrations fill nothing in.** They add a record of
  renamed projects' old slugs, the everyone-can-run setting, and the
  tables chat apps' sign-in keeps. So existing projects keep
  everyone-can-run off until a project admin turns it on, and a project
  renamed before the upgrade doesn't hold its old slugs: 0.5.0's Known
  issue still holds for those. Change an old slug to the new one wherever
  you named it, or name the project by its id. The first start after the
  upgrade also builds one new index on the runs table, without locking
  the table; with many runs, that start takes longer.

- **The authorization model gains the runner role and everyone-can-run.**
  A runtime that serves one tenant brings its store to the new model when
  it starts, and logs `tenant <id>: store <store> now has the current
  model (<old> → <new>), digest <digest>`; a store it can't reach then is
  tried again at the next start. A runtime that serves many tenants
  doesn't: run `kindgi-runtime tenants repair --all` right after the
  upgrade, before people use it, and each tenant's line says "its
  authorization model brought to this runtime's"
  ([After each upgrade: tenants repair](../../deploy/self-hosted/serve-many-tenants/#after-each-upgrade-tenants-repair)).
  Until it has run, a tenant's store has the old model: lists of runs
  and new personal schedules fail for anyone who isn't a tenant
  admin, and runner roles are best given after it. A person's or a
  team's runner role given before it takes effect up to an hour later;
  if it still hasn't, remove it and give it again. A service account's
  is refused until it has run, so give it again then.

- **An upgrade that stops on a locked table can be started again.** If the
  new version's migration stops because another database session holds a
  lock on a table it changes, start it again once that session has ended
  (the error names it). Each migration is applied together with its own
  record, so the ones before the stop stay applied, the one it stopped on
  leaves nothing behind, and nothing needs restoring.

- **A remote MCP endpoint that redirects to another origin no longer
  connects.** The runtime now follows a remote MCP endpoint's redirect
  only when it stays within the same origin, so an endpoint whose
  registered URL redirects to another origin fails to connect with
  `mcp-connect-failed`, and the error names the redirect target as not
  followed. Register the URL it redirects to. This takes the MCP SDK's
  fix for advisory GHSA-6prh-2h8m-c8cw: before it, a redirect to another
  origin sent that origin the request's custom headers, and on a 307 or
  308 its body too.
