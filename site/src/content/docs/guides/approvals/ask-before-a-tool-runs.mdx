This guide makes an agent wait for a person before it calls a tool that
changes something, then approves or rejects the call.

An agent turns on approval gates in its `conversationPolicy`. When the model
asks for a gated tool, the run stops before the tool is called and waits for a
reviewer. Approve, and the tool runs. Reject, and it doesn't.

## Before you start

- **A pack** on a runtime such as `kindgi dev`, with Kindgi 0.2's CLI. This
  guide uses the pack `acme-ops`, with a read-only tool, `acme-ops.greet`.
- **A model the agent can route to,** with `tool-use`, as
  [Models](../../models/) shows.

## Gate a tool

`acme-ops.post-update` posts to a public status page. It changes something
outside your app, so it doesn't say `mutating: false`. Ask your coding agent:
"I want a tool that posts an update to our public status page." Kindgi's
skills in your pack tell it how
([How it knows Kindgi](../../../start/coding-agents/)). For reference, the
tool looks like this:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// tools/post-update/index.ts
import { defineTool } from '@kindgi/sdk/define';
import type { ToolId } from '@kindgi/sdk/types';
import { z } from 'zod';

const defined = defineTool({
  id: 'acme-ops.post-update' as ToolId,
  description: 'Posts a message to the public status page.',
  version: '0.1.0',
  input: z.object({ message: z.string().min(1).max(500) }),
  output: z.object({ posted: z.boolean(), postedAt: z.string() }),
  effects: [{ kind: 'external-side-effect', resource: 'external:status-page' }],
  handler: async () => ({ posted: true, postedAt: new Date().toISOString() }),
});

if (defined.kind === 'err') throw new Error(defined.error.message);
export default defined.value;
```

class Posted(BaseModel):
    posted: bool
    posted_at: str = Field(alias="postedAt")

`hitl.tools` turns tool gates on for this agent. Each tool then gets a gate:

- **`always_ask`**: every call waits for a decision.
- **`never_ask`**: calls run without asking.
- **No override:** a tool declared read-only, with `mutating: false`, runs
  without asking. Any other tool asks. So `hitl: { tools: {} }` asks before
  every tool that can change something. Here `acme-ops.greet`, which is
  read-only, never asks.

An agent without `hitl.tools` has no tool gates, unless your tenant has
[approval rules](../approval-rules-for-every-agent/).

### Someone other than whoever asked

**A tool call's approval names who asked:** the person the turn runs for, in
`requestedBy` (`user:<id>`, or `service_account:<id>` for an app's key). It
stays the same when someone else's decision resumes the turn.

**By default, that person may approve it too.** `hitl.separateApprover`
makes the approval need someone else (four eyes):

- **`true`** applies to every gated tool.
- **Per tool,** set `overrides`, keyed by tool id as in `tools`. An optional
  `default` covers the tools you don't name.

```ts
conversationPolicy: {
  hitl: {
    tools: { overrides: { 'acme-ops.post-update': 'always_ask' } },
    separateApprover: { overrides: { 'acme-ops.post-update': true } },
  },
},
```

Every pack language sets it the same way: Python's `conversation_policy`,
and the map Java and Scala pass to `set("conversationPolicy", …)`, take the
same keys, `separateApprover` included.

**When four eyes is on:**
- **The person who asked isn't offered Approve.** That holds on the
  console's approval page, in its inbox's keyboard decisions ("You asked
  for this, so someone else approves it."), and on the Kindgi plugin for
  WordPress's Approvals tab.
- **The API refuses their approve:**

  ```json
  {
    "error": {
      "code": "separate-approver-required",
      "message": "Approval ecaaa545-… was asked for by you: someone else must approve it",
      "details": { "approvalId": "ecaaa545-…" },
      "requestId": "…"
    }
  }
  ```

- **They may still reject their own request.**
- **A turn that's already waiting** keeps the rule it parked with.
- **It compares people.** A turn started with an app's key names the key's
  service account (`service_account:<id>`), so a person holding that key
  can still approve the call as themselves.
- **With `ask_on_first_use`,** only a tool's first call is asked, and
  someone other than whoever asked approves that one.
- **The template's tools:** the store agent sets `separateApprover` per tool,
  and `defineAgent` refuses an override naming a tool the agent doesn't
  have, so a mistyped id never leaves the real tool without four eyes.

**The `woocommerce` template's store agent turns it on** for
`<pack>.woo.refund-large`, `<pack>.woo.set-price` and
`<pack>.woo.publish-product` (`acme-shop.woo.refund-large` in a pack named
`acme-shop`).

## When no person started the run

**A tool can ask for a person's yes on every call no person is there to
see:** it declares `needsApprovalWhenUnattended: true`. Declare it on a tool
that moves money or changes something people rely on. Then, in a run no
person started:

- **An agent's call of the tool waits** for a reviewer, as `always_ask`
  does. The agent's `hitl` can't lift it, nor can your tenant's
  [approval rules](../approval-rules-for-every-agent/): agents are reused,
  and the tool's author knows what it does. Only the schedule, webhook
  trigger or mail trigger that started the run can, by listing the tool
  ([Tools allowed unattended](#tools-allowed-unattended)).
- **A flow's tool step that calls it fails,** as [In a flow](#in-a-flow)
  shows.

In a run a person started, the agent's own gates decide, as for any tool.
Absent means `false`. Here `acme-ops.post-update`, which posts in public,
declares it:

**How a run started** is on the run, as `startedBy`:

| `startedBy` | Who started it | Counts as a person |
| --- | --- | --- |
| `person` | A person: signed in (the console, the chat of the Kindgi plugin for WordPress), or with their own API key | Yes |
| `key` | A service account's key | No |
| `schedule`, `webhook`, `event`, `mail` | A trigger | No |

- **A key acts as its person.** A script on your own key starts runs as
  you, and they count as yours. For automation, use a
  [service account's key](../../../deploy/people-and-keys/#service-accounts): its runs count as
  unattended.
- **A flow's agent step, and any run a run starts,** started the way its run
  did.
- **A run from before your runtime recorded it** reads as its trigger's
  kind when a trigger started it, and has no `startedBy` otherwise. Either
  way it counts as unattended: it never reads as a person's.
- **The `woocommerce` template declares it** on `<pack>.woo.refund`,
  `<pack>.woo.refund-large`, `<pack>.woo.set-price` and
  `<pack>.woo.publish-product`. A staff member's refund in the store chat
  runs as the agent says; one an order webhook's run asks for waits for a
  person.

### Tools allowed unattended

A schedule, a webhook trigger or a mail trigger can list tools its runs
call without waiting for a person's yes: its tools allowed unattended
(`toolsAllowedUnattended`, runtime 0.2.0 or later). List a tool there when
the trigger is there to run it, such as a nightly status post. A mail
trigger's list needs more care, since anyone who can write to the mailbox
writes its runs' input
([List a tool](../../runs/start-runs-from-new-mail/#list-a-tool)):

```sh
pnpm exec kindgi schedules update <schedule-id> --allow-unattended=acme-ops.post-update
```

- **It lifts only the wait for a person.** In the trigger's runs, a listed
  tool's call goes as the agent's own `hitl` and your tenant's
  [approval rules](../approval-rules-for-every-agent/) say, as in a run a
  person started: a rule that asks before the tool runs still asks. The
  run still acts as the trigger's owner, so the call is checked against
  their access. It covers both kinds of tool that ask: one that declares
  `needsApprovalWhenUnattended`, and one that uses a person's connection,
  reads included
  ([Use a connection in a tool](../../connections/use-a-connection/#approvals)).
  Such a run still can't wait for anyone to connect
  ([When the connection is missing](../../connections/use-a-connection/#when-the-connection-is-missing)).
- **Each entry is one tool's id,** with no wildcard or pattern, at most
  100 of them. Each must be a tool the trigger's agent or flow calls: the
  agent's tools, or a flow's tool steps and its agent steps' tools, its
  subflows' included. That's checked when you set it, and a tool it
  doesn't call is
  refused (`400 bad-input`). A schedule that starts
  [Improve runs](../../improve/improve-an-agent/) calls no tools, so its
  list stays empty.
- **Only the trigger's runs have it.** A run takes the list as it is when
  the trigger fires, and the runs that run starts, such as a flow's agent
  steps, take the same list. A run that waits and resumes keeps the list it
  started with, so a change reaches the next fire. Any other run has none:
  a person's, a key's, an event trigger's. `POST /v1/runs` can't set one.
- **Setting it takes `admin` on the trigger's project,** clearing it too.
  A caller with only `write` is answered `403 permission-denied`.
- **With the CLI,** it's `--allow-unattended=<tool-id>`, once for each
  tool, on `kindgi schedules create` and `update`, on `kindgi webhooks
  register` and `update`, and on `kindgi mail-triggers create` and
  `update`. On `update` it replaces the list,
  `--allow-unattended=none` clears it, and leaving it out keeps it. From
  your app, it's `toolsAllowedUnattended` on `register` and `update` of
  `schedules`, `webhooks` and `mailTriggers`
  (`tools_allowed_unattended` in Python). `kindgi schedules get`,
  `kindgi webhooks get` and `kindgi mail-triggers get` show it when it
  isn't empty. A schedule's or webhook trigger's page in the console shows
  it as **Tools allowed unattended**, or "None". The console doesn't
  change it.
- **A new owner keeps it.** After a take-over, the trigger's runs call the
  tools it lists as the new owner, with their access, and the CLI says so,
  with the line that clears it. A take-over can't change the list: use
  `update`. Changing the list keeps the owner, as every change does
  ([Shared or personal](../../runs/run-on-a-schedule/#shared-or-personal)).
- **A schedule pointed at another agent or flow** must name its list
  again, as it is or `none` (`[]` from your app), or the change is refused
  (`400 bad-input`). A new version of the same one keeps the list.
  Pointed at Improve runs, it must name `none`, since an Improve run
  calls no tools.
- **Each change is recorded as evidence,**
  `trigger-tools-allowed-unattended-set`, with the list before and after
  and what the trigger runs. It's kept for good, on
  [legal hold](../../../deploy/retention/#on-legal-hold). A take-over's
  `trigger-owner-set` records the list it kept.

## Say what a reviewer reads

The approval above reads "Approve a call to acme-ops.post-update", with the
model's arguments in `subjectRef.arguments`. Give the tool an `approval`, and
each call also reads in the tool's own words: a `title`, a `summary` if you
like, and `about`, what the call acts on. It needs a runtime on Kindgi \<x>
or later: an older one refuses a tool that declares `approval`.

Each `{field}` takes the value the model chose for that field of the input:

The next call's approval keeps its words in `context`:

```json
{
  …
  "title": "Approve a call to acme-ops.post-update",
  "context": {
    "text": {
      "title": "Post to the status page: Checkout is back to normal."
    }
  },
  …
}
```

- **Its `title` stays "Approve a call to acme-ops.post-update".** The title
  goes out in the reviewer's mail and in the `approval.requested` event, which
  never carry a call's arguments. The words stay in the approval, behind
  sign-in. In the console, a signed-in reviewer reads the call in these words.
- **Each `{field}` names a required top-level field of the input** whose type
  is a string, a number, an integer or a boolean (or an enum of those).
  Defining the tool fails for any other, naming the tool and the text: an
  optional field (a call may leave it out), an object, an array, a field that
  may be `null`. So does a brace that isn't part of a placeholder.
- **`summary` and `about` work the same way.** `about` names what the call
  acts on, as a `kind` (a lowercase dotted name, such as `woocommerce.order`)
  and an `id` that holds at least one placeholder. The approval keeps it as
  `context.about`. The WooCommerce starter (`kindgi init --template=woocommerce`)
  gives each of its four tools that change the store a title and an `about`,
  and its two refunds a summary too: `Refund {amount} on order #{orderId}`,
  with `{reason}`, about `woocommerce.order` `{orderId}`.
- **`about.id` is a thing's id, never a person's details:** an order number,
  never an email. A summary can hold a person's details:
  [erasing a person's data](../../agents/erase-a-persons-data/) clears a call's
  words and its `about.id` with its arguments, and keeps `about.kind`. The
  approval then reads its title.
- **Each value is filled in as plain text, on one line.** Line breaks and
  control characters become spaces, bidi controls go, and a long value is cut,
  ending in `…`: 80 characters in the title, 500 in the summary and 200 in
  `about.id`. Then each whole text is cut the same way: at 200, 1000 and 200.
- **It doesn't make a call wait.** The agent's rules and
  `needsApprovalWhenUnattended` decide that.

## Reject it

With `--decision=reject`, the tool doesn't run. The agent gets the rejection
as the tool's result, with your rationale, and finishes its turn. A real
model can tell the user why nothing was posted. `<approval-id>` is the
approval's `id`:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi approvals complete <approval-id> --decision=reject --rationale="Not confirmed yet"
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi approvals complete <approval-id> --decision=reject --rationale="Not confirmed yet"
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw approvals complete <approval-id> --decision=reject --rationale="Not confirmed yet"
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw approvals complete <approval-id> --decision=reject --rationale="Not confirmed yet"
```

</TabItem>
</Tabs>

It prints the recorded decision, as approving does. The run's messages then
hold the rejection as the tool's result:

```json
      {
        "role": "tool",
        "content": {
          "status": "rejected",
          "rationale": "Not confirmed yet"
        },
        …
```

The run completes; it doesn't fail. The turn's
[provenance](../../observability/trace-an-answer/) keeps the rejected call:
its `tool-call`, and a `tool-result` that is the rejection the model read.

## In a flow

When the agent is a step of a flow, the flow waits with it: the flow run is
`suspended` too, and its journal shows the step waiting. `<flow-run-id>` is
the flow run's id:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi runs journal <flow-run-id>
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi runs journal <flow-run-id>
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw runs journal <flow-run-id>
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw runs journal <flow-run-id>
```

</TabItem>
</Tabs>

```json
  {
    "sequence": 6,
    "kind": "wait.suspended",
    "nodeId": "respond",
    …
  }
```

The approval's `provenanceRef.runId` is the agent step's own run, not the flow
run. Once the approval is decided, the agent's turn finishes and the flow
continues from that step.

**A tool step can't wait for a person.** In a run no person started, a step
whose tool needs a person's yes fails, and the tool never runs: one that
declares `needsApprovalWhenUnattended`, or one that uses a person's
connection
([Use a connection in a tool](../../connections/use-a-connection/#approvals)).
The run's `failureMessage` says why:

```text
needs-a-person: tool "acme-ops.post-update" needs a person's yes when no person started the run (needsApprovalWhenUnattended), and a flow's tool step can't wait for one. Call it from an agent step instead: there the call waits for a person to approve it.
```

For a tool that uses a person's connection, the reason in parentheses
reads `it uses a person's connection`. Call such a
tool from an agent step, whose call waits for a reviewer. In a schedule's,
a webhook trigger's or a mail trigger's run, the message adds that the
trigger could list the tool instead
([Tools allowed unattended](#tools-allowed-unattended)). A schedule's run's
message ends:

```text
Or a project admin can list it in the schedule's toolsAllowedUnattended, so its runs call it without one.
```

In a mail trigger's run, two more reasons can stop a step: `a mail started
the run, and it changes things` (the tool isn't `mutating: false`), and `a
mail started the run, and it uses a connection of the run's own mailbox`
([What waits for a yes](../../runs/start-runs-from-new-mail/#what-waits-for-a-yes)).
