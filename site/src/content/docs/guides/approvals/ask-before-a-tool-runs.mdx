This guide makes an agent wait for a person before it calls a tool that
changes something, then approves or rejects the call.

An agent turns on approval gates in its `conversationPolicy`. When the model
asks for a gated tool, the run stops before the tool is called and waits for a
reviewer. Approve, and the tool runs. Reject, and it doesn't.

## Before you start

- **A pack** on a runtime such as `kindgi dev`, with Kindgi 0.2's CLI. This
  guide uses the pack `acme-ops`, with a read-only tool, `acme-ops.greet`.
- **A model the agent can route to,** with `tool-use`, as
  [Models](../../models/) shows.

## Gate a tool

`acme-ops.post-update` posts to a public status page. It changes something
outside your app, so it doesn't say `mutating: false`. Ask your coding agent:
"I want a tool that posts an update to our public status page." Kindgi's
skills in your pack tell it how
([How it knows Kindgi](../../../start/coding-agents/)). For reference, the
tool looks like this:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// tools/post-update/index.ts
import { defineTool } from '@kindgi/sdk/define';
import type { ToolId } from '@kindgi/sdk/types';
import { z } from 'zod';

const defined = defineTool({
  id: 'acme-ops.post-update' as ToolId,
  description: 'Posts a message to the public status page.',
  version: '0.1.0',
  input: z.object({ message: z.string().min(1).max(500) }),
  output: z.object({ posted: z.boolean(), postedAt: z.string() }),
  effects: [{ kind: 'external-side-effect', resource: 'external:status-page' }],
  handler: async () => ({ posted: true, postedAt: new Date().toISOString() }),
});

if (defined.kind === 'err') throw new Error(defined.error.message);
export default defined.value;
```

`hitl.tools` turns tool gates on for this agent. Each tool then gets a gate:

- **`always_ask`**: every call waits for a decision.
- **`never_ask`**: calls run without asking.
- **No override:** a tool declared read-only, with `mutating: false`, runs
  without asking. Any other tool asks. So `hitl: { tools: {} }` asks before
  every tool that can change something. Here `acme-ops.greet`, which is
  read-only, never asks.

An agent without `hitl.tools` has no tool gates, unless your tenant has
[approval rules](../approval-rules-for-every-agent/).

### Someone other than whoever asked

**A tool call's approval names who asked:** the person the turn runs for, in
`requestedBy` (`user:<id>`, or `service_account:<id>` for an app's key). It
stays the same when someone else's decision resumes the turn.

**By default, that person may approve it too.** `hitl.separateApprover`
makes the approval need someone else (four eyes):

- **`true`** applies to every gated tool.
- **Per tool,** set `overrides`, keyed by tool id as in `tools`. An optional
  `default` covers the tools you don't name.

```ts
conversationPolicy: {
  hitl: {
    tools: { overrides: { 'acme-ops.post-update': 'always_ask' } },
    separateApprover: { overrides: { 'acme-ops.post-update': true } },
  },
},
```

Every pack language sets it the same way: Python's `conversation_policy`,
and the map Java and Scala pass to `set("conversationPolicy", …)`, take the
same keys, `separateApprover` included.

**When four eyes is on:**
- **The person who asked isn't offered Approve.** That holds on the
  console's approval page, in its inbox's keyboard decisions ("You asked
  for this, so someone else approves it."), and on the Kindgi plugin for
  WordPress's Approvals tab.
- **The API refuses their approve:**

  ```json
  {
    "error": {
      "code": "separate-approver-required",
      "message": "Approval ecaaa545-… was asked for by you: someone else must approve it",
      "details": { "approvalId": "ecaaa545-…" },
      "requestId": "…"
    }
  }
  ```

- **They may still reject their own request.**
- **A turn that's already waiting** keeps the rule it parked with.
- **It compares people.** A turn started with an app's key names the key's
  service account (`service_account:<id>`), so a person holding that key
  can still approve the call as themselves.
- **With `ask_on_first_use`,** only a tool's first call is asked, and
  someone other than whoever asked approves that one.
- **The template's tools:** the store agent sets `separateApprover` per tool,
  and `defineAgent` refuses an override naming a tool the agent doesn't
  have, so a mistyped id never leaves the real tool without four eyes.

**The `woocommerce` template's store agent turns it on** for
`<pack>.woo.refund-large`, `<pack>.woo.set-price` and
`<pack>.woo.publish-product` (`acme-shop.woo.refund-large` in a pack named
`acme-shop`).

## When no person started the run

**A tool can ask for a person's yes on every call no person is there to
see:** it declares `needsApprovalWhenUnattended: true`. Declare it on a tool
that moves money or changes something people rely on. Then, in a run no
person started:

- **An agent's call of the tool waits** for a reviewer, as `always_ask`
  does. The agent's `hitl` can't lift it, nor can your tenant's
  [approval rules](../approval-rules-for-every-agent/): agents are reused,
  and the tool's author knows what it does.
- **A flow's tool step that calls it fails,** as [In a flow](#in-a-flow)
  shows.

In a run a person started, the agent's own gates decide, as for any tool.
Absent means `false`. Here `acme-ops.post-update`, which posts in public,
declares it:

**How a run started** is on the run, as `startedBy`:

| `startedBy` | Who started it | Counts as a person |
| --- | --- | --- |
| `person` | A person: signed in (the console, the chat of the Kindgi plugin for WordPress), or with their own API key | Yes |
| `key` | A service account's key | No |
| `schedule`, `webhook`, `event` | A trigger | No |

- **A key acts as its person.** A script on your own key starts runs as
  you, and they count as yours. For automation, use a
  [service account's key](../../../deploy/people-and-keys/#service-accounts): its runs count as
  unattended.
- **A flow's agent step, and any run a run starts,** started the way its run
  did.
- **A run from before your runtime recorded it** reads as its trigger's
  kind when a trigger started it, and has no `startedBy` otherwise. Either
  way it counts as unattended: it never reads as a person's.
- **The `woocommerce` template declares it** on `<pack>.woo.refund`,
  `<pack>.woo.refund-large`, `<pack>.woo.set-price` and
  `<pack>.woo.publish-product`. A staff member's refund in the store chat
  runs as the agent says; one an order webhook's run asks for waits for a
  person.

## Become a reviewer

Approvals are decided by **reviewers**. Under `kindgi dev` you're one already,
an `admin`. On any other runtime, register yourself once, as the user your API
token belongs to. It covers any token of yours, a console sign-in too:

## Reject it

With `--decision=reject`, the tool doesn't run. The agent gets the rejection
as the tool's result, with your rationale, and finishes its turn. A real
model can tell the user why nothing was posted. `<approval-id>` is the
approval's `id`:

The approval's `provenanceRef.runId` is the agent step's own run, not the flow
run. Once the approval is decided, the agent's turn finishes and the flow
continues from that step.

**A tool step can't wait for a person.** In a run no person started, a step
whose tool declares `needsApprovalWhenUnattended` fails, and the tool never
runs. The run's `failureMessage` says why:

```text
needs-a-person: tool "acme-ops.post-update" needs a person's yes when no person started the run (needsApprovalWhenUnattended), and a flow's tool step can't wait for one. Call it from an agent step instead: there the call waits for a person to approve it.
```

Call such a tool from an agent step, whose call waits for a reviewer.
