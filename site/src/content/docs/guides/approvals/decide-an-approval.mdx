A run that waits for a person (a [gated tool call](../ask-before-a-tool-runs/)
or a [long conversation](../ask-after-n-turns/)) creates an **approval**. A
**reviewer** decides it, and the run moves on.

## Reviewers and roles

Only reviewers see approvals. Under `kindgi dev` you're one already: when it
starts on a database where you aren't a reviewer yet, it registers you, the
user of its token, as an `admin`:

```sh
kindgi reviewers list
```

```json
{
  "data": [
    {
      "id": "6c11cfb1-d0c2-46dd-a3a0-e859a57b5da0",
      "tenantId": "9126df1e-094b-496d-9ea8-7daab93c3f4f",
      "userId": "26fc414a-b49f-4e1f-a022-162865770178",
      "role": "admin",
      "createdAt": "2026-10-05T20:10:59.747Z"
    }
  ],
  "hasMore": false
}
```

On any other runtime, register each person who reviews, the user their API
token belongs to, with a role. That covers any token of theirs: an API key or
a console sign-in.

```sh
kindgi reviewers register --spec='{"role":"standard","displayName":"Ada Lovelace"}'
```

```json
{
  "id": "b4bc07d5-1640-4c4c-9cbe-710aa6ca7d36",
  "tenantId": "3a9fb26d-9782-4bdb-a4f9-3c97d2644b72",
  "userId": "b9b6a8af-84ee-4514-a609-a76230750869",
  "role": "standard",
  "displayName": "Ada Lovelace",
  "createdAt": "2026-10-03T19:55:32.200Z"
}
```

The roles rank `standard`, `senior`, `admin`. Each approval has a
`requiredRole`, and a reviewer sees and decides the approvals that need their
role or a lower one. An approval that needs a higher role doesn't show up in
the list, and fetching or deciding it answers `not-found`.

Registering again changes the role. `kindgi reviewers list` shows the
reviewers; `kindgi reviewers unregister <reviewer-id>` removes one (their
past decisions stay). A user who isn't a reviewer is refused:

```text
Error [auth]: The caller isn't a reviewer: its token carries no reviewer role, and its user isn't registered as one (`kindgi reviewers register`). The approvals surface is reviewer-only.
```

`kindgi dev` leaves a role you set as it is, and doesn't register you again
after you unregister yourself.

## Reviewer email

With `KINDGI_REVIEWER_EMAIL=on`, the runtime emails reviewers when an
approval starts waiting, and when a waiting approval is assigned:

- **Who:** the people the approvals list would show it to: its assigned
  reviewer, or else every active reviewer of its required role or above.
  Only those who may read its project.
- **Assigned later:** a reviewer an approval is assigned to after it started
  waiting is emailed then, unless they were already emailed about it.
- **What:** its title, project, required role and when it was asked, and a
  link to it in the console. Never what it's about: that stays behind
  sign-in.
- **How often:** a reviewer's first email goes at once. Anything more for
  them within five minutes comes as one digest at the end of the five
  minutes. An approval decided in the meantime is left out.

One approval, as a reviewer gets it (ids elided):

```text
Subject: Approval needed: Refund over the limit

An approval is waiting for you.

Refund over the limit
  Project: Default
  Needs: a standard reviewer or above
  Asked: 2026-10-10 01:37 UTC
  …/console/approvals/…

Sign in to decide: what each approval is about is only in the console.

You're getting this because you're a reviewer in Kindgi.
```

Several in one digest have the subject "2 approvals are waiting for you",
with the same lines for each.

It uses the emailed sign-in link's server (`KINDGI_AUTH_EMAIL_SMTP_URL` and
`KINDGI_AUTH_EMAIL_FROM`). Turned on without them, the runtime refuses to
start. It's off by default. For a system of your own, an
[`approval.requested` webhook](../../webhooks/receive-run-finished/#approvals)
carries the same facts.

## Find what's waiting

```sh
kindgi approvals list --status=pending
kindgi approvals get <approval-id>
```

Without `--status`, the list includes decided approvals too. In each
approval:

- **`subjectKind`** is what waits: `tool-call:pending` is a tool call (the
  `subjectRef` has the `toolId` and the `arguments`);
  `agent-turn:session-hitl-gate` is a conversation that reached its turn limit
  (the `subjectRef` has the `conversationId` and the `turnCount`).
- **`requiredRole`** is the lowest role that may decide it.
- **`provenanceRef.runId`** is the run that waits.
- **`decision`**, once someone decided it: the decision, the rationale, who
  (`decidedBy`, as `user:<id>`, and their `reviewerId`), their role then, and
  when. There's none while it's open, nor when it ended without a decision
  (it expired, or a timeout escalated it).

```json
"decision": {
  "decision": "approve",
  "decidedBy": "user:26fc414a-b49f-4e1f-a022-162865770178",
  "reviewerId": "974b5bb3-c690-4886-a609-c7fe0cbd5659",
  "reviewerRoleAtDecision": "standard",
  "decidedAt": "2026-10-05T16:25:52.878Z",
  "rationale": "Confirmed with the on-call engineer"
}
```

## Decide

```sh
kindgi approvals complete <approval-id> --decision=approve --rationale="Confirmed with the on-call engineer"
```

`--rationale` is optional and is kept with the decision. The four decisions:

| Decision | The approval | The run |
| --- | --- | --- |
| `approve` | `approved` | Continues: the tool runs, or the turn runs. |
| `reject` | `rejected` | A tool call: the tool doesn't run, and the agent gets the rejection as the tool's result. A turn: the run fails with `hitl-rejected`. |
| `escalate` | `escalated`, and a new approval for the next role up | Keeps waiting for the new approval. |
| `withdraw` | `withdrawn` | Ends: its turn fails with `hitl-withdrawn`. |

An approve, reject or withdraw resolves the run within the same call, so the
run has moved on by the time the command returns.

An approval that's no longer waiting (decided, expired, or withdrawn by a
reviewer or by its run's end) can't be decided again. The decision is
refused with `409 approval-terminal`, saying how the approval ended, and
nothing is recorded:

```text
Approval … was withdrawn: its run was cancelled
```

A turn that ends at its approval fails with one of these codes, each a
person's outcome, not an error:

- `hitl-rejected`: a reviewer rejected the turn (its session gate; a rejected
  tool call skips only the tool, and the turn goes on).
- `hitl-withdrawn`: a reviewer withdrew the approval.
- `hitl-cancelled`: nobody decided in time, so the approval expired at the
  `admin` role.

A run cancelled while it waits ends `cancelled`, with no failure code.

An approval still waiting when its run, or a run it's a step of, has already
ended can't be decided either: the decision is refused with
`409 run-already-terminal`, and nothing is recorded. Its `details` name
the run that ended (it may be the run the approval's run is a step of) and
its `status`. A decision recorded just before its run ended stands: the
answer has `waitpointResolved: false` and the run's `runStatus`.

Each decision also goes into the audit trail, as an `hitl-decision` event:
who decided, how it ended and the rationale. It's kept for good, even when the
runtime purges other audit events (see
[Audit events](../../../deploy/retention/#audit-events)).

### Escalate

A `standard` reviewer who wants a second opinion escalates:

```sh
kindgi approvals complete 2134897a-d176-4ca8-b000-8bc00d79ad04 --decision=escalate --rationale="Needs sign-off from the incident lead"
```

```json
{
  "kind": "escalated",
  "approval": {
    "id": "2134897a-d176-4ca8-b000-8bc00d79ad04",
    …
    "requiredRole": "standard",
    "status": "escalated",
    …
  },
  …
  "nextApproval": {
    "id": "a65cd23c-1bdb-47d8-9b3a-aaec36475a4f",
    …
    "requiredRole": "senior",
    "status": "pending",
    …
  },
  "waitpointResolved": false
}
```

The new approval needs a `senior` reviewer, so the `standard` reviewer no
longer sees it. A `senior` (or `admin`) reviewer approves or rejects
`a65cd23c-…`, and the run continues.

### Withdraw

Withdraw closes an approval without deciding what it asked, when the
request is moot. The run waiting on it can't go on, so it ends: its turn
fails with `hitl-withdrawn` ("The approval for tool call acme-desk.echo was
withdrawn").

```sh
kindgi approvals complete <approval-id> --decision=withdraw --rationale="Asked by mistake"
```

Cancelling a run withdraws its open approvals by itself: see
[Cancel a run](../../runs/cancel-a-run/#approvals-of-a-cancelled-run).
Those approvals show `withdrawnBecause: "run-cancelled"` (or `run-ended`,
when a run ended otherwise while they waited, e.g. it failed) and no
`decision`.

### When nobody decides

Each approval has a deadline, its `expiresAt`: 24 hours after it's asked for,
or the agent's own `hitl.timeoutMs` (one hour:
`conversationPolicy: { hitl: { tools: {}, timeoutMs: 3_600_000 } }`). When the
deadline passes with no decision:

- **Below `admin`,** the approval becomes `escalated`, and a new one asks the
  next role up (`standard`, then `senior`, then `admin`), with a deadline as
  long again. The run keeps waiting.
- **At `admin`,** the approval becomes `expired`, and the run's turn fails:

  ```text
  "error":{"code":"hitl-cancelled","message":"Tool-call HITL cancelled for acme-desk.echo: timeout","reason":"timeout"}
  ```

  The run's `failure` says the same as data: `code: "hitl-cancelled"`,
  `reason: "timeout"`. Read `reason` rather than the message; a runtime from
  before 0.1.6 doesn't send it, so go by `code` alone there.

A decision made before the deadline always wins. A deadline always escalates
this way: `hitl.onTimeout` takes only `'escalate'`, the default. An agent that
asks for anything else is refused when it's defined:

```text
hitl.onTimeout 'auto-approve' isn't supported: an approval that times out escalates one reviewer tier, and at admin it expires (the turn fails with hitl-cancelled). Use 'escalate', or leave it out.
```

## From your app

A reviewer usually decides in your app, not in a terminal. The client lists
the pending approvals and records the decision; the reviewer is the user the
API token belongs to.

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// review.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

const pending = await kindgi.approvals.list({ status: 'pending' });
for (const approval of pending.data) {
  console.log(approval.id, approval.title, approval.subjectRef);
}

const first = pending.data[0];
if (first) {
  const result = await kindgi.approvals.decide(first.id, {
    decision: 'approve',
    rationale: 'Checked the dashboard',
  });
  console.log(result.approval.status, result.waitpointResolved);
}
```

```text
46f0f9ad-f22d-4a93-8337-25b7c32a7473 HITL review: acme-ops.post-update {
  callId: 'dev-echo-call-1',
  toolId: 'acme-ops.post-update',
  agentId: 'acme-ops.status-agent',
  …
  arguments: { message: 'Checkout is slow for some customers.' },
  …
}
approved true
```

</TabItem>
<TabItem label="Python">

```python
# review.py
from kindgi.client import Kindgi

kindgi = Kindgi()  # KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

pending = kindgi.approvals.list(status="pending")
for approval in pending.data:
    print(approval.id, approval.title, approval.subject_ref)

if pending.data:
    result = kindgi.approvals.complete(
        pending.data[0].id, decision="approve", rationale="Checked the dashboard"
    )
    print(result.approval.status, result.waitpoint_resolved)
```

```text
approved True
```

`list` takes a `scope` to see one project's approvals, or every project's in
an org: `{ kind: 'project', projectId }` (`scope_kind="project", scope_id=…`)
or `{ kind: 'org', orgId }`. An agent's approval is in its turn's project.
Approvals from before Kindgi 0.1.3 have no project, so only a list without a
scope shows them. `runId` lists the approvals one run asked for, and with
`includeDescendants: true` those of the runs inside it.

An approval also says:

- **who asked for it** (`requestedBy`: `user:<id>`, `service_account:<id>`
  or `system:<what>`), and whether that person may approve it
  (`separateApprover: true` means they may not). Compare `requestedBy` with
  the caller's `actor` from `identity.whoami()` to leave out an Approve
  button they can't use.
- **where an escalation came from and went:** `escalatedFrom` and
  `escalatedTo`, approval ids.
