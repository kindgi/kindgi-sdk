This guide gets a waiting approval decided, so the run that waits on it goes
on.

A run that waits for a person creates an **approval**, such as a
[gated tool call](../ask-before-a-tool-runs/) or a
[long conversation](../ask-after-n-turns/). A **reviewer** decides it, and the
run moves on. [Approvals reference](../approvals-reference/) has every field,
decision, code and console page.

## Before you start

- **A run that waits for an approval.**
  [Ask before a tool runs](../ask-before-a-tool-runs/) makes one.
- **`kindgi dev` running** in your pack's directory, with Kindgi 0.2's CLI.
- **For the app's half:** Node 22.12 or later, Python 3.11 or later, or Java
  17 or later, with Kindgi 0.2's client, and `KINDGI_API_URL` and
  `KINDGI_API_TOKEN` set.

## Reviewers and roles

approvals without being one ([Approvals reference](../approvals-reference/)),
but registers to decide.

you aren't a reviewer yet, it registers you, the user of its token, as an

approvals that need their role or a lower one. Registering again changes the
role. A tenant admin can also add reviewers in the console, on
[the Reviewers page](../approvals-reference/#the-reviewers-page).

## Reviewer email

Email lets reviewers hear about an approval without watching the console.
It's optional, and off by default.

Set `KINDGI_REVIEWER_EMAIL=on` in the runtime's environment. It sends through
the emailed sign-in link's server, so `KINDGI_AUTH_EMAIL_SMTP_URL` and
`KINDGI_AUTH_EMAIL_FROM` must be set too. Turned on without them, the
runtime refuses to start.

The runtime then emails reviewers when an approval starts waiting, and when a
waiting approval is assigned:

- **Who:** the people the approvals list would show it to: the one person
  it's addressed to (its `approver`), else its assigned reviewer, or else
  every active reviewer of its required role or above.
  Only those who may read its project are emailed.
- **Assigned later:** a reviewer an approval is assigned to after it started
  waiting is emailed then, unless they were already emailed about it.
- **What:** its title, project, required role and when it was asked, and a
  link to it in the console. Never what it's about: that stays behind
  sign-in.
- **How often:** a reviewer's first email goes at once. Anything more for
  them within five minutes comes as one digest at the end of the five
  minutes. An approval decided in the meantime is left out.

One approval, as a reviewer gets it, with the ids elided:

```text
Subject: Approval needed: Refund over the limit

An approval is waiting for you.

Refund over the limit
  Project: First Project
  Needs: a standard reviewer or above
  Asked: 2026-10-10 01:37 UTC
  …/console/approvals/…

Sign in to decide: what each approval is about is only in the console.

You're getting this because you're a reviewer in Kindgi.
```

Several in one digest have the subject "2 approvals are waiting for you",
with the same lines for each. For a system of your own, an
[`approval.requested` webhook](../../webhooks/webhook-events/#approvals)
carries the same facts.

```

```

- `--status` takes several statuses, comma-separated.
- `--assigned-to=me` keeps the approvals assigned to you. Assigning one moves
  it to `assigned`.
- `--order=asc` lists the oldest first.

Each approval says what waits, who may decide it and which run waits on it.
[An approval's fields](../approvals-reference/#an-approvals-fields) lists
them.

### What a run waits for

From a run, `kindgi runs resume <run-id>` says what it waits for, and how it
goes on. `<run-id>` is the run's id:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi runs resume 45d986f1-8a8d-4341-a786-5ddcf239bb93
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi runs resume 45d986f1-8a8d-4341-a786-5ddcf239bb93
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw runs resume 45d986f1-8a8d-4341-a786-5ddcf239bb93
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw runs resume 45d986f1-8a8d-4341-a786-5ddcf239bb93
```

</TabItem>
</Tabs>

```text
Run 45d986f1-8a8d-4341-a786-5ddcf239bb93 waits for approval b3fcf729-0137-430e-92a3-2ff10f4a6bde ("HITL review required for Chat desk"), for a standard reviewer or above. It continues once the approval is decided: kindgi approvals complete b3fcf729-0137-430e-92a3-2ff10f4a6bde --decision=approve (or --decision=reject).
```

That sentence goes to stderr. Its standard output is the same answer as
JSON, for a script:

```json
{
  "kind": "approval",
  "runId": "45d986f1-8a8d-4341-a786-5ddcf239bb93",
  "status": "suspended",
  "approvals": [
    {
      "id": "b3fcf729-0137-430e-92a3-2ff10f4a6bde",
      "title": "HITL review required for Chat desk",
      "requiredRole": "standard",
      "status": "pending"
    }
  ],
  "alsoWaitsOn": []
}
```

Its exit code says which:

| Exit | The run |
| --- | --- |
| `0` | isn't waiting: `Run … is completed: it isn't waiting, so there's nothing to resume.` |
| `3` | waits for an approval, named in the sentence |
| `4` | waits on the runtime: a queued start, a child run, a retry, a lease |
| `5` | waits for another system's answer to a tool's call, which `kindgi runs resume <run-id> --output=<json>` can also give |
| `6` | waits for the person who started it to [connect an app](../../connections/use-a-connection/#when-the-connection-is-missing), and the sentence ends with the link they connect from |

A run that waits for more than one of these exits with the first that
applies, in this order: `3`, `5`, `6`, `4`. `1` and `2` stay the CLI's
error and usage codes.

Once the approval is decided, the run goes on by itself. From your app,
`runs.get` answers the same as the run's
[`waitingFor`](../approvals-reference/#a-runs-waitingfor).

In the console, a reviewer's **Inbox** lists every approval they may decide,
as [The Inbox](../approvals-reference/#the-inbox) describes.

## Decide

Deciding the approval lets the run go on, or ends what it asked for.

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi approvals complete <approval-id> --decision=approve --rationale="Confirmed with the on-call engineer"
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi approvals complete <approval-id> --decision=approve --rationale="Confirmed with the on-call engineer"
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw approvals complete <approval-id> --decision=approve --rationale="Confirmed with the on-call engineer"
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw approvals complete <approval-id> --decision=approve --rationale="Confirmed with the on-call engineer"
```

</TabItem>
</Tabs>

- `<approval-id>` is the approval's `id`.
- `--decision` is one of the four decisions in the table.
- `--rationale` (optional) is kept with the decision, and goes into the audit
  trail.

| Decision | The approval | The run |
| --- | --- | --- |
| `approve` | `approved` | Continues: the tool runs, or the turn runs. |
| `reject` | `rejected` | A tool call: the tool doesn't run, and the agent gets the rejection as the tool's result. A turn: the run fails with `hitl-rejected`. |
| `escalate` | `escalated`, and a new approval for the next role up | Keeps waiting for the new approval. |
| `withdraw` | `withdrawn` | Ends: its turn fails with `hitl-withdrawn`. |

An approve, reject or withdraw resolves the run within the same call. So the
run has moved on by the time the command returns. A decision can be
refused, such as on an approval that's no longer waiting:
[Decisions](../approvals-reference/#decisions) lists why.

In the console, a reviewer decides on the approval's page or in the Inbox,
as [Deciding in the console](../approvals-reference/#deciding-in-the-console)
shows. In a run a mail started, it shows that mail too.

### Escalate

Escalating asks a reviewer of the next role up instead. A `standard` reviewer
who wants a second opinion escalates:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh

```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi approvals complete 2134897a-d176-4ca8-b000-8bc00d79ad04 --decision=escalate --rationale="Needs sign-off from the incident lead"
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw approvals complete 2134897a-d176-4ca8-b000-8bc00d79ad04 --decision=escalate --rationale="Needs sign-off from the incident lead"
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw approvals complete 2134897a-d176-4ca8-b000-8bc00d79ad04 --decision=escalate --rationale="Needs sign-off from the incident lead"
```

</TabItem>
</Tabs>

It prints the escalated approval and the new one:

```json
{
  "kind": "escalated",
  "approval": {
    "id": "2134897a-d176-4ca8-b000-8bc00d79ad04",
    …
    "requiredRole": "standard",
    "status": "escalated",
    …
  },
  …
  "nextApproval": {
    "id": "a65cd23c-1bdb-47d8-9b3a-aaec36475a4f",
    …
    "requiredRole": "senior",
    "status": "pending",
    …
  },
  "waitpointResolved": false
}
```

The new approval needs a `senior` reviewer, so the `standard` reviewer no
longer sees it. A `senior` or `admin` reviewer approves or rejects
`a65cd23c-…`, and the run continues.

**An approval addressed to one person can't be escalated.** That's a tool
call that acts with the person's own connection: only its `approver`
decides it, and only they see it among the reviewers. A tenant admin sees
it too, but can't decide it (`403 named-approver-required`). An escalation
is refused with `409 invalid-transition`, and at its deadline it expires
instead ([When nobody decides](../approvals-reference/#when-nobody-decides)).
The person approves or rejects it
([Use a connection in a tool](../../connections/use-a-connection/#approvals)).

## From your app

A reviewer usually decides in your app, not in a terminal. The client lists
the pending approvals and records the decision. The reviewer is the user the
API token belongs to.

Ask your coding agent: "In my app, let a reviewer see the pending approvals
and approve one." For reference, the code looks like this, with what it
prints:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// review.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

const pending = await kindgi.approvals.list({ status: 'pending' });
for (const approval of pending.data) {
  console.log(approval.id, approval.title, approval.subjectRef);
}

const first = pending.data[0];
if (first) {
  const result = await kindgi.approvals.decide(first.id, {
    decision: 'approve',
    rationale: 'Checked the dashboard',
  });
  console.log(result.approval.status, result.waitpointResolved);
}
```

It prints each pending approval, then the decision's outcome:

```text
46f0f9ad-f22d-4a93-8337-25b7c32a7473 HITL review: acme-ops.post-update {
  callId: 'dev-echo-call-1',
  toolId: 'acme-ops.post-update',
  agentId: 'acme-ops.status-agent',
  …
  arguments: { message: 'Checkout is slow for some customers.' },
  …
}
approved true
```

</TabItem>
<TabItem label="Python">

```java
// src/main/java/com/acme/app/Review.java
package com.acme.app;

import com.kindgi.client.Kindgi;
import com.kindgi.client.models.Approval;
import com.kindgi.client.models.ApprovalCollectionPage;
import com.kindgi.client.models.ApprovalStatus;
import com.kindgi.client.models.CompleteApprovalBody;
import com.kindgi.client.models.CompleteApprovalResult;
import com.kindgi.client.resources.ApprovalsListParams;
import java.util.List;

public final class Review {
  public static void main(String[] args) {
    Kindgi kindgi = Kindgi.create(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

    ApprovalCollectionPage pending = kindgi.approvals().list(
        ApprovalsListParams.builder().status(List.of(ApprovalStatus.PENDING)).build());
    for (Approval approval : pending.data()) {
      System.out.println(approval.id() + " " + approval.title() + " " + approval.subjectRef());
    }

    if (!pending.data().isEmpty()) {
      CompleteApprovalResult result = kindgi.approvals().complete(pending.data().get(0).id(),
          CompleteApprovalBody.builder()
              .decision(CompleteApprovalBody.Decision.APPROVE)
              .rationale("Checked the dashboard")
              .build());
      System.out.println(result.approval().status() + " " + result.waitpointResolved());
    }
  }
}
```

It prints each pending approval, then the decision's outcome:

```text
6faa8787-ff70-476e-b68b-74044b3711cc HITL review: acme-ops.post-update {callId=dev-echo-call-1, toolId=acme-ops.post-update, agentId=acme-ops.status-agent, …, arguments={message=Checkout is slow for some customers.}, …}
approved true
```
