This guide makes an agent version live where you choose, checks which
version a run gets, rolls back, and gates a release behind your test set.

A run that names no version gets the agent's latest version. Once a new
version has done better on your test set, as
[Compare a version on a test set](../compare-an-agent-version/) shows, you
can make it **live** where you choose: the whole tenant, an org, a project, or
a segment of a project's runs, such as one company's. Runs there use it from
the next run, nothing changes anywhere else, and you can roll back at once.
[Live versions reference](../live-versions-reference/) has every rule,
refusal and console page.

## Before you start

- **An agent with more than one version,** registered on a runtime such as
  `kindgi dev`, with Kindgi 0.1's CLI. This guide uses `acme.order-desk`,
  with versions 1.0.0, 1.1.0, 1.2.0 and 1.3.0.
- **A project's id,** for a project or a segment: `kindgi projects list`
  lists them.
- **For a gate:** a comparison of the version on your test set, and a second
  reviewer to approve.
- **For the app's half:** Node 22.12 or later, or Python 3.11 or later, with
  Kindgi 0.1's client, and `KINDGI_API_URL` and `KINDGI_API_TOKEN` set.

## Make a version live

A live version is what a run that names no version gets.

Make 1.0.0 live for the whole tenant:

```sh
kindgi agents promote acme.order-desk 1.0.0 --tenant --reason="1.0.0 is the version we checked"
```

- `acme.order-desk 1.0.0` is the agent and the version.
- `--tenant` is the scope: the whole tenant.
- `--reason` is kept on the record.

It prints the promotion:

```json
{
  "id": "ea4e7c15-7990-41b6-b153-0847a83f2e9d",
  "agentId": "acme.order-desk",
  "scope": { "kind": "tenant" },
  "action": "promote",
  "fromVersion": null,
  "toVersion": "1.0.0",
  "requestedBy": { "kind": "user", "id": "5c0a7e11-0000-4000-8000-0000000000aa" },
  "reason": "1.0.0 is the version we checked",
  "createdAt": "2026-10-06T18:46:15.125Z"
}
```

From the next run, a run that names no version gets 1.0.0, and says why:

```sh
kindgi runs start --agent=acme.order-desk --input='{"userMessage":"Where is order A-1002?"}'
```

```json excerpt
  "agent": {
    "id": "acme.order-desk",
    "version": "1.0.0",
    "conversationId": "4af092ea-5e8e-42f1-832e-b7ba1ed6e3d8",
    "via": "live",
    "liveScope": { "kind": "tenant" }
  },
```

`via: "live"` says it got the live version of the scope in `liveScope`.
[How a run gets its version](../live-versions-reference/#how-a-run-gets-its-version)
lists every `via`. A version only goes live this way: publishing a newer
version doesn't change what a scope with a live version runs.

## Make it live for some runs only

A narrower scope tries a version with some runs first. The most specific
live version wins: a **segment** path in a project, then the **project**, the
project's **org**, the **tenant**, and then the latest version. A segment
path is one or more `key:value` steps, coarse to fine, that a run is started
with: `company:acme`, or `company:acme` then `role:counsel`.

Try 1.1.0 with acme's runs only:

```sh
kindgi agents promote acme.order-desk 1.1.0 --project=<project-id> --segment=company:acme --reason="Trying 1.1.0 with acme first"
```

- `--project=<project-id>` is the project, where `<project-id>` is its id.
- `--segment=company:acme` is the segment path in it.
- `--org=<org-id>` names an org instead.

It prints the promotion, with the segment as its `scope`.

A run started with that segment gets 1.1.0:

```sh
kindgi runs start --agent=acme.order-desk --project=<project-id> --segment=company:acme --input='{"userMessage":"Where is order A-1002?"}'
```

```json excerpt
  "agent": {
    "id": "acme.order-desk",
    "version": "1.1.0",
    "conversationId": "d35be284-99c0-4437-9186-b951386db8b3",
    "via": "live",
    "liveScope": {
      "kind": "segment",
      "projectId": "367e1657-8067-4a1d-8ec4-bfa3c5fc5865",
      "path": [{ "key": "company", "value": "acme" }]
    }
  },
```

A run with `--segment=company:globex` has no live version of its own, so it
gets the tenant's, 1.0.0. Without `--project`, a run is in its agent's own
project, which is Default for what `kindgi deploy` registers.

## See which version a run would get

`kindgi agents live` answers without starting a run:

```sh
kindgi agents live acme.order-desk --project=<project-id> --segment=company:acme
```

```json
{
  "agentId": "acme.order-desk",
  "version": "1.1.0",
  "via": "live",
  "liveScope": {
    "kind": "segment",
    "projectId": "367e1657-8067-4a1d-8ec4-bfa3c5fc5865",
    "path": [{ "key": "company", "value": "acme" }]
  }
}
```

`kindgi agents live-versions acme.order-desk` lists every scope with a live
version, and since when.

## From your app

Your app can do the same, with the project's id as the script's argument:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// release.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
const projectId = process.argv[2];
const acme = [{ key: 'company', value: 'acme' }];

// Make 1.1.0 live for acme's runs in this project.
await kindgi.agents.promotions.create('acme.order-desk', {
  version: '1.1.0',
  scope: { kind: 'segment', projectId, path: acme },
  reason: 'Trying 1.1.0 with acme first',
});

// Which version would a run there use, and why?
const live = await kindgi.agents.live.resolve('acme.order-desk', { projectId, segments: acme });
console.log(live.version, live.via, live.liveScope?.kind);

// A run that names no version gets it.
const run = await kindgi.runs.start({
  agent: 'acme.order-desk',
  projectId,
  segments: acme,
  input: { userMessage: 'Where is order A-1002?' },
});
console.log(run.agent?.version, run.agent?.via);
```

</TabItem>
<TabItem label="Python">

```python
# release.py
import sys

from kindgi.client import Kindgi

kindgi = Kindgi()  # KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
project_id = sys.argv[1]
acme = [{"key": "company", "value": "acme"}]

# Make 1.1.0 live for acme's runs in this project.
kindgi.agents.promotions.create(
    "acme.order-desk",

    scope={"kind": "segment", "project_id": project_id, "path": acme},
    reason="Trying 1.1.0 with acme first",
)

# Which version would a run there use, and why?
live = kindgi.agents.live.resolve("acme.order-desk", project_id=project_id, segments=acme)
print(live.version, live.via, live.live_scope.kind if live.live_scope else None)

# A run that names no version gets it.
run = kindgi.runs.start(
    agent="acme.order-desk",
    project_id=project_id,
    segments=acme,
    input={"userMessage": "Where is order A-1002?"},
)
if run.agent is not None:  # set on an agent's runs
    print(run.agent.version, run.agent.via)
```

## Roll back, or unpin

A rollback puts a scope back on the version that was live there before, at
once:

```sh
kindgi agents rollback acme.order-desk --tenant --reason="1.2.0 answers worse"
```

`--to=<version>` rolls back to another version instead. It prints the
rollback:

```json
{
  "id": "7da674c5-c835-42c0-8cde-59571afd0915",
  "agentId": "acme.order-desk",
  "scope": { "kind": "tenant" },
  "action": "rollback",
  "fromVersion": "1.2.0",
  "toVersion": "1.0.0",
  …
}
```

`kindgi agents unpin` removes a scope's own live version. Its runs then use
the scope above, or the latest version when nothing above is live:

```sh
kindgi agents unpin acme.order-desk --tenant --reason="Back to the latest"
```

Every promotion, rollback and unpin is kept, with who asked and why.
`kindgi agents promotions list acme.order-desk --table` lists them, as
[The history](../live-versions-reference/#the-history) shows.
[Rollbacks and unpins](../live-versions-reference/#rollbacks-and-unpins)
lists what each refuses.

## Gate a release

A **gate policy** says what a promotion must show before a version goes live
for a scope: a recent comparison on your test set, enough judged cases,
figures at least this good, a clean replay and, if you want, a reviewer's
approval. An agent has one policy per scope. A promotion is checked by the
most specific one covering its scope, at its latest version.

### Set a gate

A gated scope needs a live version of its own, so give the tenant one first:

```sh
kindgi agents promote acme.order-desk 1.0.0 --tenant --reason="1.0.0 is the version we checked"
```

Write the policy in `gate.json`:

```json
{
  "comparison": { "maxAgeHours": 168 },
  "evidence": { "minCases": 3 },
  "metrics": [{ "name": "weightedYesShare", "minCandidate": 0.6, "maxDrop": 0.02 }],
  "replay": { "maxRefusedWrites": 0 },
  "approvals": { "role": "senior" }
}
```

Then publish it:

```sh
kindgi gate-policies publish acme.order-desk-release --policy-version=1.0.0 --agent=acme.order-desk --tenant --spec=@gate.json --description="What a release of the order desk must show"
```

- `acme.order-desk-release` is the policy's id, and `--policy-version` its
  version.
- `--agent` and `--tenant` are the agent and the scope it gates.
- `--spec=@gate.json` reads the policy from the file.

The tenant's promotions of `acme.order-desk` now go through the gate.
[Gate policies](../live-versions-reference/#gate-policies) has what each
part asks, and who may publish one.

### Check before you promote

`--check` asks the gate without recording anything:

```sh
kindgi agents promote acme.order-desk 1.3.0 --tenant --eval-run=<comparison-id> --check
```

`--eval-run=<comparison-id>` names the comparison of 1.3.0, where
`<comparison-id>` is its eval run's id. It prints what the gate would say:

```json
{
  "outcome": "needs-approval",
  "policy": { "id": "acme.order-desk-release", "version": "1.0.0" },
  "checks": [
    { "name": "comparison.freshness", "passed": true, "message": "The comparison finished 0.013 hours ago; the policy accepts up to 168.", … },
    { "name": "baselineIsLive", "passed": true, "message": "The baseline is acme.order-desk 1.0.0, the version live for the scope.", … },
    { "name": "metric.weightedYesShare.minCandidate", "passed": true, "message": "The weighted yes share is 1; the policy needs at least 0.6.", … },
    …
  ],
  "approval": { "role": "senior", "count": 1, "separateApprover": true }
}
```

`gate-failed` lists each check that failed, such as
`` This policy needs a comparison: name one with `evalRunId` (a finished comparison eval run of this version). ``
when there's no `--eval-run`.

### Promote through the gate

Promote it the same way, without `--check`:

```sh
kindgi agents promote acme.order-desk 1.3.0 --tenant --eval-run=<comparison-id> --reason="1.3.0 did as well on the order checks"
```

It prints the promotion or the gate's refusal:

- **When the policy has no `approvals`,** a promotion that passes goes live
  at once, `"status": "promoted"`.
- **When it has,** it waits: `"status": "pending-approval"`, with an
  `approvalId`. The scope keeps its version until a reviewer approves.
- **When it fails,** nothing changes. It's refused with every failed check,
  such as `The gate refused acme.order-desk 1.3.0: The weighted yes share rests on 3 judged cases for the candidate; the policy needs at least 20. …`,
  and kept in the history as `refused`.

### Approve it

The request is an approval like any other, for a reviewer with the policy's
role, as [Decide an approval](../../approvals/decide-an-approval/) shows:

```sh
kindgi approvals complete <approval-id> --decision=approve --rationale="Checked the comparison"
```

`<approval-id>` is the promotion's `approvalId`. The version goes live, and
the promotion is `promoted`. Whoever asked can't approve their own request:

```text
Approval <approval-id> was asked for by you: someone else must approve it
```

That holds unless the policy's `approvals` has `"separateApprover": false`.
A deployment that one person uses with the API token has nobody else to
approve, so its gates with `approvals` need `"separateApprover": false`.
With [people of their own](../../../deploy/people-and-keys/), register a
second reviewer instead.

### Promote from your app

Your app checks the gate, then promotes, with the comparison's id as the
script's argument:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// promote-gated.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
const evalRunId = process.argv[2]; // the comparison of 1.3.0
const request = {
  version: '1.3.0',
  scope: { kind: 'tenant' as const },
  evalRunId,
  reason: '1.3.0 did as well on the order checks',
};

// What would the gate say? Nothing is recorded.
const check = await kindgi.agents.promotions.check('acme.order-desk', request);
console.log(check.outcome);
for (const c of check.checks.filter((c) => !c.passed)) console.log(c.message);

if (check.outcome !== 'gate-failed') {
  const promotion = await kindgi.agents.promotions.create('acme.order-desk', request);
  console.log(promotion.status, promotion.approvalId ?? '');
}
```

</TabItem>
<TabItem label="Python">

```python
# promote_gated.py
import sys

from kindgi.client import Kindgi

kindgi = Kindgi()  # KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
request = {
    "version": "1.3.0",
    "scope": {"kind": "tenant"},
    "eval_run_id": sys.argv[1],  # the comparison of 1.3.0
    "reason": "1.3.0 did as well on the order checks",
}

# What would the gate say? Nothing is recorded.
check = kindgi.agents.promotions.check("acme.order-desk", **request)
print(check.outcome)
for c in check.checks:
    if not c.passed:
        print(c.message)

if check.outcome != "gate-failed":
    promotion = kindgi.agents.promotions.create("acme.order-desk", **request)
    print(promotion.status, promotion.approval_id or "")
```

</TabItem>
</Tabs>
