This guide makes an agent version live where you choose, checks which
version a run gets, rolls back, and gates a release behind your test cases.

A run that names no version gets the agent's latest version. Once a new
version has done better on your test cases, as
[Try a version on the test cases](../compare-an-agent-version/) shows, you
can make it **live** where you choose: the whole tenant, an org, a project, or
a segment of a project's runs, such as one company's. Runs there use it from
the next run, nothing changes anywhere else, and you can roll back at once.
[Live versions reference](../live-versions-reference/) has every rule,
refusal and console page.

## Before you start

- **An agent with more than one version,** registered on a runtime such as
  `kindgi dev`, with Kindgi 0.2's CLI. This guide uses `acme.order-desk`,
  with versions 1.0.0, 1.1.0, 1.2.0 and 1.3.0.
- **A project's id,** for a project or a segment: `kindgi projects list`
  lists them.
- **For a release gate policy:** a run of the version on your test cases, and
  a second reviewer to approve.
- **For the app's half:** Node 22.12 or later, or Python 3.11 or later, with
  Kindgi 0.2's client, and `KINDGI_API_URL` and `KINDGI_API_TOKEN` set.

live version wins: a **segment** path in a project, then the **project**, the
project's **org**, the **tenant**, and then the latest version. A segment
path is one or more `key:value` steps, coarse to fine, that a run is started
with: `company:acme`, or `company:acme` then `role:counsel`.

## From your app

Your app can do the same. Ask your coding agent: "I want to make a new version
of my agent live for one company's runs, and check which version a run gets."
For reference, the script looks like this, with the project's id as its
argument:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// release.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
const projectId = process.argv[2];
const acme = [{ key: 'company', value: 'acme' }];

// Make 1.1.0 live for acme's runs in this project.
await kindgi.agents.promotions.create('acme.order-desk', {
  version: '1.1.0',
  scope: { kind: 'segment', projectId, path: acme },
  reason: 'Trying 1.1.0 with acme first',
});

// Which version would a run there use, and why?
const live = await kindgi.agents.live.resolve('acme.order-desk', { projectId, segments: acme });
console.log(live.version, live.via, live.liveScope?.kind);

// A run that names no version gets it.
const run = await kindgi.runs.start({
  agent: 'acme.order-desk',
  projectId,
  segments: acme,
  input: { userMessage: 'Where is order A-1002?' },
});
console.log(run.agent?.version, run.agent?.via);
```

</TabItem>
<TabItem label="Python">

```python
# release.py
import sys

from kindgi.client import Kindgi

kindgi = Kindgi()  # KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
project_id = sys.argv[1]
acme = [{"key": "company", "value": "acme"}]

# Make 1.1.0 live for acme's runs in this project.
kindgi.agents.promotions.create(
    "acme.order-desk",
    version="1.1.0",
    scope={"kind": "segment", "project_id": project_id, "path": acme},
    reason="Trying 1.1.0 with acme first",
)

# Which version would a run there use, and why?
live = kindgi.agents.live.resolve("acme.order-desk", project_id=project_id, segments=acme)
print(live.version, live.via, live.live_scope.kind if live.live_scope else None)

# A run that names no version gets it.
run = kindgi.runs.start(
    agent="acme.order-desk",
    project_id=project_id,
    segments=acme,
    input={"userMessage": "Where is order A-1002?"},
)
if run.agent is not None:  # set on an agent's runs
    print(run.agent.version, run.agent.via)
```

## Gate a release

A **release gate policy** says what a request to make a version live must
show before the version goes live for a scope: a recent run on your test
cases, enough corrected cases, figures at least this good, a clean replay and,
if you want, a reviewer's approval. An agent has one policy per scope. A
request to make a version live is checked by the most specific one covering
its scope, at its latest version.

`--eval-run=<comparison-id>` names the run of 1.3.0 on the test cases, where
`<comparison-id>` is its eval run's id. It prints what the policy would say:

```json
{
  "outcome": "needs-approval",
  "policy": { "id": "acme.order-desk-release", "version": "1.0.0" },
  "checks": [
    { "name": "comparison.freshness", "passed": true, "message": "The test run finished 0.013 hours ago; the policy accepts up to 168.", … },
    { "name": "baselineIsLive", "passed": true, "message": "The test run measured this version against the live version, acme.order-desk 1.0.0.", … },
    { "name": "metric.weightedYesShare.minCandidate", "passed": true, "message": "The weighted share marked right is 1; the policy needs at least 0.6.", … },
    …
  ],
  "approval": { "role": "senior", "count": 1, "separateApprover": true }
}
```

`gate-failed` lists each check that failed, such as
`` This policy needs a test run: name one with `evalRunId` (a finished eval run that tried this version on the test cases). ``
when there's no `--eval-run`.

`--check` exits 0 for `would-promote` and 3 for the other two, so a script
can stop on the answer.

When the test cases have corrections that say what the run should have
done, the summary of the run on the test cases also says how many the
version passed, in `corrections`
([What it should have done](../compare-an-agent-version/#what-it-should-have-done)).
No release gate policy checks it, so name it in the `--reason`, such as
`--reason="Passes 3 of 3 corrections"`.

It prints the request, with its status, or the policy's refusal:

- **When the policy has no `approvals`,** a request that passes goes live
  at once, `"status": "promoted"`.
- **When it has,** it waits: `"status": "pending-approval"`, with an
  `approvalId`. The scope keeps its version until a reviewer approves.
- **When it fails,** nothing changes. It's refused with every failed check,
  such as `The release gate policy refused acme.order-desk 1.3.0: The weighted share marked right rests on 3 corrected cases for this version; the policy needs at least 20. …`,
  and kept in the history as `refused`.

It exits 0 when the version is live, and 3 when it waits for an approval or
the policy refused it.

To wait for the reviewer, add `--wait`. It names the approval it waits for and
the command that approves it, then exits 0 once the version is live, or 3 when
the approval is rejected or expires or the wait runs out: an hour, or the time
`--wait=30m` gives. It exits 3 too when the request is superseded: it was
approved, but something the check measured had changed by then, such as the
version serving the scope or its release gate policy, so promote it again: the
check runs anew. It exits 1 when it can't read the request 3 times in a row,
after printing what it read last. Neither that nor Ctrl-C stops the request:
once it's approved, the version goes live.

The request is an approval like any other, for a reviewer with the policy's
role, as [Decide an approval](../../approvals/decide-an-approval/) shows:


</TabItem>

`<approval-id>` is the request's `approvalId`. The version goes live, and
the request is `promoted`. Whoever asked can't approve their own request:

```text
Approval <approval-id> was asked for by you: someone else must approve it
```

That holds unless the policy's `approvals` has `"separateApprover": false`.
A deployment that one person uses with the API token has nobody else to
approve, so its release gate policies with `approvals` need
`"separateApprover": false`.
With [people of their own](../../../deploy/people-and-keys/), register a
second reviewer instead.

### Make it live from your app

Your app checks the release gate policy, then makes the version live. Ask your
coding agent: "Check the release gate policy for my new agent version, and
make it live unless the policy refuses." For reference, the script looks like
this, with the id of the run on the test cases as its argument:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// promote-gated.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
const evalRunId = process.argv[2]; // the comparison of 1.3.0
const request = {
  version: '1.3.0',
  scope: { kind: 'tenant' as const },
  evalRunId,
  reason: '1.3.0 did as well on the order checks',
};

// What would the gate say? Nothing is recorded.
const check = await kindgi.agents.promotions.check('acme.order-desk', request);
console.log(check.outcome);
for (const c of check.checks.filter((c) => !c.passed)) console.log(c.message);

if (check.outcome !== 'gate-failed') {
  const promotion = await kindgi.agents.promotions.create('acme.order-desk', request);
  console.log(promotion.status, promotion.approvalId ?? '');
}
```

</TabItem>
<TabItem label="Python">

```python
# promote_gated.py
import sys

from kindgi.client import Kindgi

kindgi = Kindgi()  # KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
request = {
    "version": "1.3.0",
    "scope": {"kind": "tenant"},
    "eval_run_id": sys.argv[1],  # the comparison of 1.3.0
    "reason": "1.3.0 did as well on the order checks",
}

# What would the gate say? Nothing is recorded.
check = kindgi.agents.promotions.check("acme.order-desk", **request)
print(check.outcome)
for c in check.checks:
    if not c.passed:
        print(c.message)

if check.outcome != "gate-failed":
    promotion = kindgi.agents.promotions.create("acme.order-desk", **request)
    print(promotion.status, promotion.approval_id or "")
```
