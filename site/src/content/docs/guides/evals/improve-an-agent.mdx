This guide has an Improve run search for better settings or better
instructions for an agent version, within a budget, and write its best
candidate as a suggested change a person reviews.

An **Improve run** does the search a [suggested change](../propose-a-change/)
starts from. It tries candidates on part of the test cases, within a budget,
proves the best one on the cases it didn't learn from, and writes it as a
suggested change only when it's better. A person still decides: the suggested
change waits for a reviewer. On the CLI, `kindgi proposals passes` lists
the Improve runs and `kindgi proposals` the suggested changes.

## Before you start

An Improve run needs what a suggested change does, as
[Propose a change, and test it](../propose-a-change/#before-you-start)
lists:

- **an agent whose instructions or settings are data blocks;**
- **test cases;**
- **a live version of the agent for the whole tenant.** Without one, the
  Improve run is refused with `proposal-needs-pin`;
- **a deployed runtime,** with Kindgi 0.1's CLI. Under `kindgi dev`, it's
  refused with `registry-read-only`;
- **`publish` on the agent,** to start one.

## Mark what Improve may change

An Improve run changes only what you let it. On settings, it changes only the keys a
settings block's schema marks with `"x-kindgi-tunable": true`: a number or an
integer with a `minimum` below its `maximum`, or an `enum`. Any other mark is
refused when the block is published.

```json
{
  "type": "object",
  "properties": {
    "maxSentences": { "type": "integer", "minimum": 1, "maximum": 6, "x-kindgi-tunable": true },
    "tone": { "enum": ["friendly", "formal"], "x-kindgi-tunable": true },
    "refundLimit": { "type": "number", "minimum": 0 }
  }
}
```

Here Improve may try other sentence limits and tones, and never touches the
refund limit. Publish the schema with the block's next version, with
`kindgi blocks publish … --schema=@reply-style.schema.json`, as
[Publish the blocks](../change-a-prompt-or-setting/#publish-the-blocks)
shows. A version that pins no block with a marked key has nothing Improve may change,
and the Improve run is refused, saying so.

## Start an Improve run

An Improve run searches for a better version of the settings Improve may change:

```sh
kindgi proposals improve --agent=acme.rank.scorer --tenant --test-set=acme.rank-prompt-52080 --max-candidates=4 --wait
```

- **The agent and scope:** `--agent` and `--tenant`, or another scope flag.
- **The version** is the one serving the scope, unless `--from-version` names
  another.
- **The test cases:** `--test-set`.
- **The budget:** `--max-cost` in US dollars, 5 by default and at most 100,
  and `--max-candidates`, 30 by default and at most 200. An Improve run stops at
  whichever it reaches first. It checks the cost between runs on the test cases, so the
  one already running can take it a little over `--max-cost`.
- **What better means:** `--objective`, `weightedYesShare` by default or
  `weightedPrecisionAtK`, as in a
  [run on the test cases](../compare-an-agent-version/#read-the-result).
- **How it decides:** it searches on 70% of the test cases and proves
  its best candidate on the other 30% (checked on cases it didn't learn from), a
  split fixed for the Improve run. On the 70%, a candidate has to beat the current
  version by more than the spread between the current version's own repeated
  runs. On the 30%, the best one has to beat the recorded outputs, and only
  then does it become a suggested change, which carries both figures: the recorded
  outputs' score and the candidate's.

It answers at once with the Improve run. `--wait` waits for its outcome, at most 30
minutes, and prints it:

- **`proposed`**, with the suggested change it wrote, which a person decides: run
  `kindgi proposals request <proposal-id>`, then decide the approval. An Improve run's
  suggested change always waits for a reviewer, because an Improve run, not a person, drafted
  it. When the scope's [release gate policy](../release-an-agent-version/#gate-a-release)
  has no `approvals`, that reviewer can be you, if you're registered as a
  reviewer. When it has, someone else must approve it, unless its `approvals`
  sets `"separateApprover": false`.
- **`nothing-found`**, with why. No candidate beat the current version by more
  than the noise on the 70%. Or the best one didn't beat the recorded outputs
  on the 30%: the outcome shows both figures for the cases it didn't learn
  from. Or the best one is a change an existing suggested change already
  holds. Or nothing could be measured: an Improve run scores only the items of
  an output that corrections cover (a ranking's entries, say). So a changed
  free-text answer is a new answer no one has corrected yet and has nothing to
  score, and then you
  [judge the new answers, then rescore](../propose-a-change/#judge-the-new-answers-then-rescore).
  The reason also says if the Improve run ran out of budget before comparing the
  rest.
- **`failed`**, with the reason.

An Improve run is `running`, then `completed`, `failed` or `cancelled`. Here one
tried four candidates. On the search part, setting `fit` to 0 scored best,
but an earlier suggested change already held that change, so it wrote none.
The cost is 0 on `dev-echo`, which costs nothing:

### Whose corrections it learns from

By default, an Improve run counts only the corrections recorded under a
[restricted judge class](../judge-a-runs-output/#restrict-who-may-judge-as-a-class),
`classWeights: "restricted-only"`. So who may steer it is a choice
you make. `"as-recorded"` counts every correction, by its class's weight: set
it in the API or the clients.

## Draft the agent's instructions instead

An Improve run can also draft the agent's instructions. The agent version must take its
instructions from a [data block](../change-a-prompt-or-setting/) it pins.
The CLI starts Improve runs on settings, so start one on instructions from the API or the
clients:

```sh
curl -X POST "$KINDGI_API_URL/v1/proposals/improve" \
  -H "Authorization: Bearer $KINDGI_API_TOKEN" -H 'content-type: application/json' \
  -d '{"agentId":"acme-ops.reply-drafter","scope":{"kind":"tenant"},"suiteId":"acme.reply-cases","tiers":["prompt"],"model":{"providerId":"anthropic","model":"claude-sonnet-5-5"},"candidates":3}'
```

- `$KINDGI_API_URL` and `$KINDGI_API_TOKEN` are your runtime's URL and API
  token.
- `tiers: ["prompt"]` drafts the agent's instructions.
- `model` is the provider and model of yours that drafts them.
- `candidates` is how many drafts it makes: 1 to 5, 3 by default.

It answers at once (`202`) with the Improve run, as the CLI does without `--wait`.

The drafter sees the cases corrected as wrong and their reasons. A draft it
writes is tried on the test cases only if it stays within what the agent already has:

- it parses as Liquid;
- it reads only the prompt's declared parameters, the variables the current
  template reads, `today`, `now`, `agent`, `conversation`, and
  `settings["<id>"]` of a settings block the version pins;
- it names no tool, agent or block id the agent doesn't already use;
- it isn't empty or the current template, and it's at most twice as long as
  the current one: at least 2,000 characters, never over 20,000;
- it quotes no test case: a run of 8 or more words in a row from what the
  drafter was shown is refused, and cut from the hypothesis it keeps.

A refused draft shows in the Improve run's `comparisons` with its issues, as
`refused`, and each drafted one with its `hypothesis`. Here a local model
drafted a template reading a variable the agent doesn't have. The drafts are
that model's words, and yours will differ:

```sh
kindgi proposals passes get <pass-id>
```

```json
{
  "id": "7d56260c-0b5a-43ef-9c56-164c59bd76f7",
  …
  "model": {
    "model": "qwen2.5:7b",
    "providerId": "ollama-qwen"
  },
  …
  "comparisons": [
    …
    {
      "role": "candidate",
      "part": "search",
      "blockId": "acme.rank.prompt",
      "changed": {
        "template": "Rank the candidates from most to least preferred. Consider the following weights for each pair: {{score}}. Report the ranking."
      },
      "hypothesis": "This template emphasizes ranking from most to least preferred and uses {{score}} to include specific weights, aiming to provide more context for accurate ranking.",
      "refused": [
        {
          "path": "/template",
          "message": "it reads \"score\", which the agent doesn't have (a declared parameter, a variable the current template reads, or a settings block the version pins)"
        }
      ],
      "failed": "The drafted template was refused: it reads \"score\", which the agent doesn't have (a declared parameter, a variable the current template reads, or a settings block the version pins)."
    }
  ],
  …
}
```

An Improve run's drafts and hypotheses live on in the run, the suggested change and the
published block version, which erasing a person's words doesn't reach. That's
why a template may not quote a test case, and why a person reviews it before
it goes live.

## Read Improve runs back, or stop one

```sh
kindgi proposals passes list --table
kindgi proposals passes get <pass-id>
kindgi proposals passes cancel <pass-id>
```

- `list --table` prints each Improve run's agent version, scope, status, the
  candidates compared, the cost and the outcome.
- `get` adds its comparisons, each an eval run you can open. `<pass-id>` is
  the Improve run's `id`.
- `cancel` stops a running Improve run: it ends `cancelled` and writes no suggested change.
  An Improve run that already ended answers `409 improvement-pass-finished`.

From your app: `proposals.improve` and `improvementPasses.list`, `get` and
`cancel` in TypeScript; `proposals.improve` and `improvement_passes` in
Python. An endpoint subscribed to `improvement-pass.finished` gets each Improve run
when it ends ([Webhook events and deliveries](../../webhooks/webhook-events/#improvement-passes)).

## Run Improve on a schedule

A schedule can start an Improve run when enough new corrections have come
in, counted the way the Improve run will count them, as
[Improve on a schedule](../../runs/run-on-a-schedule/#improve-on-a-schedule)
shows.

## In the console

The same loop runs in the console. On an agent's **Suggested changes** page,
**Improve** starts an Improve run, and its page follows it. The suggested
change it writes shows its verdict and the figures from the test cases, and an
**Ask to make it live** button to send it for a decision. A schedule that starts Improve runs is made with the CLI,
the API or the clients, as
[Improve on a schedule](../../runs/run-on-a-schedule/#improve-on-a-schedule)
shows: the console lists schedules and can pause, resume, run or remove them, but
doesn't make them.
