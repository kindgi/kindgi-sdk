This guide records whether what a run did and returned was right, counts
some people's corrections more than others, and queues the runs that need a
correction.

A **correction** says whether a finished run's decisions, the tools it
called, were right, whether its answer was right, and what was right
instead. For an answer that is a ranked list, it says which items were
right. People who know the work, your users or your experts, correct it.
Each correction goes to whoever fixes it, and moves on until it's fixed.
The corrections also tell you how an agent or flow version does: they're
the cases of the agent's [test set](../build-a-test-set/), and you
[try a new version](../compare-an-agent-version/) on them.
[Corrections reference](../expert-queue-reference/) has every field, rule and
console page.

## Before you start

- **A finished run to correct,** and its id, on a runtime such as `kindgi dev`,
  with Kindgi 0.2's CLI. [List runs](../../runs/list-runs/) finds one.
- **Write access to the run's project,** when authorization is on.
- **For the app's half:** Node 22.12 or later, Python 3.11 or later, or
  Java 17 or later, with Kindgi 0.2's client, and `KINDGI_API_URL` and
  `KINDGI_API_TOKEN` set.

## Correct a run's answer

A correction records whether the run's answer was right.

From the CLI, correct the run's answer:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi corrections add --run=<run-id> --item=answer --yes --reason="Echoes the message back"
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi corrections add --run=<run-id> --item=answer --yes --reason="Echoes the message back"
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw corrections add --run=<run-id> --item=answer --yes --reason="Echoes the message back"
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw corrections add --run=<run-id> --item=answer --yes --reason="Echoes the message back"
```

</TabItem>
</Tabs>

- `--run=<run-id>` is the run's id.
- `--item=answer` says it's about the run's answer. For a flow run, it's
  `--item=output`, the whole output.
- `--yes` says it was right, or `--no` that it was wrong.
- `--reason` says why. It's optional, but a wrong answer needs one.

It prints the correction:

```json
    "by": { "kind": "user", "id": "26fc414a-b49f-4e1f-a022-162865770178" },

  "createdAt": "2026-10-06T04:08:27.667Z",
```

Nothing in it is wrong, so it's `fixed` as soon as it's saved, as
`recorded-right`.

From your app, when your users correct runs in your own UI, ask your coding
agent: "I want to record whether my user says a run's answer was right." For
reference, the script looks like this, with the run's id as its argument:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts

const correction = await kindgi.corrections.create({

  participantId: 'customer-user-17', // your id for the user who corrected it, if you correct for your users

console.log(correction.id, correction.answer, correction.madeBy);
```

```java
// src/main/java/com/acme/app/RecordCorrection.java
package com.acme.app;

import com.kindgi.client.Kindgi;
import com.kindgi.client.models.CreateCorrectionBody;
import com.kindgi.client.models.Correction;

public final class RecordCorrection {
  public static void main(String[] args) {
    Kindgi kindgi = Kindgi.create(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

    Correction correction = kindgi.corrections().create(CreateCorrectionBody.builder()
        .runId(args[0])
        .answer(CreateCorrectionBody.Answer.RIGHT)
        .why("Echoes the message back")
        .participantId("customer-user-19") // your id for the user who corrected it, if you correct for your users
        .build());
    System.out.println(correction.id() + " " + correction.answer() + " " + correction.madeBy());
  }
}
```

- **`answer`** is `right` or `wrong`. A wrong answer needs what it should
  have said, `shouldSay`, or why it was wrong, `why`.
- **`participantId`** is your app's own opaque id for the user who made the
  correction. Who called comes from the token, as `madeBy`. Your users'
  corrections stay `open` until a person sorts them.
- **For an answer that is a ranked list,** `items` says which items were
  right, as [An agent's test set](../build-a-test-set/#correct-some-runs) shows.
  Each item's `key` is an id, such as the matched case's id, never the
  item's text.
- **One correction per run and person.** Correcting the run again, as the
  same caller and participant, replaces your earlier correction, and the
  earlier one stays in the history. From a client, send the whole
  correction each time. The CLI does that for you: each
  `kindgi corrections add` adds to your correction of the run.

The run now has the correction. Only a finished run can be corrected, and
each item's pointer must find something.
[Corrections](../expert-queue-reference/#corrections) has the rules and the
refusals.

In the console, a finished run's page has **Correct this run**, or a
**Corrections** tab once it has corrections. It lists the answer and each
element of a list in the output, each with **Yes** and **No** and the counts
so far. It lists each correction with who made it, its group and its reason.

## Say what it should have done

A correction of an agent's run can also say what the run should have done
(runtime 0.2.0 or later): the tool calls it should have made, with the
arguments that matter, and the tools it shouldn't have called. It's about
the run's decisions, not its answer. When you
[try a version](../compare-an-agent-version/#what-it-should-have-done) on
test cases built from the run, it checks what that version does against it.

Write what it should have done in a file, such as `refund-fix.json`:

```json
{
  "calls": [
    { "tool": "acme-store.offer-store-credit", "args": { "orderId": "A-1042" } }
  ],
  "notCalled": ["acme-store.refund"]
}
```

- **`calls`** are the calls it should have made. `args` holds only the
  top-level arguments that matter, each compared whole. Arguments left out
  aren't compared, and `{}` asks only that the tool was called.
- **`notCalled`** are the tools it shouldn't have called at all.

Then record it with your mark:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi corrections add --run=<run-id> --no --reason="Final sale: store credit, never a refund" --correction=@refund-fix.json
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi corrections add --run=<run-id> --no --reason="Final sale: store credit, never a refund" --correction=@refund-fix.json
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw corrections add --run=<run-id> --no --reason="Final sale: store credit, never a refund" --correction=@refund-fix.json
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw corrections add --run=<run-id> --no --reason="Final sale: store credit, never a refund" --correction=@refund-fix.json
```

</TabItem>
</Tabs>

- `--correction` is what it should have done, as JSON or `@<file>`.
- `--no` marks the run's decisions wrong.
- It's about the run's decisions, so leave out `--item` and `--pointer`.

It prints the correction, with what it should have done as its `shouldCall`
and `mustNotCall`:

```text
CAPTURE: the printed correction, with "decisions": "wrong", its "shouldCall" and "mustNotCall", "why", "status": "with-owner" and "sortedTo": "owner"
```

- **Part of your one correction of the run.** Saving it again replaces what
  you said about the decisions, and keeps what you said about the answer.
- **It goes to the agent's owner.** Wrong decisions are `with-owner` as soon
  as they're saved: a change to what the agent does may loosen a limit, and
  only the owner decides that.
- **Only the agent's own tools.** A tool the agent version that ran doesn't
  have is refused: `The corrected version has no tool "<tool>".`

From your app, ask your coding agent: "I want to record what my expert says
the run should have done." The clients' `corrections.create` takes it as
`decisions: 'wrong'`, with `shouldCall`, the calls it should have made
(`[{ tool, args? }]`, with `args` only when the inputs matter), and
`mustNotCall`, the tool ids it shouldn't have called. In Python, they're
`should_call` and `must_not_call`. To say its decisions were right, send
`decisions: 'right'` alone.

In the console, a completed agent run's **Correct this run**, or its
**Corrections** tab once it has corrections, has
**What should it have done?**:

1. It lists the run's calls. Keep the ones that were right, and edit or
   untick the argument fields that matter.
2. Flag the calls that shouldn't have happened, and add any the run missed
   with **Add a call…**.
3. Choose **The decisions were wrong** or **The decisions were right**, add
   **Why (optional)**, and **Save correction**.

`remove` prints its id with `"removed": true`.

run's own retention. The clients have the same: `corrections.list`,
`corrections.get` and `corrections.remove`. Their `corrections.list` also
filters by status, sorting, who made it and when, as
[Where a correction goes](#where-a-correction-goes) shows.

## Where a correction goes

Each correction has a `status`, and `sortedTo` says who fixes it:
`improve`, a `developer`, or the agent's `owner`. It's sorted when it's
saved:

- **Your users' corrections,** made with a `participantId`, stay `open` and
  unsorted until a person sorts them. One under a restricted corrector group is
  an expert's, and is sorted like any other.
- **Wrong decisions** go to the agent's owner: `with-owner`, sorted to
  `owner`. This is so even when the answer was wrong too.
- **A wrong answer,** or a wrong item of it, goes to Improve: `open`, sorted
  to `improve`.
- **Nothing wrong** is `fixed`, as `recorded-right`.

A person then moves it on. With `publish` on the agent,
`corrections.change` re-sorts it, changes its status, or both. Here a
developer says they're fixing it, with a link to the work:

```sh
curl -X PATCH "$KINDGI_API_URL/v1/corrections/<correction-id>" \
  -H @<(printf 'Authorization: Bearer %s\n' "$KINDGI_API_TOKEN") -H 'content-type: application/json' \
  -d '{"status":"being-fixed","link":"https://code.acme.example/store/pull/42"}'
```

In TypeScript, that's
`kindgi.corrections.change(correctionId, { status: 'being-fixed', link })`.
It answers the changed correction. A change its status doesn't allow is
refused with `409 correction-status-change-not-allowed`.
[Status and sorting](../expert-queue-reference/#status-and-sorting) has every
status, and [Change a correction](../expert-queue-reference/#change-a-correction)
the changes each allows.

To see how many of a project's corrections are in each status, or one
agent's, count them:

```sh
curl -s -H @<(printf 'Authorization: Bearer %s\n' "$KINDGI_API_TOKEN") \
  "$KINDGI_API_URL/v1/corrections/counts?scopeKind=project&scopeId=<project-id>&agentId=acme-store.refunds"
```

```json
{ "open": 3, "beingFixed": 1, "withOwner": 1, "fixed": 12, "wontFix": 0, "removed": 0 }
```

In TypeScript, that's `kindgi.corrections.counts({ projectId, agentId })`.
To list the ones behind a count, `corrections.list` takes `status`, such as
`not-fixed`, short for `open`, `being-fixed` and `with-owner`, and
`sortedTo`.

## Weight corrections by corrector group

Without a group, every correction counts once. A **corrector group** counts some
people's corrections more, for the tenant, a project, or an agent in a
project.

Add a group, then correct as it:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi corrector-groups add --name=expert --weight=3 --project=<project-id>
pnpm exec kindgi corrections add --run=<run-id> --item=answer --yes --group=<corrector-group-id>
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi corrector-groups add --name=expert --weight=3 --project=<project-id>
uv run kindgi corrections add --run=<run-id> --item=answer --yes --group=<corrector-group-id>
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw corrector-groups add --name=expert --weight=3 --project=<project-id>
./kindgiw corrections add --run=<run-id> --item=answer --yes --group=<corrector-group-id>
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw corrector-groups add --name=expert --weight=3 --project=<project-id>
./kindgiw corrections add --run=<run-id> --item=answer --yes --group=<corrector-group-id>
```

</TabItem>
</Tabs>

- `--name` names the group, and `--weight=3` counts its corrections three
  times.
- `--project=<project-id>` is the project it applies to.
  [Read the test set](../build-a-test-set/#read-the-test-set) shows how to
  find a project's id.
- `--group=<corrector-group-id>` is the group's `id`, which `add` printed. In the
  clients, it's `correctorGroupId`.

The correction now counts with the group's weight.

### Restrict who may correct as a group

An expert group says who may correct as it, so the people using your app
can't move the figures that release a version.

Add the group with a restriction, before your reviewers correct runs:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi corrector-groups add --name=expert --weight=3 --tenant --min-reviewer-role=senior --description="Order desk leads"
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi corrector-groups add --name=expert --weight=3 --tenant --min-reviewer-role=senior --description="Order desk leads"
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw corrector-groups add --name=expert --weight=3 --tenant --min-reviewer-role=senior --description="Order desk leads"
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw corrector-groups add --name=expert --weight=3 --tenant --min-reviewer-role=senior --description="Order desk leads"
```

</TabItem>
</Tabs>

- `--tenant` makes it the tenant's group.
- `--min-reviewer-role=senior` lets only a
  [reviewer](../../approvals/decide-an-approval/#reviewers-and-roles) of that
  role or above correct as it: `standard`, `senior` or `admin`.
- `--description` says who it is for.
- `--principal-kind=user|service` and `--principal-id=<id>`, which repeat,
  restrict it to people or service tokens, or to named ones.

A caller must meet each restriction you set. One who doesn't is refused with
`403`, and nothing is recorded:

```text
Error [auth]: You can't correct as "expert": it needs a senior reviewer or above; you're a standard reviewer.
Error [auth]: You can't correct as "tokens": only service tokens may assert it.
```

A correction made under a restriction carries `"expert": true`. It's
decided when the correction is made, so corrections recorded before the
restriction don't count as expert.
[Corrector groups](../expert-queue-reference/#corrector-groups) has the rest.

## Queue the runs to correct

**Queue rules** pick the project's runs that need a person's correction, so
your experts don't pick runs one at a time. As a run of the project ends,
each rule checks it. A run that any rule matches joins the project's queue of
answers waiting for a correction, **To correct** in the console, once.

To make a rule, ask your coding agent: "Queue a sample of my agent's live runs
for people to correct." For reference, the code looks like this:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// queue-rule.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient();
const project = await kindgi.projects.getDefault();

const rule = await kindgi.projects.queueRules.create(project.id, {
  name: 'Live refund runs',
  when: { agentIds: ['acme.refunds'], versions: ['live'] },
  sample: 0.05, // 5% of them
  maxOpen: 20, // at most 20 waiting at once
});
console.log(rule.ruleId, rule.version);
```

</TabItem>
<TabItem label="Python">

```python
# queue_rule.py
from kindgi.client import Kindgi

kindgi = Kindgi()
project = kindgi.projects.get_default()

rule = kindgi.projects.queue_rules.create(
    project.id,
    name="Live refund runs",
    when={"agent_ids": ["acme.refunds"], "versions": ["live"]},
    sample=0.05,  # 5% of them
    max_open=20,  # at most 20 waiting at once
)
print(rule.rule_id, rule.version)
```

</TabItem>
<TabItem label="Java">

```java
// src/main/java/com/acme/app/QueueRule.java
package com.acme.app;

import com.kindgi.client.Kindgi;
import com.kindgi.client.models.QueueRuleSpec;
import com.kindgi.client.models.QueueRuleWhen;
import com.kindgi.client.models.Project;
import java.util.List;

public final class QueueRule {
  public static void main(String[] args) {
    Kindgi kindgi = Kindgi.create(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

    Project project = kindgi.projects().getDefault();
    var rule = kindgi.projects().queueRules().create(project.id(), QueueRuleSpec.builder()
        .name("Live refund runs")
        .when(QueueRuleWhen.builder().agentIds(List.of("acme.refunds")).versions(List.of("live")).build())
        .sample(0.05) // 5% of them
        .maxOpen(20L) // at most 20 waiting at once
        .build());
    System.out.println(rule.ruleId() + " " + rule.version());
  }
}
```

### Work through the queue

The queue lists the runs waiting for a correction, oldest first. To list the
ones you can close, ask your coding agent: "Show me the runs waiting for my
correction." For reference, the code looks like this:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// expert-queue.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient();
const project = await kindgi.projects.getDefault();

const waiting = await kindgi.projects.expertQueue.list(project.id, { forMe: true });
console.log(waiting.total, waiting.data.length);
```

`forMe: true` keeps the items you can close: those that want a group you
may correct as, or any correction. It prints how many such items wait in all,

Correct each item's run, as [Correct a run's answer](#correct-a-runs-answer) shows. An
item closes as `corrected` once each rule that queued it has the correction it
wants. `expertQueue.dismiss`, with an optional reason, takes a run not worth
correcting out of the queue.
[Answers waiting for a correction](../expert-queue-reference/#answers-waiting-for-a-correction)
has every field and count.

Reading the rules and the queue takes read access to the project. Changing a
rule, and dismissing or reopening an item, take write access, as correcting
a run does.
