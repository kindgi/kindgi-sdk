This guide records people's yes or no on what a run returned, weights some
judges more than others, and queues the runs that need judging.

A **judgment** is a yes or no, with an optional reason, about one item of a
finished run's output: the whole answer, or one element of a list it
returned. People who know the work, your users or your experts, judge. The
judgments then tell you how an agent or flow version does: you
[build a test set](../build-a-test-set/) from them, and
[compare a new version](../compare-an-agent-version/) on it.
[Judging reference](../judging-reference/) has every field, rule and console
page.

## Before you start

- **A finished run to judge,** and its id, on a runtime such as `kindgi dev`,
  with Kindgi 0.2's CLI. [List runs](../../runs/list-runs/) finds one.
- **Write access to the run's project,** when authorization is on.
- **For the app's half:** Node 22.12 or later, Python 3.11 or later, or
  Java 17 or later, with Kindgi 0.2's client, and `KINDGI_API_URL` and
  `KINDGI_API_TOKEN` set.

## Judge an item

A judgment records whether one item of the run's output was right.

From the CLI, judge the run's answer:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi judgments add --run=<run-id> --item=answer --pointer=/response/content --yes --reason="Echoes the message back"
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi judgments add --run=<run-id> --item=answer --pointer=/response/content --yes --reason="Echoes the message back"
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw judgments add --run=<run-id> --item=answer --pointer=/response/content --yes --reason="Echoes the message back"
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw judgments add --run=<run-id> --item=answer --pointer=/response/content --yes --reason="Echoes the message back"
```

</TabItem>
</Tabs>

- `--run=<run-id>` is the run's id.
- `--item=answer` is your id for the item: `answer` for the whole answer.
- `--pointer=/response/content` is where the item is in the run's output, as
  a JSON Pointer.
- `--yes` is the verdict, or `--no`.
- `--reason` (optional) says why.

It prints the judgment:

```json

  "runId": "bc6d1b53-3562-48c9-9f29-719779e3d110",
  "subject": { "kind": "agent", "id": "acme-ops.echo-agent", "version": "0.1.0" },
  "item": { "key": "answer", "pointer": "/response/content" },

  "reason": "Echoes the message back",

  "createdAt": "2026-10-06T04:08:27.667Z",
  …

```

From your app, when your users judge in your own UI, ask your coding agent:
"I want to record my user's yes or no on a run's answer." For reference, the
script looks like this, with the run's id as its argument:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// judge.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

const judgment = await kindgi.judgments.create({
  runId: process.argv[2],
  item: { key: 'answer', pointer: '/response/content' },
  verdict: 'yes',
  reason: 'Echoes the message back',
  participantId: 'customer-user-17', // your id for the user who judged, if you judge for your users
});
console.log(judgment.id, judgment.verdict, judgment.assertedBy);
```

</TabItem>
<TabItem label="Python">

```python
# judge.py
import sys

from kindgi.client import Kindgi

kindgi = Kindgi()  # KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

judgment = kindgi.judgments.create(
    run_id=sys.argv[1],
    item={"key": "answer", "pointer": "/response/content"},
    verdict="yes",
    reason="Echoes the message back",
    participant_id="customer-user-18",  # your id for the user who judged, if you judge for your users
)
print(judgment.id, judgment.verdict, judgment.asserted_by)
```

</TabItem>
<TabItem label="Java">

```java
// src/main/java/com/acme/app/Judge.java
package com.acme.app;

import com.kindgi.client.Kindgi;
import com.kindgi.client.models.CreateJudgmentBody;
import com.kindgi.client.models.JudgedItem;
import com.kindgi.client.models.Judgment;

public final class Judge {
  public static void main(String[] args) {
    Kindgi kindgi = Kindgi.create(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

    Judgment judgment = kindgi.judgments().create(CreateJudgmentBody.builder()
        .runId(args[0])
        .item(JudgedItem.builder().key("answer").pointer("/response/content").build())
        .verdict(CreateJudgmentBody.Verdict.YES)
        .reason("Echoes the message back")
        .participantId("customer-user-19") // your id for the user who judged, if you judge for your users
        .build());
    System.out.println(judgment.id() + " " + judgment.verdict() + " " + judgment.assertedBy());
  }
}
```

- **`participantId`** is your app's own opaque id for the user who judged.
  Who called comes from the token, as `assertedBy`.
- **Judging the same item again,** as the same caller and participant,
  replaces the earlier judgment, and the earlier one stays in the history.

The run now has the judgment. Only a finished run can be judged, and the
pointer must find something.
[Judgments](../judging-reference/#judgments) has the rules and the
refusals.

In the console, a finished run's page has **Judge this run**, or a
**Judgments** tab once it has judgments. It lists the answer and each element
of a list in the output, each with **Yes** and **No** and the counts so far.
It lists each judgment with who made it, its class and its reason.

## See the judgments

A run's judgments say how its output was judged, and by whom:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi judgments list --run=<run-id>      # newest first; replaced and removed ones are left out
pnpm exec kindgi judgments show <judgment-id>       # with copies of the run's input and output, and the item's value
pnpm exec kindgi judgments remove <judgment-id>
```

</TabItem>
<TabItem label="Python">

```sh

```

</TabItem>

```sh
./kindgiw judgments show <judgment-id>       # with copies of the run's input and output, and the item's value
./kindgiw judgments remove <judgment-id>
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw judgments list --run=<run-id>      # newest first; replaced and removed ones are left out
./kindgiw judgments show <judgment-id>       # with copies of the run's input and output, and the item's value
./kindgiw judgments remove <judgment-id>
```

</TabItem>
</Tabs>

- `<run-id>` is the run's id, and `<judgment-id>` a judgment's `id`, from the
  list.
- `list` also filters by agent and version, flow, verdict, judge class,
  participant and project.

`list` prints a page of judgments as JSON: `data`, `hasMore`, and
`nextCursor` when there's another page. `show` prints one judgment, and
`remove` prints its id with `"removed": true`.

A judgment keeps copies of the run's input and output, so it outlives the
run's own retention. The clients have the same: `judgments.list`,
`judgments.get` and `judgments.unregister`.

## Weight judges by class

Without a class, every judgment counts once. A **judge class** counts some
judges more, for the tenant, a project, or an agent in a project.

Add a class, then judge as it:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi judge-classes add --name=expert --weight=3 --project=<project-id>
pnpm exec kindgi judgments add --run=<run-id> --item=answer --pointer=/response/content --yes --class=<judge-class-id>
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi judge-classes add --name=expert --weight=3 --project=<project-id>
uv run kindgi judgments add --run=<run-id> --item=answer --pointer=/response/content --yes --class=<judge-class-id>
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw judge-classes add --name=expert --weight=3 --project=<project-id>
./kindgiw judgments add --run=<run-id> --item=answer --pointer=/response/content --yes --class=<judge-class-id>
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw judge-classes add --name=expert --weight=3 --project=<project-id>
./kindgiw judgments add --run=<run-id> --item=answer --pointer=/response/content --yes --class=<judge-class-id>
```

</TabItem>
</Tabs>

- `--name` names the class, and `--weight=3` counts its judgments three
  times.
- `--project=<project-id>` is the project it applies to.
  [Build the test set](../build-a-test-set/#build-the-test-set) shows how to
  find a project's id.
- `--class=<judge-class-id>` is the class's `id`, which `add` printed. In the
  clients, it's `judgeClassId`.

The judgment now counts with the class's weight.

### Restrict who may judge as a class

A restricted class says who may judge as it, so the people using your app
can't move the figures that release a version.

Add the class with a restriction, before your reviewers judge:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```sh
pnpm exec kindgi judge-classes add --name=expert --weight=3 --tenant --min-reviewer-role=senior --description="Order desk leads"
```

</TabItem>
<TabItem label="Python">

```sh
uv run kindgi judge-classes add --name=expert --weight=3 --tenant --min-reviewer-role=senior --description="Order desk leads"
```

</TabItem>
<TabItem label="Java">

```sh
./kindgiw judge-classes add --name=expert --weight=3 --tenant --min-reviewer-role=senior --description="Order desk leads"
```

</TabItem>
<TabItem label="Scala">

```sh
./kindgiw judge-classes add --name=expert --weight=3 --tenant --min-reviewer-role=senior --description="Order desk leads"
```

</TabItem>
</Tabs>

- `--tenant` makes it the tenant's class.
- `--min-reviewer-role=senior` lets only a
  [reviewer](../../approvals/decide-an-approval/#reviewers-and-roles) of that
  role or above judge as it: `standard`, `senior` or `admin`.
- `--description` says who it is for.
- `--principal-kind=user|service` and `--principal-id=<id>`, which repeat,
  restrict it to people or service tokens, or to named ones.

A caller must meet each restriction you set. One who doesn't is refused with
`403`, and nothing is recorded:

```text
Error [auth]: You can't judge as "expert": it needs a senior reviewer or above; you're a standard reviewer.
Error [auth]: You can't judge as "tokens": only service tokens may assert it.
```

A judgment made under a restriction carries `"restricted": true`. It's
decided when the judgment is made, so judgments recorded before the
restriction don't count as restricted.
[Judge classes](../judging-reference/#judge-classes) has the rest.

## Queue the runs to judge

**Judging rules** pick the project's runs that need a person's judgment, so
your experts don't pick runs one at a time. As a run of the project ends,
each rule checks it. A run that any rule matches joins the project's
**judging queue**, once.

To make a rule, ask your coding agent: "Queue a sample of my agent's live runs
for people to judge." For reference, the code looks like this:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// judging-rule.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient();
const project = await kindgi.projects.getDefault();

const rule = await kindgi.projects.judgingRules.create(project.id, {
  name: 'Live refund runs',
  when: { agentIds: ['acme.refunds'], versions: ['live'] },
  sample: 0.05, // 5% of them
  maxOpen: 20, // at most 20 waiting at once
});
console.log(rule.ruleId, rule.version);
```

</TabItem>
<TabItem label="Python">

```python
# judging_rule.py
from kindgi.client import Kindgi

kindgi = Kindgi()
project = kindgi.projects.get_default()

rule = kindgi.projects.judging_rules.create(
    project.id,
    name="Live refund runs",
    when={"agent_ids": ["acme.refunds"], "versions": ["live"]},
    sample=0.05,  # 5% of them
    max_open=20,  # at most 20 waiting at once
)
print(rule.rule_id, rule.version)
```

</TabItem>
<TabItem label="Java">

```java
// src/main/java/com/acme/app/JudgingRule.java
package com.acme.app;

import com.kindgi.client.Kindgi;
import com.kindgi.client.models.JudgingRuleSpec;
import com.kindgi.client.models.JudgingRuleWhen;
import com.kindgi.client.models.Project;
import java.util.List;

public final class JudgingRule {
  public static void main(String[] args) {
    Kindgi kindgi = Kindgi.create(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

    Project project = kindgi.projects().getDefault();
    var rule = kindgi.projects().judgingRules().create(project.id(), JudgingRuleSpec.builder()
        .name("Live refund runs")
        .when(JudgingRuleWhen.builder().agentIds(List.of("acme.refunds")).versions(List.of("live")).build())
        .sample(0.05) // 5% of them
        .maxOpen(20L) // at most 20 waiting at once
        .build());
    System.out.println(rule.ruleId() + " " + rule.version());
  }
}
```

- `when` is which runs it matches: here, runs of `acme.refunds`'s live

- `sample` is the share of them to queue, `0.05` for 5%.

### Work through the queue

The queue lists the runs waiting for a judgment, oldest first. To list the
ones you can close, ask your coding agent: "Show me the runs waiting for my
judgment." For reference, the code looks like this:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// judging-queue.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient();
const project = await kindgi.projects.getDefault();

const waiting = await kindgi.projects.judgingQueue.list(project.id, { forMe: true });
console.log(waiting.total, waiting.data.length);
```

</TabItem>
<TabItem label="Python">

```python
# judging_queue.py
from kindgi.client import Kindgi

kindgi = Kindgi()
project = kindgi.projects.get_default()

waiting = kindgi.projects.judging_queue.list(project.id, for_me=True)
print(waiting.total, len(waiting.data))
```

</TabItem>
<TabItem label="Java">

may judge as, or any judgment. It prints how many such items wait in all,
and how many are on this page. One item, as that rule queued it:

```json

  "projectId": "153a0091-613e-4c34-9535-da8194f9068e",
  "agentId": "acme.refunds",
  "agentVersion": "2.1.0",
  "flowId": "agent.turn",
```

Judge each item's run, as [Judge an item](#judge-an-item) shows. An item
closes as `judged` once each rule that queued it has the judgment it wants.
`judgingQueue.dismiss`, with an optional reason, takes a run not worth
judging out of the queue. [The judging queue](../judging-reference/#the-judging-queue)
has every field and count.

Reading the rules and the queue takes read access to the project. Changing a
rule, and dismissing or reopening an item, take write access, as judging a
run does.
