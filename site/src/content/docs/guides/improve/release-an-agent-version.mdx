This guide pins an agent version where you choose, checks which
version a run gets, unpins, and gates a pin behind your test cases.

A run that names no version gets the agent's **Latest** in its project: the
version the newest deployment into the project shipped, or the one a person
published there in full, whichever came last. A version derived from an edit
to its prompts or settings isn't Latest by itself, and neither is a higher
number. Once a new version has done better on your test cases, as
[Try a version on the test cases](../compare-an-agent-version/) shows, you
can **pin** it where you choose: the whole tenant, an org, a project, or
a segment of a project's runs, such as one company's. Runs there use it from
the next run, nothing changes anywhere else, and you can unpin at once.
[Pinned versions reference](../pinned-versions-reference/) has every rule,
refusal and console page.

## Before you start

- **An agent with more than one version,** registered on a runtime such as
  `kindgi dev`, with Kindgi 0.2's CLI. This guide uses `acme.order-desk`,
  with versions 1.0.0, 1.1.0, 1.2.0 and 1.3.0.
- **A project's id,** for a project or a segment: `kindgi projects list`
  lists them.
- **For a release gate:** a run of the version on your test cases, and
  a second reviewer to approve.
- **For the app's half:** Node 22.12 or later, or Python 3.11 or later, with
  Kindgi 0.2's client, and `KINDGI_API_URL` and `KINDGI_API_TOKEN` set.

## Pin it for some runs only

pinned version wins: a **segment** path in a project, then the **project**, the
project's **org**, the **tenant**, and then the project's Latest. A segment
path is one or more `key:value` steps, coarse to fine, that a run is started
with: `company:acme`, or `company:acme` then `role:counsel`.

## From your app

Your app can do the same. Ask your coding agent: "I want to pin a new version
of my agent for one company's runs, and check which version a run gets."
For reference, the script looks like this, with the project's id as its
argument:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// release.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
const projectId = process.argv[2];
const acme = [{ key: 'company', value: 'acme' }];

// Pin 1.1.0 for acme's runs in this project.
await kindgi.agents.pinned.pin('acme.order-desk', {
  version: '1.1.0',
  scope: { kind: 'segment', projectId, path: acme },
  reason: 'Trying 1.1.0 with acme first',
});

// Which version would a run there use, and why?
const pinned = await kindgi.agents.pinned.resolve('acme.order-desk', { projectId, segments: acme });
console.log(pinned.version, pinned.via, pinned.pinnedScope?.kind);

// A run that names no version gets it.
const run = await kindgi.runs.start({
  agent: 'acme.order-desk',
  projectId,
  segments: acme,
  input: { userMessage: 'Where is order A-1002?' },
});
console.log(run.agent?.version, run.agent?.via);
```

</TabItem>
<TabItem label="Python">

```python
# release.py
import sys

from kindgi.client import Kindgi

kindgi = Kindgi()  # KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
project_id = sys.argv[1]
acme = [{"key": "company", "value": "acme"}]

# Pin 1.1.0 for acme's runs in this project.
kindgi.agents.pinned.pin(
    "acme.order-desk",
    version="1.1.0",
    scope={"kind": "segment", "project_id": project_id, "path": acme},
    reason="Trying 1.1.0 with acme first",
)

# Which version would a run there use, and why?
pinned = kindgi.agents.pinned.resolve("acme.order-desk", project_id=project_id, segments=acme)
print(pinned.version, pinned.via, pinned.pinned_scope.kind if pinned.pinned_scope else None)

# A run that names no version gets it.
run = kindgi.runs.start(
    agent="acme.order-desk",
    project_id=project_id,
    segments=acme,
    input={"userMessage": "Where is order A-1002?"},
)
if run.agent is not None:  # set on an agent's runs
    print(run.agent.version, run.agent.via)
```

</TabItem>
</Tabs>

It prints the version a run there would get, then the version the run got:

```text

```

## Gate a pin

A **release gate** says what a request to pin a version must
show before the version is pinned for a scope: a recent run on your test
cases, enough corrected cases, figures at least this good, a clean replay and,
if you want, a reviewer's approval. An agent has one release gate per scope. A
request to pin a version is checked by the most specific one covering
its scope, at its latest version.

the tenant one first:

Ask your coding agent to write the release gate:

```text
Before a new version of my agent is pinned, I want it to have done well on my test cases, and a senior reviewer to approve it.
```

For reference, the release gate it writes looks like this. This guide saves it as
`gate.json`:

```json
{
  "comparison": { "maxAgeHours": 168 },
  "evidence": { "minCases": 3 },
  "metrics": [{ "name": "passRate", "minCandidate": 0.6, "maxDrop": 0.02 }],
  "replay": { "maxRefusedWrites": 0 },
  "approvals": { "role": "senior" }
}
```

**For an agent whose job is a write,** such as sending a reply or placing
an order, leave `replay` out and gate on `cases` instead, for example
`"cases": { "minPassing": 3, "noNewFailures": true }`.
[A replay](../compare-an-agent-version/#what-a-replay-does) refuses a call
that changes things unless the past run made the same call, with the same
arguments, and a write the model words, such as a mail's body, almost never
repeats word for word. Each refusal counts in `refusedWrites`, so
`"maxRefusedWrites": 0` refuses every version. To keep `replay`, set
`maxRefusedWrites`, and any other count the version's run on the test cases
shows, to what you accept: those left out are 0.

`--test-run=<test-run-id>` names the run of 1.3.0 on the test cases. It prints
what the release gate would say:

```json
{
  "outcome": "needs-approval",
  "releaseGate": { "id": "acme.order-desk-release", "version": "1.0.0" },
  "checks": [
    { "name": "comparison.freshness", "passed": true, "message": "The test run finished 0.013 hours ago; the gate accepts up to 168.", … },
    { "name": "baselineIsPinned", "passed": true, "message": "The test run measured this version against the pinned version, acme.order-desk 1.0.0.", … },
    { "name": "metric.passRate.minCandidate", "passed": true, "message": "The weighted share marked right is 1; the gate needs at least 0.6.", … },
    …
  ],
  "approval": { "role": "senior", "count": 1, "separateApprover": true }
}
```

`gate-failed` lists each check that failed, such as
`` This release gate needs a test run: name one with `testRunId` (a completed test run that tried this version on the test cases). ``
when there's no `--test-run`.

`--check` exits 0 for `would-pin` and 3 for the other two, so a script
can stop on the answer.

When the test cases have corrections that say what the run should have
done, the summary of the run on the test cases also says how many the
version passed, in `corrections`
([What it should have done](../compare-an-agent-version/#what-it-should-have-done)).
No release gate checks it, so name it in the `--reason`, such as
`--reason="Passes 3 of 3 corrections"`.

It prints the request, with its status, or the release gate's refusal:

- **When the release gate has no `approvals`,** a request that passes is pinned
  at once, `"status": "pinned"`.
- **When it has,** it waits: `"status": "pending-approval"`, with an
  `approvalId`. The scope keeps its version until a reviewer approves.
- **When it fails,** nothing changes. It's refused with every failed check,
  such as `The release gate refused acme.order-desk 1.3.0: The weighted share marked right rests on 3 corrected cases for this version; the gate needs at least 20. …`,
  and kept in the history as `refused`.

It exits 0 when the version is pinned, and 3 when it waits for an approval or
the release gate refused it.

To wait for the reviewer, add `--wait`. It names the approval it waits for and
the command that approves it, then exits 0 once the version is pinned, or 3 when
the approval is rejected or expires or the wait runs out: an hour, or the time
`--wait=30m` gives. It exits 3 too when the request is superseded: it was
approved, but something the check measured had changed by then, such as the
version serving the scope or its release gate, so pin it again: the
check runs anew. It exits 1 when it can't read the request 3 times in a row,
after printing what it read last. Neither that nor Ctrl-C stops the request:
once it's approved, the version is pinned.

`<approval-id>` is the request's `approvalId`. The version is pinned, and
the request is `pinned`. Whoever asked can't approve their own request:

```text
Approval <approval-id> was asked for by you: someone else must approve it
```

That holds unless the release gate's `approvals` has `"separateApprover": false`.
A deployment that one person uses with the API token has nobody else to
approve, so its release gates with `approvals` need
`"separateApprover": false`.
With [people of their own](../../../deploy/people-and-keys/), register a
second reviewer instead.

### Pin from your app

Your app checks the release gate, then pins the version. Ask your
coding agent: "Check the release gate for my new agent version, and
pin it unless the gate refuses." For reference, the script looks like
this, with the id of the run on the test cases as its argument:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// pin-gated.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
const testRunId = process.argv[2]; // the test run of 1.3.0
const request = {
  version: '1.3.0',
  scope: { kind: 'tenant' as const },
  testRunId,
  reason: '1.3.0 did as well on the order checks',
};

// What would the gate say? Nothing is recorded.
const check = await kindgi.agents.pinned.check('acme.order-desk', request);
console.log(check.outcome);
for (const c of check.checks.filter((c) => !c.passed)) console.log(c.message);

if (check.outcome !== 'gate-failed') {
  const change = await kindgi.agents.pinned.pin('acme.order-desk', request);
  console.log(change.status, change.approvalId ?? '');
}
```

</TabItem>
<TabItem label="Python">

```python
# pin_gated.py
import sys

from kindgi.client import Kindgi

kindgi = Kindgi()  # KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev
request = {
    "version": "1.3.0",
    "scope": {"kind": "tenant"},
    "test_run_id": sys.argv[1],  # the test run of 1.3.0
    "reason": "1.3.0 did as well on the order checks",
}

# What would the gate say? Nothing is recorded.
check = kindgi.agents.pinned.check("acme.order-desk", **request)
print(check.outcome)
for c in check.checks:
    if not c.passed:
        print(c.message)

if check.outcome != "gate-failed":
    change = kindgi.agents.pinned.pin("acme.order-desk", **request)
    print(change.status, change.approval_id or "")
```
