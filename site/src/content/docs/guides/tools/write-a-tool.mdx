A tool is a function with a typed input and a typed output. This one looks an
order up by its id. The orders live in a map here; in your app, the handler
calls your own code.

## The tool

Ask your coding agent: "I want a tool that looks up an order by its id."
Kindgi's skills in your pack tell it how
([How it knows Kindgi](../../../start/coding-agents/)). For reference, the
tool looks like this. This guide calls it `my-pack.lookup-order`:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// tools/lookup-order/index.ts
import { defineTool } from '@kindgi/sdk/define';
import type { ToolId } from '@kindgi/sdk/types';
import { z } from 'zod';

// Stands in for your app's database.
const ORDERS = new Map([
  ['ord_1001', { status: 'shipped', totalCents: 4200 }],
  ['ord_1002', { status: 'pending', totalCents: 1250 }],
]);

const defined = defineTool({
  id: 'my-pack.lookup-order' as ToolId,
  description: 'Looks up an order by id. Returns its status and total in cents.',
  version: '0.1.0',
  input: z.object({
    orderId: z.string().regex(/^ord_\d+$/),
  }),
  output: z.object({
    orderId: z.string(),
    status: z.enum(['pending', 'shipped', 'delivered']),
    totalCents: z.number().int(),
  }),
  effects: [],
  mutating: false,
  handler: async ({ orderId }, ctx) => {
    const order = ORDERS.get(orderId);
    if (order === undefined) throw new Error(`No order ${orderId}`);
    console.log(`lookup-order ${orderId} for tenant ${ctx.tenantId}`);
    return { orderId, status: order.status as 'pending' | 'shipped', totalCents: order.totalCents };
  },
});

if (defined.kind === 'err') {
  throw new Error(`my-pack.lookup-order failed to compile: ${defined.error.message}`);
}

export default defined.value;
```

- `input` and `output` are Zod schemas (or JSON Schema). The handler gets the
  parsed input, with defaults and transforms applied.
- `defineTool` returns a result instead of throwing. Unwrap it when the file
  loads, so a bad definition fails at once rather than on the first call.
- `ctx` carries `tenantId`, `runId`, `requestId` and an `abortSignal` that
  fires when the call is cancelled, or passes its deadline
  ([Work that takes longer than a call](#work-that-takes-longer-than-a-call)).
  In a run it also carries `projectId`, the
  run's project, and `orgId`, the project's org when it has one. The runtime
  sets both from the run, never from the input, so compare an id in the input
  with them rather than trusting it.

</TabItem>
<TabItem label="Python">

```python
# tools/lookup_order.py
from typing import Literal

from pydantic import BaseModel, Field

from kindgi import ToolContext, tool

# Stands in for your app's database.
ORDERS = {
    "ord_1001": {"status": "shipped", "totalCents": 4200},
    "ord_1002": {"status": "pending", "totalCents": 1250},
}


class OrderRef(BaseModel):
    order_id: str = Field(alias="orderId", pattern=r"^ord_\d+$")


class Order(BaseModel):
    order_id: str = Field(alias="orderId")
    status: Literal["pending", "shipped", "delivered"]
    total_cents: int = Field(alias="totalCents")


@tool(id="my-pack.lookup-order", mutating=False)
def lookup_order(ref: OrderRef, ctx: ToolContext) -> Order:
    """Looks up an order by id. Returns its status and total in cents."""
    order = ORDERS.get(ref.order_id)
    if order is None:
        raise LookupError(f"No order {ref.order_id}")
    print(f"lookup-order {ref.order_id} for tenant {ctx.tenant_id}")
    return Order(orderId=ref.order_id, **order)
```

- The first parameter's annotation is the input, the return annotation the
  output: pydantic models here (a `TypedDict` or a dataclass works too).
  Field aliases are the names on the wire.
- The docstring is the description. The version is the pack's, unless you
  pass `version=`.
- `ctx` carries `tenant_id`, `run_id`, `request_id` and `cancellation`,
  which fires when the call is cancelled, or passes its deadline
  ([Work that takes longer than a call](#work-that-takes-longer-than-a-call)).
  In a run it also carries `project_id`, the run's project, and `org_id`, the
  project's org when it has one (else `None`). The runtime sets both from the
  run, never from the input. A `def` handler runs in a worker thread, so
  blocking calls are fine; an `async def` handler runs on the event loop.

</TabItem>
<TabItem label="Java">

```java
// src/main/java/mypack/tools/LookupOrder.java
package mypack.tools;

import com.fasterxml.jackson.annotation.JsonProperty;
import com.kindgi.pack.Tool;
import jakarta.validation.constraints.Pattern;
import java.util.Map;

public final class LookupOrder {
  public record Input(@Pattern(regexp = "^ord_\\d+$") String orderId) {}

  public enum Status {
    @JsonProperty("pending") PENDING,
    @JsonProperty("shipped") SHIPPED,
    @JsonProperty("delivered") DELIVERED
  }

  public record Output(String orderId, Status status, long totalCents) {}

  // Stands in for your app's database.
  private static final Map<String, Output> ORDERS = Map.of(
      "ord_1001", new Output("ord_1001", Status.SHIPPED, 4200),
      "ord_1002", new Output("ord_1002", Status.PENDING, 1250));

  public static final Tool<Input, Output> TOOL = Tool.define("my-pack.lookup-order")
      .description("Looks up an order by id. Returns its status and total in cents.")
      .version("0.1.0")
      .input(Input.class)
      .output(Output.class)
      .mutating(false)
      .handler((input, ctx) -> {
        Output order = ORDERS.get(input.orderId());
        if (order == null) throw new IllegalArgumentException("No order " + input.orderId());
        System.out.println("lookup-order " + input.orderId() + " for tenant " + ctx.tenantId());
        return order;
      });

  private LookupOrder() {}
}
```

- The tool is a `public static final` field of a class under `tools/`: the
  indexer finds it there. The package comes from the pack's id (`my-pack` →
  `mypack`).
- `input` and `output` are records, and their schemas come from the records:
  a Jakarta Validation constraint such as `@Pattern` becomes its schema
  keyword, and an enum the list of its JSON values.
- `ctx` carries `tenantId()`, `runId()`, `requestId()` and `cancellation()`,
  which fires when the call is cancelled, or passes its deadline
  ([Work that takes longer than a call](#work-that-takes-longer-than-a-call)).
  In a run it also carries
  `projectId()`, the run's project, and `orgId()`, the project's org when it
  has one (else `null`). The runtime sets both from the run, never from the
  input. Each call runs on its own thread, so blocking calls are fine.

</TabItem>
<TabItem label="Scala">

```scala
// src/main/scala/mypack/tools/LookupOrder.scala
package mypack.tools

import com.kindgi.pack.scaladsl._
import jakarta.validation.constraints.Pattern

object LookupOrder {
  final case class Input(@Pattern(regexp = "^ord_\\d+$") orderId: String)

  enum Status {
    case pending, shipped, delivered
  }

  final case class Output(orderId: String, status: Status, totalCents: Long)

  // Stands in for your app's database.
  private val orders = Map(
    "ord_1001" -> Output("ord_1001", Status.shipped, 4200),
    "ord_1002" -> Output("ord_1002", Status.pending, 1250))

  val tool: Tool[Input, Output] = Tool[Input, Output]("my-pack.lookup-order")
    .description("Looks up an order by id. Returns its status and total in cents.")
    .version("0.1.0")
    .readOnly
    .handler { (in, ctx) =>
      val order = orders.getOrElse(in.orderId, throw new NoSuchElementException(s"No order ${in.orderId}"))
      println(s"lookup-order ${in.orderId} for tenant ${ctx.tenantId}")
      order
    }
}
```

- The tool is a `val` of an object named like its file, under `tools/`: the
  indexer finds it there.
- `Input` and `Output` are case classes, and their schemas come from them: a
  Jakarta Validation constraint such as `@Pattern` becomes its schema
  keyword, and a Scala 3 enum's cases are the values its string may take.
- `ctx` is the same context as in Java: `ctx.tenantId`, `ctx.runId`,
  `ctx.projectId` and `ctx.orgId` (`null` when the project has no org), set
  by the runtime from the run.

</TabItem>
</Tabs>

In every language:

- The id is `<pack-id>.<tool-name>`, in kebab case.
- The description is what a model reads to decide when to call the tool. Say
  what it does and what it returns.
- `mutating: false` (`.mutating(false)` in Java, `.readOnly` in Scala)
  declares that the tool only reads. See
  [Mark a tool read-only](../read-only-tools/).
- A `pattern` (`@Pattern` in Java and Scala) is read as JavaScript's
  `RegExp` reads it, in the runtime. In Python, Java and Scala, the pack
  checks data against it with its own regular expressions too, so it must be
  one both read, as `^ord_\d+$` is:
  - In Python, one JavaScript doesn't read, such as `(?P<name>.)`, is
    refused when the tool is defined. A schema given as a dict has its data
    checked with Python's `re`, so one `re` doesn't read, such as `\p{L}`, is
    refused then too. A pydantic model's `Field(pattern=...)` is checked by
    pydantic, which reads `\p{L}`. One pydantic doesn't read, such as `a\Z`,
    fails when the model class is created.
  - In Java and Scala, one JavaScript or Java doesn't read, such as `[^]`,
    which Java doesn't, is refused when the pack is indexed.
- What the handler prints shows in the `kindgi dev` terminal, prefixed `[pack]`.
- Open files, databases and connections inside the handler, on first use,
  not at the module's top level (in a static field or an object's `val`, in
  Java and Scala). `kindgi build` loads every tool, guardrail and flow module
  to index it, so what a module does when it's loaded runs during the build
  too, inside an image that doesn't have your app's files or services
  ([Build, sign and push your pack](../../../deploy/self-hosted/self-host/#3-build-sign-and-push-your-pack)).

Once the file is saved, `kindgi dev` indexes it and registers the tool; the
next call runs the new code.

## Try it from a flow

A flow step can call any tool, which makes a one-step flow the quickest way
to run one. Ask your coding agent: "I want a flow that runs the order lookup,
so I can try it." For reference, the flow and the command that starts it look
like this:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// flows/check-order/index.ts
import { defineFlow } from '@kindgi/sdk/define';

const defined = defineFlow({
  id: 'my-pack.check-order',
  version: '0.1.0',
  name: 'Check order',
  description: 'Looks up one order.',
  nodes: [
    {
      id: 'lookup',
      kind: 'tool',
      ref: 'my-pack.lookup-order',
      inputMapping: { orderId: { path: 'runInput.orderId' } },
    },
  ],
  edges: [
    { id: 'e-start', from: '$start', to: 'lookup' },
    { id: 'e-end', from: 'lookup', to: '$end' },
  ],
});

if (defined.kind === 'err') {
  throw new Error(`my-pack.check-order failed to compile: ${defined.error.message}`);
}

export default defined.value;
```

## Log from a tool

`ctx.log` writes a record bound to the call: it carries the run's ids, the
tool's id and the runtime's trace id, so it can be found beside the run's own
records ([Logs](../../../deploy/self-hosted/logs/#your-packs-service)). Fields go in as
an object, never in the message. Ask your coding agent: "Log each order my
lookup tool looks up." For reference, it adds a line like this to the
handler:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts excerpt
// in tools/lookup-order/index.ts, in the handler
ctx.log?.info('looked up order', { orderId, status: order.status });
```

The pack service sets `ctx.log`. A context your own code builds may not have
one, so write `ctx.log?.`.

</TabItem>
<TabItem label="Python">

```python excerpt
# in tools/lookup_order.py, in the handler
ctx.log.info("looked up order", {"orderId": ref.order_id, "status": order["status"]})
```

Fields can also be keywords (`order_id=…`). In a test,
`ToolContext.for_test(…)` logs nothing unless you pass it a logger as `log=`.

</TabItem>
<TabItem label="Java">

```java excerpt
// in src/main/java/mypack/tools/LookupOrder.java, in the handler
ctx.log().info("looked up order", Map.of("orderId", input.orderId(), "status", order.status()));
```

`ctx.log().warn("retrying", e)` logs an exception, under `err`. In a
test, `ToolContext.forTest()` logs nothing; `ToolContext.forTest(log)` takes
a logger.

</TabItem>
<TabItem label="Scala">

```scala excerpt
// in src/main/scala/mypack/tools/LookupOrder.scala, in the handler

```

Fields can also be a map. A case class is logged as an object of its fields,
so one named like a secret (`apiKey`) is redacted.

## Make a side effect happen once

A run's step can run more than once: resumed after an approval, retried after
a failure, or run again when the runtime restarted while it ran. A tool that
changes something (a refund, an email, a payment) would then do it twice.

`ctx.idempotencyKey` is the same every time the same call runs, and
different for every other call. Pass it to the system you write to: one that
takes an idempotency key keeps the first request and answers a repeat with its
result. Ask your coding agent: "Make sure my refund tool never issues the same
refund twice." For reference, the handler passes the key on like this:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts excerpt
// in tools/issue-refund/index.ts, in the handler
const res = await fetch('https://payments.acme.example/refunds', {
  method: 'POST',
  headers: {
    'content-type': 'application/json',
    ...(ctx.idempotencyKey !== undefined && { 'Idempotency-Key': ctx.idempotencyKey }),
  },
  body: JSON.stringify({ orderId: input.orderId, amount: input.amount }),
});
```

</TabItem>
<TabItem label="Python">

```python excerpt
# in tools/issue_refund.py, in the handler
headers = {"Idempotency-Key": ctx.idempotency_key} if ctx.idempotency_key else {}
res = httpx.post(
    "https://payments.acme.example/refunds",
    json={"orderId": ref.order_id, "amount": ref.amount},
    headers=headers,
)
```

</TabItem>
<TabItem label="Java">

```java excerpt
// in src/main/java/mypack/tools/IssueRefund.java, in the handler
HttpRequest.Builder request = HttpRequest.newBuilder(URI.create("https://payments.acme.example/refunds"))
    .POST(HttpRequest.BodyPublishers.ofString(body));
if (ctx.idempotencyKey() != null) {
  request.header("Idempotency-Key", ctx.idempotencyKey());
}
```

</TabItem>
<TabItem label="Scala">

```scala excerpt
// in src/main/scala/mypack/tools/IssueRefund.scala, in the handler

  .POST(HttpRequest.BodyPublishers.ofString(body))
Option(ctx.idempotencyKey).foreach(key => request.header("Idempotency-Key", key))
```

</TabItem>
</Tabs>

When the system has no such key, keep it with what you wrote (in a column
that must be unique) and look for it before you write. The key is a UUID.

- **`requestId` won't do.** A model's call id is only unique within one of
  its answers: two turns of a loop can share one.
- **It can be absent** outside a run: a unit test passes its own, or none.
  Check for it, as above; without one, the call can't be deduped on it.

## Work that takes longer than a call

A tool call has a deadline: 120 seconds by default. When it passes, the
call fails with `deadline-exceeded`, and the handler's abort signal fires:
`ctx.abortSignal` in TypeScript, `ctx.cancellation` in Python,
`ctx.cancellation()` in Java and `ctx.cancellation` in Scala. In Java and
Scala the thread is interrupted too, which ends a wait such as `Thread.sleep`.
A handler that doesn't stop then runs on, and what it returns goes nowhere.

- **In an agent,** the failure fails the turn, unless `tool-error` is in
  the agent's `toolErrors.retryOn` (`tool_errors` in Python). Then it goes
  back to the model, which can call the tool again. The list replaces the
  default one, so name `invalid-arguments` and `unknown-tool` in it too to
  keep their retries.
- **In a flow,** it fails the step. An edge's `retry` runs the step again,
  maybe while the first handler still runs, with the same
  `ctx.idempotencyKey` ([Make a side effect happen once](#make-a-side-effect-happen-once)).
  An edge's `timeoutMs` can fail the step sooner, never later.

While a call runs, its run is executing, not waiting. If the runtime stops
in the middle, for a deploy, a restart or a crash, the run fails
([If the runtime stops](../../../concepts/runs/#if-the-runtime-stops)). On a
runtime you run, `KINDGI_PACK_CALL_TIMEOUT_MS` sets the deadline, in
milliseconds. A longer deadline doesn't change that.

So don't make a tool wait for work that takes minutes or hours, such as a
report, a batch job or someone's answer in another system. Hand the work on
instead:

- **Pause the run** until the other system answers. The tool hands that
  system a link and returns `ctx.pause()`. The answer becomes the call's
  result, and the run goes on from there. The run waits parked, for up to
  24 days, so a restart doesn't end it. It's in TypeScript and Python
  ([Wait for another system's answer](../wait-for-another-system/)).
- **Start the job and return its id.** The tool starts the job and returns
  at once. It passes `ctx.idempotencyKey` along, so a call that runs again
  doesn't start a second job ([Make a side effect happen once](#make-a-side-effect-happen-once)).
  When the job ends, it posts its result to a
  [webhook trigger](../../webhooks/start-runs-from-webhooks/), which starts a
  run that takes it on. Your app hears that each run ended from
  [`run.finished`](../../webhooks/receive-run-finished/).
- **Check on a schedule** when the other system can't call back. A
  [scheduled](../../runs/run-on-a-schedule/) flow asks how the job stands,
  and takes it on once it's done.

## Check the run's org

When your app keeps several customers' data, give each customer its own Kindgi
org and project, and start that customer's runs there. A tool then checks what
it reads against the run's org, `ctx.orgId`, which the runtime sets from the
run. An org id in the input is something a model or a caller wrote, so it
proves nothing. Ask your coding agent: "My order lookup tool should only find
orders from the run's own org." For reference, the tool checks it like this:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts excerpt
// in tools/lookup-order/index.ts
// Stands in for your app's database. Each order belongs to one customer's org.
const ORDERS = new Map([
  ['ord_1001', { orgId: '1154e250-2a07-491e-b00a-3675b411c411', status: 'shipped', totalCents: 4200 }],
  ['ord_1002', { orgId: 'feb005e6-6798-47eb-a87a-8feed584d37b', status: 'pending', totalCents: 1250 }],
]);

// …
  handler: async ({ orderId }, ctx) => {
    const order = ORDERS.get(orderId);
    // Another org's order is as missing as one that doesn't exist.
    if (order === undefined || order.orgId !== ctx.orgId) throw new Error(`No order ${orderId}`);
    return { orderId, status: order.status as 'pending' | 'shipped', totalCents: order.totalCents };
  },
```

</TabItem>
<TabItem label="Python">

```python excerpt
# in tools/lookup_order.py
# Stands in for your app's database. Each order belongs to one customer's org.
ORDERS = {
    "ord_1001": {"org_id": "1154e250-2a07-491e-b00a-3675b411c411", "status": "shipped", "totalCents": 4200},
    "ord_1002": {"org_id": "feb005e6-6798-47eb-a87a-8feed584d37b", "status": "pending", "totalCents": 1250},
}


@tool(id="my-pack.lookup-order", mutating=False)
def lookup_order(ref: OrderRef, ctx: ToolContext) -> Order:
    """Looks up an order by id. Returns its status and total in cents."""
    order = ORDERS.get(ref.order_id)
    # Another org's order is as missing as one that doesn't exist.
    if order is None or order["org_id"] != ctx.org_id:
        raise LookupError(f"No order {ref.order_id}")
    return Order(orderId=ref.order_id, status=order["status"], totalCents=order["totalCents"])
```

</TabItem>


with `projectId` on `runs.start`.

## Test it

Ask your coding agent: "Write tests for my order lookup tool." For reference,
the tests look like this, with the command that runs them:

<TabItem label="TypeScript">

`invokeTool` calls a tool the way the runtime does: input checked, handler
called, output checked. It returns a result rather than throwing.
`toolContextForTest()`, also from `@kindgi/sdk/define`, builds a context like

```ts
test('finds a shipped order', async () => {

    kind: 'ok',

test('rejects a malformed id before the handler runs', async () => {
```

## A CommonJS package in TypeScript

A pack's code runs as ES modules, the app modules its tools import
included. `kindgi build` bundles it into `.mjs` files and leaves out the
packages it imports from `node_modules`: the image installs them, and Node
loads them by name. `kindgi dev` and a deployed pack load that code with
Node's own `import()`, with no loader in between.

That shows with a package that ships only CommonJS and puts its class on
`exports.default`, as TypeScript's CommonJS output does for
`export default`. Node gives `import OrdersClient from '@acme/orders-client'`
the package's whole `module.exports`, with the class on its `default`.
Vitest, Next.js, and tsx in an app without `"type": "module"` give the class
itself. So a tool can pass `kindgi test`, and app code it imports can work in
your app, while under `kindgi dev`, and once deployed, the tool fails with
`TypeError: OrdersClient is not a constructor`. With
`"moduleResolution": "NodeNext"`, as a new pack's `tsconfig.json` has,
TypeScript types the import as Node loads it and doesn't compile
`new OrdersClient()`. With `"bundler"`, as Next.js apps have, it compiles.

Take the class either way:

```ts excerpt
import OrdersClientExport from '@acme/orders-client';

type DefaultOf<T> = T extends { default: infer C } ? C : T;

// The class itself under Vitest and Next.js; under Node, the package's
// whole module.exports, with the class on `default`.
function defaultOf<T>(loaded: T): DefaultOf<T> {
  const value = typeof loaded === 'function' ? loaded : (loaded as { default: unknown }).default;
  return value as DefaultOf<T>;
}

const OrdersClient = defaultOf(OrdersClientExport);
```

A dynamic import is the same: `(await import('@acme/orders-client')).default`
is the class under Vitest and, under Node, the package's whole
`module.exports`. Take it with `defaultOf` too:

```ts excerpt
const OrdersClient = defaultOf((await import('@acme/orders-client')).default);
```
