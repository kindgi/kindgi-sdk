This guide gives each customer an org with its projects, runs and reads
their work by project or org, and deletes an org.

A **project** holds runs, conversations, approvals and what they cost. An
**org** groups projects: one org per customer, for example, with a project
for each part of their work. Every tenant has a Default project. A run that
names no project runs in its agent's or flow's own project: the one it was
published in. For what `kindgi deploy` registers, that's the project the
deploy named (`--project`), else Default. A turn in a conversation stays in
the conversation's project.

An agent, flow, tool or test set belongs to the project its first version
was published into, and never moves. Publishing a version of it into another
project is refused with a `409`, and nothing is written. Its code names the
kind, such as `agent-project-mismatch`, `flow-…`, `tool-…` or
`eval-suite-project-mismatch`.
The refusal doesn't name the project it belongs to, since you may not be
able to read that project. A deploy that includes one is refused whole and
deploys nothing, even when that agent or flow is unchanged. Publish new
versions in its own project.

Reading an agent, flow, tool, test set or guardrail says which project
it's in: its `projectId`, with the runtime 0.1.6 or later. A pack
`kindgi dev` serves from disk has none.

## Before you start

- **A runtime,** such as `kindgi dev`, with Kindgi 0.1's client and CLI.
- **Node 22.12 or later, or Python 3.11 or later,** for the client.
- **`KINDGI_API_URL` and `KINDGI_API_TOKEN`** set, or a running
  `kindgi dev`, which the client finds.
- **An agent,** to run in the customer's project. This guide uses
  `acme-ops.echo-agent`.

## Give a customer an org and a project

Create the customer's org and a project in it once, then run the customer's
work there. The script prints the run's status and the org's runs:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
// customer-org.ts
import { createClient } from '@kindgi/sdk/client';

const kindgi = createClient(); // KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

// Once per customer: an org, and a project in it.
const org = await kindgi.orgs.create({ slug: 'acme-customer-one', name: 'Customer one' });
const project = await kindgi.projects.create({ orgId: org.id, slug: 'support', name: 'Support' });

// The customer's work runs in its project.
const run = await kindgi.runs.start({
  agent: 'acme-ops.echo-agent',
  input: { userMessage: 'Echo hello.' },
  projectId: project.id,
});

// Everything in the customer's org, across its projects.
const runs = await kindgi.runs.list({ scope: { kind: 'org', orgId: org.id } });
console.log(run.status, runs.data.map((r) => r.id));
```

</TabItem>
<TabItem label="Python">

```python
# customer_org.py
from kindgi.client import Kindgi

kindgi = Kindgi()  # KINDGI_API_URL, KINDGI_API_TOKEN, or the running kindgi dev

# Once per customer: an org, and a project in it.
org = kindgi.orgs.create(slug="acme-customer-one", name="Customer one")
project = kindgi.projects.create(org_id=str(org.id), slug="support", name="Support")

# The customer's work runs in its project.
run = kindgi.runs.start(
    agent="acme-ops.echo-agent",
    input={"userMessage": "Echo hello."},
    project_id=project.id,
)

# Everything in the customer's org, across its projects.
runs = kindgi.runs.list(scope_kind="org", scope_id=str(org.id))
print(run.status, [str(r.id) for r in runs.data])
```

</TabItem>
</Tabs>

```text
completed [ '68ebe748-4259-4f46-ae21-cf0da3b978c6' ]
```

Keep the org's and the project's ids on the customer's row in your app. From
the CLI, `kindgi runs start … --project=<project-id>` runs in a customer's
project, and `kindgi projects list` lists the projects with their ids.

**Slugs.** An org's slug is unique in the tenant. A project's slug is unique
in its org, so every customer can have a `support` project. A project with
no org has a slug unique among the projects with none. A taken slug is
refused with `409 slug-conflict`:

```text
Another org in the tenant has the slug "acme-customer-one"
Another project in its org has the slug "support" (for a project without an org: another project without one)
```

A tenant has one Default project. Asking for a second one answers
`409 project-default-already-exists`, "The tenant already has a Default
project".

## Deploy a client's pack into its project

Give each client its own project and its own pack. `kindgi init` makes a
pack whose ids all start with its pack id, so two clients' packs never share
an id:

```sh
kindgi init acme-shop --template=woocommerce
cd acme-shop
kindgi deploy --project acme-shop
```

`--project` takes the project's id or its slug. A slug is unique within an
org, so if two orgs each have a project with that slug, the CLI refuses it
and names both ids: pass the id instead. Without `--project`, a deploy is
tenant-wide and registers into the Default project, as before.

What a deploy into a project does, with the runtime 0.1.8 or later:

- **Its agents, flows, tools and guardrails** are registered in that
  project, and the deployment records it (`projectId` on
  `GET /v1/deployments/{deploymentId}`).
- **`kindgi deploy --sync-secrets`** writes the secrets into that project,
  so one client's credentials stay in its own project. A tenant-wide
  deploy writes them tenant-wide.
- **It needs admin on that project** (a tenant-wide deploy needs admin on
  the tenant). An API key limited to another project is refused with
  `403 key-project-mismatch`.
- **A project of another tenant, or none,** is `404 project-not-found`.
- **A suspended project** takes no deploy, where the runtime suspends
  projects: `409 project-suspended`, before anything is written. No run
  starts in it either: `POST /v1/runs` answers the same.

Deploying the same pack into a second project is refused, because its ids
already belong to the first project: `409 tool-project-mismatch` (or
`agent-…`, `flow-…`, `guardrail-…`), and nothing is deployed. The message
names the fix: make a copy of the pack for the new client with `kindgi init`,
which gives every id the new pack's id.

## Read a customer's work

The lists take a `scope`: one project's, or every project's in an org.
In TypeScript, it's `{ kind: 'project', projectId }` or
`{ kind: 'org', orgId }`. In Python, it's
`scope_kind="project", scope_id=…`.

- Runs: [List runs](../../runs/list-runs/).
- Approvals: [Decide an approval](../../approvals/decide-an-approval/).
- Conversations: [Conversations](../../agents/conversations/).
- Where answers came from: [Trace an answer](../../observability/trace-an-answer/).
- What it cost, by month and model: [Cost per run and per customer](../../observability/cost-per-run/).

A record with no project shows only in a list without a scope.

A tool sees the run's project and org, as `ctx.projectId` and `ctx.orgId`.
So it can check that a record belongs to the customer the run is for, as
[Check the run's org](../../tools/write-a-tool/#check-the-runs-org) shows.

## Put a project in production

A project is in production when the customer's real work runs in it:
serving their customers, or processing their live business data. A run in a
project in production is a **production** run, and a run anywhere else is
**staging**. A runtime that counts usage (`KINDGI_USAGE_METERING=on`) labels
each run with its class for usage counting, so test work is counted apart
from real work. A run's own read doesn't show it.

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts
const { productionSince } = await kindgi.projects.setProduction(project.id, true);
// …and out again: productionSince is null.
await kindgi.projects.setProduction(project.id, false);
```

</TabItem>
<TabItem label="Python">

```python
done = kindgi.projects.production.set(str(project.id), production=True)
print(done.production_since)
kindgi.projects.production.set(str(project.id), production=False)
```

</TabItem>
</Tabs>

- **Tenant admins only,** both ways: anyone else gets
  `403 permission-denied`.
- **Setting what's already set changes nothing,** and keeps the first
  `productionSince`. Reading the project shows it while it's in production.
- **The production gate:** a runtime may require the tenant to be allowed
  to put projects in production, for example once it has a payment card
  (`KINDGI_PRODUCTION_GATE=on`). Until then, putting one in production is
  refused with `403 production-not-allowed`, and the error's `details.next`
  says where to go when the runtime names it
  (`KINDGI_PRODUCTION_NEXT_URL`). A project already in production stays so,
  and staging keeps working. `GET /v1/tenant` says where the tenant stands:
  `productionAllowed`, and `productionNext` while it isn't allowed.

  ```json
  {
    "error": {
      "code": "production-not-allowed",
      "message": "This tenant can't put projects in production yet. To be allowed: https://platform.example.com/account/billing. Projects not in production keep working as staging.",
      "details": {
        "projectId": "b3bc8d28-8487-4d90-be57-4e522488f10c",
        "next": "https://platform.example.com/account/billing"
      },
      "requestId": "req-04d7cdca-a8ca-4ff6-87ad-9939387223a0"
    }
  }
  ```
- **A runtime whose projects can't be put in production** answers
  `501 production-unsupported`.

## Delete an org

Delete an org when its customer leaves. With `kindgi` and `org` from the
script:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts excerpt
await kindgi.orgs.delete(org.id);
```

</TabItem>
<TabItem label="Python">

```python excerpt
kindgi.orgs.delete(str(org.id))
```

</TabItem>
</Tabs>

- **The org is gone:** lists leave it out, and fetching it answers
  `404 org-not-found`. Its slug is free at once. Deleting it again changes
  nothing.
- **Its projects and teams stay,** with no org, and so does their work.
- **Its own secrets and their mappings are deleted for good.** Its own
  environments and MCP endpoints are unregistered.
- **Writes to it are refused:** setting a secret in it, registering an MCP
  endpoint in it, and creating or moving a project or a team into it. Creating
  or moving a project or a team there answers `404 org-not-found`, as for an
  org that never existed: `No org with id "0404cbc2-9612-461d-9997-0cbf1d12341a"`.

Kindgi keeps the deleted org's record until a
[retention policy](../../../deploy/retention/) on `org` purges it. That
comes after its environments' and MCP endpoints' own records are purged.
