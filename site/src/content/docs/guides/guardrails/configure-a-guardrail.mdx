This guide gives a guardrail's check its settings, so you change a limit
without touching the check's code. Then it chooses where in the agent's turn
the guardrail runs.

## Before you start

- **The answer-length guardrail** from
  [Write a guardrail](../write-a-guardrail/), in the pack `my-pack`, with
  `kindgi dev` running and Kindgi 0.2's CLI.

## Declare the settings

A check's settings don't belong in its code: a limit, a list of words or a
tool's id, for example. The guardrail declares them as `config`, and the
check runs with them. Ask your coding agent, for example: "I want to change
my guardrail's limit without touching its check." Kindgi's skills in your
pack tell it how ([How it knows Kindgi](../../../start/coding-agents/)).

For reference, the answer-length guardrail has one setting, `maxChars`:

<Tabs syncKey="lang">
<TabItem label="TypeScript">

```ts excerpt
// in guardrails/answer-length/index.ts
export const check = defineCheck({
  id: 'my-pack.checks.answer-length',
  kind: 'zero-llm',
  configSchema: z.object({ maxChars: z.number().int().positive().default(500) }),
  evaluate: async (config, trace) => {
    // config.maxChars: 60 here, or 500 when the declaration gives none
    // …
  },
});

export default {
  id: 'my-pack.answer-length',
  // …
  check,
  config: { maxChars: 60 },
  // …
};
```

`configSchema` describes the settings. `config` in the declaration gives
their values. The check's `evaluate` gets those values, typed from the
schema.

</TabItem>
<TabItem label="Python">

```python excerpt
# in guardrails/answer_length.py
class Config(BaseModel):
    max_chars: int = Field(500, alias="maxChars", gt=0)


@guardrail(
    id="my-pack.answer-length",
    # …
    config={"maxChars": 60},
)
def answer_length(config: Config, trace: RunTrace) -> CheckResult:
    ...
```

The type of the check's first parameter describes the settings. `config=`
gives their values, keyed by their wire names, which are the aliases:
`maxChars`, not `max_chars`.

</TabItem>
<TabItem label="Java">

```java excerpt
// in src/main/java/mypack/guardrails/AnswerLength.java
  public record Config(@JsonProperty(defaultValue = "500") @Positive int maxChars) {}

  public static final Guardrail<Config> GUARDRAIL = Guardrail.define("my-pack.answer-length")
      // …
      .config(Config.class)
      .set("config", Map.of("maxChars", 60))
      .check((config, trace) -> {
        // config.maxChars(): 60 here, or 500 when the declaration gives none
        // …
      });
```

The `Config` record describes the settings: its fields' types and
annotations make the schema, and `@JsonProperty(defaultValue = …)` a
default. `set("config", …)` gives their values, keyed by their wire names.
The check gets those values as a `Config`.

</TabItem>
<TabItem label="Scala">

```scala excerpt
// in src/main/scala/mypack/guardrails/AnswerLength.scala
  final case class Config(@Positive maxChars: Int = 500)

  val guardrail: Guardrail[Config] = Guardrail[Config]("my-pack.answer-length")
    // …
    .set("config", Map("maxChars" -> 60))
    .check { (config, trace) =>
      // config.maxChars: 60 here, or 500 when the declaration gives none
      // …
    }
```

The case class describes the settings: a field's default value is the
schema's default. `set("config", …)` gives their values, keyed by their wire
names. The check gets those values as a `Config`.

</TabItem>
</Tabs>

## Change a setting

next turn uses it. With `maxChars: 300`, the `dev-echo` answer from
[Write a guardrail](../write-a-guardrail/#run-it) passes:

## What the check receives

The check gets `config` resolved by its schema:

- **Defaults are filled in.** A guardrail without `config` runs with the
  schema's defaults; here, a limit of 500.
- **A value that doesn't fit is refused,** and the message names the
  setting. In TypeScript and Python that happens before any turn runs; in
  Java and Scala, on the turns the guardrail checks.

<Tabs syncKey="lang">
<TabItem label="TypeScript">

Zod's `.default()` and a JSON Schema's `default` both apply. When the pack is
indexed, each guardrail's `config` is checked against its `configSchema`, so
`kindgi dev` reports the file and `kindgi build` refuses the pack. With
`config: { maxChars: -5 }`:

```text
guardrails/answer-length/index.ts: guardrail my-pack.answer-length's config doesn't fit its configSchema at /maxChars: must be > 0
```

A setting the schema requires, with no default, must be in `config`:

```text
guardrails/answer-length/index.ts: guardrail my-pack.answer-length's config doesn't fit its configSchema: must have required property 'maxChars'
```

In a deployment, a guardrail registered through the API, with
`kindgi guardrails register`, names the pack's check with its own `config`.
A config that doesn't fit the check's `configSchema` is refused with
`422 guardrail-config-invalid`, and nothing is registered:

```text
Error [invalid-request]: Guardrail "acme.strict-length" doesn't fit check "my-pack.checks.answer-length": config.maxChars must be > 0.
  ✗ /config/maxChars: config.maxChars must be > 0.
```

Under `kindgi dev` the indexer has refused such a config already.

The pack service also checks the config on every call, as sent, against the
indexed `configSchema`. A registered guardrail whose config doesn't fit
fails every turn it checks, whatever its action: the check doesn't run.
`kindgi runs start` exits 1 with:

```text
Error [run-failed]: input-validation-failed: Check "my-pack.checks.answer-length" config failed validation at /maxChars: must be > 0
```

To fix it, unregister the guardrail and register it again with a config that
fits.

</TabItem>
<TabItem label="Python">

The check gets `config` parsed into its type:

- **Defaults are filled in.** Give every field a default: a required field
  with no value isn't caught when the pack is indexed, and fails every turn
  the guardrail checks, whatever its action. `kindgi runs start` exits 1 with
  `Error [run-failed]: input-validation-failed: Check "my-pack.req-cfg" config failed validation: must have required property 'maxChars'`.
- **Values are checked where they're declared.** A value that doesn't fit is
  a `DefinitionError`. `kindgi dev` reports the file, and so does
  `python -m kindgi.pack index`, which indexes the pack:

  ```text
  Guardrail "my-pack.answer-length": config does not fit its type: 1 validation error for Config
  maxChars
    Input should be greater than 0 [type=greater_than, input_value=-5, input_type=int]
  ```

- **A key that isn't a wire name is ignored.** `config={"max_chars": 60}`
  isn't an error: the field keeps its default.

</TabItem>
<TabItem label="Java">

The check gets `config` as a `Config`:

- **Defaults are filled in.** A guardrail without `set("config", …)` runs
  with the schema's defaults; here, a limit of 500.
- **A value that doesn't fit isn't caught before a turn.** Indexing the pack
  and `kindgi dev` accept `Map.of("maxChars", -5)`. The pack service checks
  the config on every call, so the check can't run: with `halt`, every turn
  the guardrail checks fails, and `./kindgiw runs start` exits 1 with:

  ```text
  Error [guardrail-violation]: Turn blocked: guardrail 'my-pack.answer-length' couldn't run its check (check-failed: guardrail "my-pack.answer-length": its check threw: input-validation-failed: Check "my-pack.checks.answer-length" config failed validation at /maxChars: must be > 0)
  ```

  With another action, the turn completes, and the error is recorded as
  [When the check can't run](../halt-or-record/#when-the-check-cant-run)
  describes. Fix the value and save.
- **`set("config", …)` is keyed by wire names**, as the schema names them:
  `maxChars`.

</TabItem>
<TabItem label="Scala">

The check gets `config` as a `Config`:

- **Defaults are filled in** from the case class's default values: without
  `set("config", …)`, a limit of 500.
- **A value that doesn't fit isn't caught before a turn.** Indexing and
  `kindgi dev` accept `Map("maxChars" -> -5)`. The pack service checks the
  config on every call, so the check can't run: with `halt`, every turn the
  guardrail checks fails, and `./kindgiw runs start` exits 1 with:

  ```text
  Error [guardrail-violation]: Turn blocked: guardrail 'my-pack.answer-length' couldn't run its check (check-failed: guardrail "my-pack.answer-length": its check threw: input-validation-failed: Check "my-pack.checks.answer-length" config failed validation at /maxChars: must be > 0)
  ```

  With another action, the turn completes, and the error is recorded as
  [When the check can't run](../halt-or-record/#when-the-check-cant-run)
  describes. Fix the value and save.
- **`set("config", …)` is keyed by wire names**, as the schema names them.

</TabItem>
</Tabs>

## Where in the turn it runs

A guardrail judges the agent's final answer unless it says otherwise. `at`
says where in the turn it runs:

- **`'final-answer'`**, the default: the answer the turn would store.
- **`'before-tool'`**: a tool call the model asked for, before it runs. It
  runs after the call's access check, and before any approval is asked.
- **`'after-tool'`**: what a call returned, or the error it threw, before the
  model sees it.
- **`'model-step'`**: a model reply that asks for tool calls, before any of
  them runs.

What `halt`, `retry` and the other actions do at each point is in
[At a tool call or a model reply](../halt-or-record/#at-a-tool-call-or-a-model-reply).

A guardrail runs only where its check can. A check names its points with
`points` ([Check a tool call or a reply](../write-a-guardrail/#check-a-tool-call-or-a-reply)).
A check that names none runs at the final answer only. The built-in checks'
points are in [Where each check runs](../use-a-built-in-check/#where-each-check-runs).

At `'before-tool'` and `'after-tool'`, **`scope.tools`** limits the
guardrail to the tools it names, by id. A trailing `*` matches every id with
that prefix, such as `acme.crm.*`. Left out, the guardrail checks every
tool's calls.

<Tabs syncKey="lang">
<TabItem label="TypeScript">

This guardrail withholds any result of an `acme.crm` tool that contains
`SECRET`, before the model sees it:

```ts
// guardrails/no-secret-in-results/index.ts
export default {
  id: 'my-pack.no-secret-in-results',
  kind: 'zero-llm',
  check: 'forbidden-substring',
  config: { patterns: ['SECRET'] },
  at: 'after-tool',
  scope: { tools: ['acme.crm.*'] },
  action: { 'on-violation': 'retry' },
  severity: 'error',
};
```

When the pack is indexed, `kindgi dev` reports the file and `kindgi build`
refuses the pack if:

- `at` isn't one of the values above;
- `scope.tools` is empty, has a `*` anywhere but the end, or is set at
  `'model-step'` or `'final-answer'`;
- the action is `'escalate'` or `'compensate'` away from the final answer;
- the pack's own check doesn't run at `at`.

The answer-length check names no points, so with `at: 'before-tool'`:

```text
guardrails/answer-length/index.ts: guardrail my-pack.answer-length runs at 'before-tool', which isn't one of its check's points (final-answer)
```

Deploying the pack, or registering the guardrail through the API, refuses
the same, and also a built-in check at a point it doesn't run at. A deploy
fails with `deployment-validation-failed`, each problem named with its
guardrail and its path: `/at`, `/action/on-violation` or `/scope/tools`.
Registering answers `422 guardrail-config-invalid` for a check that doesn't
run at `at`, and `400 validation-failed` for the others.

</TabItem>
<TabItem label="Python">

A Python guardrail runs at the final answer only. `@guardrail` has no field
for `at`, and a check has no `points`, so `scope.tools` doesn't apply
either.

</TabItem>
<TabItem label="Java">

A Java guardrail runs at the final answer only. `Guardrail.define` has no
method for `at`, and a check has no `points`, so `scope.tools` doesn't apply
either.

</TabItem>
<TabItem label="Scala">

A Scala guardrail runs at the final answer only. `Guardrail[Config](…)` has
no method for `at`, and a check has no `points`, so `scope.tools` doesn't
apply either.

</TabItem>
</Tabs>

### How long its check may take

At `'before-tool'`, `'after-tool'` and `'model-step'`, a check may take as
long as its guardrail's `budget.maxLatencyMs`, such as
`budget: { maxLatencyMs: 2_000 }` for two seconds. Past it, the agent loop
stops waiting for the check and cancels it. A guardrail without one gets a
limit by its kind: 10 seconds for `zero-llm`, 60 for `llm-judge` and 30 for
any other. A check cancelled this way fails with `check-timed-out`, and the
guardrail's action handles it as a check that couldn't run
([When the check can't run](../halt-or-record/#when-the-check-cant-run)).
A pack's check already running on its service can still finish there; its
result is dropped.

At the final answer, a check has no time limit. `budget.maxCostUsd` isn't
enforced at any point.
